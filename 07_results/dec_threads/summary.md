# 앱 FFmpeg HEVC 프레임 스레드 수: 스윕과 자동 대 1스레드 회귀 A/B

## 측정 조건
- 측정 일시: 2026-09-29 10:3x~12:16 KST
- 목적: 앱(`yvo_pipeline`)의 FFmpeg 디코더 스레드 기본값(`thread_count=0` = 자동, `av:hevc:df0~4` 5개)을 1로 바꾸기 전에 두 가지를 본다.
  1. 스레드 수에 따라 CPU·지연·붙잡은 프레임 수가 어떻게 변하는가
  2. 1스레드가 다른 모드에서 회귀를 내는가
- 배경: [`gst_pipeline/runs/perf_dec_threads`](../gst_pipeline/runs/perf_dec_threads/summary.md)가 앱 대 GStreamer CPU 차이의 원인을 FFmpeg 프레임 스레딩으로 확정했다. 사용자가 기본값을 1로 바꾸기로 했다.
- 환경(자세한 값은 [`env_bench.txt`](env_bench.txt))
  - 부트로더 2026-09-25, `v3d_freq=1150`, PCIe Gen3, libavcodec61 `7.1.5-0+deb13u1+rpt2`, git `00ec210`
  - `throttled=0x80000`은 과거 soft temp 기록 비트이고, 현재 비트는 0이다.
- 방법
  - `RUNS=3 bash 06_tools/bench/dec_threads_bench.sh`로 21개 설정을 3회 인터리브했다(63회).
  - 스레드 수는 `YVO_DEC_THREADS`로 준다(1b9be7f). 자동은 변수를 설정하지 않은 경로다.
  - 매 실행 전 칩을 65 °C 이하로 식혔다. 표시 실행은 HDMI-A-1 확인 후 `timeout -s KILL 90`으로 감쌌다.
- 신뢰성: 63회 모두 exit 0이고, `hailort.log` warning 0, error 0, 불안정 판정 0, 실패한 설정 0이다.
- 입력: `video_h265.mp4`. 스윕, ptr·nhwc b8, nhcw b1·b4는 전체 1816프레임이고, GPU 후처리·지연·표시 설정은 900프레임이다.

## 결론
1. **스레드가 적을수록 CPU와 지연이 모두 줄고, 처리량과 정확도는 같다.**
   - 1스레드는 자동(5) 대비 CPU −0.49 ms/f(−14%), e2e 평균 −8.8 ms, p90 −15 ms다.
   - 2스레드부터 CPU와 지연이 뛴다. 프레임 스레딩이 켜지면서 스레드 간 전달 비용과 출력 지연((스레드 수 − 1)프레임 분량의 구조적 지연)이 생긴다. 3~5스레드는 비슷하다.
   - NPU 지연도 1스레드에서 짧다(297 대 306 ms). 프레임이 NPU 큐에 덜 쌓이기 때문으로 본다(**추정**).
   - HW 디코드를 쓰는 이 파이프라인은 디코드 처리량이 필요 이상(1스레드 약 266 FPS)이므로, 프레임 스레딩은 이득 없이 부담만 준다.
2. **회귀: 8개 모드 모두 FPS와 검출이 같다. CPU는 모두 같거나 줄고, e2e 평균은 모두 줄었다(−0.5~−9.2 ms).**
3. **예외: 표시 on(source pace)에서 앱 내부 e2e p90이 3회 모두 약 +1.9 ms(+1.9%) 높다.** 범위가 겹치지 않으므로 재현되는 차이다.
   - 사용자가 보는 glass-to-glass 평균은 같다(99.5 대 99.5 ms). glass p90은 실행 사이 흔들림(112.6~120.9 ms) 안에 있어 판정할 수 없다. presented 900, dropped 0으로 같다.
   - 원인은 가르지 못했다. source pace(30 FPS 소스 시계)에서 1스레드 디코드가 가끔 한 프레임의 준비를 늦추는 것으로 추정한다(**추정**).
   - 같은 설정의 CPU는 −14%다.
4. 앱 기본값을 1로 바꾸면 CPU·지연·held frame 여유에서 모든 비표시 모드가 좋아진다. 표시 on에서는 앱 내부 p90이 약 2 ms 늘어나는 대가가 있다. 기본값 결정은 이 트레이드오프를 보고 정한다.

## 주의
- 설정 순서가 고정이라 A/B 쌍 안에서 항상 자동이 먼저 돈다. 매 실행 전 냉각으로 순서 편향을 줄였지만 교대하지는 않았다.
- 표시 실행은 900프레임, source pace, 전체화면, labwc Vulkan 합성 백엔드(기본)만 쟀다. `wayland-planes`·`kms` 백엔드와 asap pace는 재지 않았다.
- 1스레드 디코드의 처리량 상한(약 266 FPS, `ffmpeg_drm_decoder.cpp:180` 주석 기준)은 이 측정에서 직접 재지 않았다. 여러 스트림을 동시에 처리하거나 NPU 병목이 없는 용도에서는 자동이 나을 수 있다.
- `held_frames_max`는 디코더 한계(약 13장)와 멀다(최대 4).

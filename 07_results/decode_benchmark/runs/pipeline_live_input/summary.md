# 실시간 입력 모사에서 HW 디코드 대 SW 디코드 (2026-11-06)

[`pipeline_sw_hw`](../pipeline_sw_hw/summary.md)는 파일 입력이라 소프트웨어 자동 스레드가 도착 전에 미리 디코드했다. 이 회차는 `--input-live`로 패킷을 도착 시각에야 디코더에 보내, 미리 읽을 수 없는 입력을 모사했다.

## 측정 조건

- 하드웨어·거버너(performance 고정, trap 원복)·모델·입력은 [`technique_ablation`](../../../technique_ablation/summary.md)과 같다. 코드 커밋 `4593529`, 바이너리 md5 `c8515629c17b1714f54c02c4021f9c76`.
- 공통: 배치 1/슬롯 1, 입력 페이싱 source, 입력 큐 1, 표시 on(Vulkan 합성), 기록 on, `--input-live`.

## 결론

- **미리 읽을 수 없는 입력에서는 하드웨어 디코더가 CPU와 지연 모두 낫다.** `sw_auto`는 CPU 약 25배(31.221 대 1.232)에 평균 지연이 132 ms 길다(221.88 대 89.73). 파일 입력에서 같아 보이던 지연(53.66 대 53.62)은 미리 디코드의 효과였다.
- **이 132 ms는 프레임 스레드 지연과 맞다.** 디코더 출력 지연이 5패킷 대 1패킷이고, 4패킷 차는 30 fps에서 133 ms다.
- **`sw_t1`은 평균은 처리하지만 안정적이지 않다.** 디코드를 전용 스레드로 분리하면 24.24 fps를 유지해, 메인 스레드 구현의 13.82 fps는 디코더 한계가 아니라 구조 때문이었음을 보여 준다. 다만 일부 구간에서 뒤처져(원인 미확인) 지연 p90이 343 ms, 최대 553 ms다. 평균도 실행에 따라 156~199 ms로 흔들린다.
- `hw_t1`도 파일 입력보다 36 ms 길다(89.73 대 53.62). 이 영상은 B 프레임 재정렬이 있어(`live_reorder` 1) 1패킷(33 ms)이 더해지기 때문이다. 재정렬 없는 카메라 스트림이라면 줄어들 것이다(재지 않음).

## 주의·남은 일

- **모사의 한계:** 패킷을 버리지 않는다. 디코드가 늦으면 패킷 전송도 밀린다(`sw_t1` 전송 지각 평균 42.8, 최대 424 ms). 실제 카메라라면 프레임 손실로 나타날 수 있다.
- 슬라이스 스레드는 재지 않았다. 지연이 적은 멀티스레드 대안이 될 수 있지만 스트림의 슬라이스 구성에 좌우된다.
- `sw_t1` 3회 중 run1이 다른 두 회보다 크다(평균 199 대 156~158). 원인은 찾지 않았다.
- 소프트웨어 디코드 CPU 배율은 영상 비트율에 따라 달라질 수 있다. 영상 1개 값이다.

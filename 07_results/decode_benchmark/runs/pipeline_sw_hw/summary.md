# 결정된 파이프라인에서 HW 디코드 대 SW 디코드 (2026-11-05)

`yvo_pipeline` 기본 운용점(O2)과 Vulkan 합성 표시를 그대로 두고 **디코더만** 바꿔 비교했다.
SW 경로는 libavcodec 소프트웨어 HEVC 출력(yuv420p)을 CPU가 dma-heap의 SAND128 NV12 버퍼로 복사하고, 전처리부터는 HW와 같은 코드를 탄다(`--decoder sw`).

## 측정 조건

- 날짜: 2026-11-05 23:19~23:32. 벤치 `06_tools/bench/decode_pipeline_bench.sh`, 3회 인터리브, 실행 전 냉각. 환경은 [`env_bench.txt`](env_bench.txt).
- 하드웨어: Raspberry Pi Compute Module 5, Hailo-8, PCIe Gen3 x1, V3D 1150 MHz, ARM 2.4 GHz.
- **CPU 거버너 performance 고정**(측정 동안만, trap으로 `ondemand` 원복).
- 모델 `yolov11m.hef`, HailoRT 4.24.0, libavcodec61 7.1.5 rpt2. 입력 `video_h265.mp4`(1080p30, 1,816프레임).
- 공통 운용: 배치 1, 슬롯 1, 입력 페이싱 source, 입력 대기열 1, NHCW dma-buf, GPU 후처리·NMS, 표시 on(전체화면 HDMI-A-1), 기록 on(`--frame-log`, `--dump-dir`).
- 코드: HEAD `85ad459` + 미커밋 변경, 바이너리 md5 `9c4ff420ad740cfa002de7a365692f77`(측정 뒤 같음).

| 설정 | 디코더 | 프레임 스레드 |
|---|---|---|
| `hw_t1` | HW(DRM_PRIME) | 1 |
| `sw_t1` | SW + CPU 복사 | 1 (메인 스레드에서 디코드) |
| `sw_auto` | SW + CPU 복사 | 자동 (`av:hevc:df` 5개) |

## 결론

- **HW 디코더는 앱 CPU를 도착 프레임당 약 30 ms 줄인다(30.939 → 1.188, 약 26분의 1).** 처리 기준으로는 38.248 → 1.465 ms다. 시스템 전체로도 33.585 → 3.420 ms로 약 10분의 1이어서, 커널 쪽으로 비용이 옮겨 간 것이 아니다.
- **FPS·지연은 SW 자동이 HW와 사실상 같다**(24.26 대 24.31, 평균 53.66 대 53.62 ms). 두 경로 모두 NPU 주기에 묶인다. 대가는 코어 약 1개(시스템 1.007 대 0.103 코어)다. 단, SW 자동 값은 파일 입력의 미리 디코드가 도운 값이다(아래 주의).
- **SW 1스레드는 이 파이프라인에서 실시간을 못 맞춘다.** FPS 13.82, 버림 53.9%, 디코드 지각 p90 143.75 ms다. 디코드가 메인 스레드에서 돌아 제출과 표시까지 함께 밀리기 때문이다.
- 이 차이의 대부분은 디코드 자체다. SW의 CPU 복사는 1.1~1.5 ms로 차이 약 30 ms의 5% 정도다.
- **검출은 디코더와 무관하게 같다.** 전체 1,816프레임(asap, 표시 off)에서 `detections.jsonl`이 HW·SW 1스레드·SW 자동 모두 바이트 동일하다([`evidence/bit_exact_detections.txt`](evidence/bit_exact_detections.txt)). 페이싱 실행의 검출 수가 다른 것은 버린 프레임이 달라서다.
- 교차 확인: `hw_t1` 1.465(1.436~1.523)는 [`demo_before_after`](../../../demo_before_after/summary.md)의 적용 후 1.492(1.459~1.494)와 범위가 겹친다.

결정: SW 경로는 CPU 복사 + 기존 셰이더로 넣고, O2 표시 on에서 SW 1스레드·자동을 HW 1스레드와 비교한다 (사용자 결정, 2026-11-05)
결정: `--decoder sw`일 때만 페이싱 루프가 프레임 1개를 디코드한 뒤 제출 기회를 준다 (사용자 결정, 2026-11-05)

## 신뢰성

- `hailort.log` warning·error는 9회 모두 0건, 종료 코드 0, `all_ok` 전부 1이다.
- SoC는 5초 간격 기록([`evidence/soc_watch.csv`](evidence/soc_watch.csv))에서 64.8~77.9 °C다. 실행 전 게이트(≤ 75 °C)는 통과했고, 실행 중 최고치가 게이트를 넘었으나 `get_throttled`는 내내 `0xe0000`(현재 비트 0, 상위는 이력)이다. Hailo 칩은 실행 전 57.1~65.1 °C로, `sw_t1` run3의 65.1 °C가 프로젝트 게이트(≤ 65 °C)를 0.1 °C 넘었다. 그 실행의 `hailort.log`에 온도·클럭 경고는 없다. 이 실행의 FPS 13.67·CPU 63.051은 세 회차 중 최저·최고(중앙값과 약 1% 차이)이지만 표의 중앙값은 run1 값이라 영향을 주지 않는다. 재측정하지 않고 유지한다.

## 주의·남은 일

- **SW에만 루프 차이가 있다.** 위 결정의 한 줄이다. 이 수정 전 `sw_t1`은 표시 off 시험에서 제출이 최대 10.36초 멈췄다(별도 시험, 보관 안 함). HW 경로는 바뀌지 않았다.
- **`sw_auto`는 파일 입력이라 유리하다.** 프레임 스레드가 도착 전에 미리 디코드해 둔다. 실시간 카메라처럼 미리 읽을 수 없는 입력에서는 스레드 수만큼 지연이 더해질 것으로 보이나 재지 않았다.
- **SW는 복사 조건이다.** 디코더가 dma-buf에 직접 쓰는 무복사 구성은 재지 않았다(기각, 사용자 결정 2026-11-05).
- 영상 비트율이 높은 후반 구간에서 `sw_t1`이 특히 늦다. 구간별 값은 `raw/*/frame_log.csv`로 다시 낼 수 있고 여기서는 집계하지 않았다.
- `sys_ms_per_arrived`에는 측정과 무관한 활동도 들어간다. 측정 중 `btop`(CPU 0.2%)과 원격 모니터 루프가 떠 있었고, 진행 확인 명령도 한 번 돌렸다. `hw_t1`의 범위 2.115~4.113이 그 잡음의 크기다.
- `wayland-planes`·kms 표시, 처리량 운용점(b8/s16)과의 조합은 재지 않았다.
- `decode_ms_mean`은 경로마다 의미가 달라(스레드 유무) 설정끼리 비교하지 않는다.

## 정정 (2026-11-05, 메인 에이전트 — 위 본문은 고치지 않는다)

- §신뢰성의 "표의 중앙값은 run1 값이라 영향을 주지 않는다"는 FPS·CPU에만 맞다. `sw_t1`의 지연 표에서 `e2e_arr` 평균 86.41·p90 118.72·최대 408.43과 `decode_late` 평균 53.64·p90 143.75·최대 340.70의 중앙값은 Hailo 65.1 °C였던 **run3의 값**이다. 이 실행의 `hailort.log`에 온도·클럭 경고는 없고, 세 회차의 평균은 83.93~86.68 ms로 차이가 약 3%다. 재측정하지 않는 판단은 그대로다.

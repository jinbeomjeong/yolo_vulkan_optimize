# 표시 통합 e2e 재측정 + 컴포지터 CPU — V3D 1150 MHz · 코드 `2f2d3d0` (2026-10-16)

[`../v3d1150_20261016`](../v3d1150_20261016/summary.md)와 같은 벤치·설정·집계에 **컴포지터(labwc) CPU 기록**을 더해 다시 쟀다.
벤치는 커밋 `ad905cd`이고, `display_bench.sh` 61열이다.

이번 재측정은 논문 심사 지적에 따른 것이다. 헤드라인 CPU(`cpu_ms_per_frame`)는 응용 프로세스의 user+sys만 센다(`getrusage(RUSAGE_SELF)`).
그런데 표시를 켜면 컴포지터가 별도 프로세스로 CPU를 쓴다. 그래서 같은 회차에서 **응용 + 컴포지터**를 함께 얻는다.

## 1. 측정 조건

- 날짜: 2026-10-16 08:14~08:26 (KST). 하드웨어는 Pi 5, Hailo-8, PCIe **Gen3 x1**이다.
  - V3D 클럭은 1150 MHz다. 측정 직전에 `v3d_freq=1150`, `measure_clock v3d` 1150.0 MHz를 확인했다(status-reporter).
  - 표시는 HDMI-A-1 1920×1080@60, labwc 0.20.2 / libwlroots 0.20.2+rpt4다.
- 코드: 커밋 **`2f2d3d0`**. 바이너리 md5 `3dda5b0f…`는 이전 회차와 같다.
- 명령: `RUNS=3 FRAMES=900 OUT_DIR=07_results/display_e2e/runs/v3d1150_labwc_20261016 bash 06_tools/bench/display_bench.sh`
  - 콘솔 전문은 [`raw/_session/bench_stdout.log`](raw/_session/bench_stdout.log)다.
- 컴포지터 CPU
  - 실행마다 `raw/<run>/labwc_stat_{pre,post}.txt`에 같은 labwc pid의 utime+stime 차를 남기고, 처리 프레임 수로 나눈다.
  - 창은 `yvo_pipeline` 프로세스 수명 전체다. 앱 창(측정 구간 getrusage)보다 기동·종료 몫만큼 넓다.
  - 같은 회차 표시 off 실행의 labwc는 실행당 10~20 ms(약 0.4~0.8 ms/s)라, 기동·종료 몇 초 몫은 프레임당 0.01 ms 미만이다.
  - 해상도는 10 ms 틱이다.
- 신뢰성
  - 12회 모두 `hailort.log` warning 0, error 0이다.
  - 검출은 3369, 표시 드롭 0, slot timeout 0이다.
  - 냉각 5회, 칩 최고 79.5 °C다.

## 3. 결론

- **헤드라인 CPU는 컴포지터를 넣으면 감소율이 줄어든다.**
  - 응용만 −47.9%, 응용 + 컴포지터 −32.9%(범위 −26 ~ −38%)다.
  - 표시 경로가 더하는 호스트 CPU의 약 43%(0.48 / 1.10 ms)가 컴포지터 몫이다.
  - 방향("표시를 켜고도 기준보다 낮다")은 유지된다.
- 이전 회차와 비교해도 처리량·검출·GPU 구간·지연은 실행 간 범위 안이다.
  - 이전 회차 값: `disp_asap` CPU 1.626, `disp_source` glass 100.10 [95.40–100.11], GPU 합 6.036
- **응용 CPU는 같은 회차 안에서도 흔들림이 크다.**
  - `disp_source`는 1.684~1.959(중앙값 대비 최대 +11%)다.
  - `reg_host_off`는 2.894~3.268(+7%)이다.
  - 그래서 감소율은 범위와 함께 적는다.

## 4. 주의·결정

- 컴포지터 창이 앱 창보다 약간 넓다(§1). 프레임당 0.01 ms 미만의 과대 계상이며, 감소율 판정에는 영향이 없다.
- 결정: 논문 §6.7·초록·결론의 헤드라인을 이 회차의 **응용 + 컴포지터** CPU로 바꾸고, 응용만의 값을 함께 적는다 (사용자 결정, 2026-10-16).

# 표시 통합 e2e — CPU 거버너 performance 고정·백그라운드 최소화 재측정 (2026-10-16)

[`../v3d1150_syscpu_20261016`](../v3d1150_syscpu_20261016/summary.md)와 같은 벤치·설정·집계로 다시 쟀다. 바꾼 조건은 세 가지다.
- CPU 거버너를 **performance로 고정**했다(2.4 GHz).
- 작업 관리자(`lxtask`)를 끄고, 측정 중에는 다른 작업을 하지 않았다.
- 반복을 **5회**로 늘렸다.

논문 7차 심사 m6이 이 재측정을 요구했다. 지적 내용은 이렇다.
- 배경 부하(0.59~0.82 ms/f)가 효과 크기와 같은 자릿수다.
- 거버너가 ondemand인데 주파수가 기록되지 않았다.

벤치는 커밋 `6165bcf`이고, `display_bench.sh`는 70열이다. 이 커밋부터 샘플러 JSON에 `cpufreq_avg_mhz`가 들어간다.

결정: 거버너 performance 고정·lxtask 종료 상태의 재측정 회차로 헤드라인을 교체한다 (사용자 결정, 2026-10-16).

## 1. 측정 조건

- 날짜: 2026-10-16 14:50~15:13 (KST)
- 하드웨어: Raspberry Pi Compute Module 5 Rev 1.0, Hailo-8, PCIe **Gen3 x1**, V3D 1150 MHz
  - 측정 직전 status-reporter 점검: 락 없음, NPU 비어 있음, HDMI-A-1, DRM master labwc
  - 표시: HDMI-A-1 1920×1080@60, labwc 0.20.2 / libwlroots 0.20.2+rpt4
- **CPU 거버너 performance**
  - 측정 동안만 바꿨다. 명령은 `sudo … echo performance > /sys/devices/system/cpu/cpufreq/policy0/scaling_governor`이고, 끝난 뒤 ondemand로 되돌렸다.
  - `env_bench.txt`에 `cpufreq policy0: governor performance cur_khz 2400000`이 남아 있다.
  - 20개 측정 창의 샘플러 `cpufreq_avg_mhz`는 모두 2400.0이다.
- 백그라운드: 측정 전에 `lxtask`를 종료했다. 대화형 에이전트 CLI(`claude`)는 대기 상태로 남았다(§2.1의 "무관한 프로세스").
- 코드: 커밋 `2f2d3d0`과 같은 바이너리(md5 `3dda5b0f…`, 측정 전후 같음)
- 명령: `RUNS=5 FRAMES=900 OUT_DIR=07_results/display_e2e/runs/v3d1150_quiet_perfgov_20261016 bash 06_tools/bench/display_bench.sh`
  - 4설정 + M5a, 반복 바깥 루프. 콘솔 전문(거버너 설정·원복 줄 포함): [`raw/_session/bench_stdout.log`](raw/_session/bench_stdout.log)
  - 실행마다 냉각 판정 뒤 idle 기준선 10 s
- 계수 방식: 앞 회차와 같다.
  - 커널 `TICK_CPU_ACCOUNTING`이고 `IRQ_TIME_ACCOUNTING`은 꺼져 있다.
  - 그래서 유휴 중 hardirq는 잡히지 않으며, 값은 **하한**이다.
- 신뢰성
  - 21개 `hailort.log`(20 실행 + 세션) 모두 warning 0, error 0
  - 검출 3369(20회), 표시 드롭 0
  - 냉각 9회, 칩 최고 77.8 °C(실행 stdout 기준)
- 집계: 실행별 값의 **5회 중앙값**이다.
  - 파이프라인 CPU는 `raw/<run>/syscpu{,_idle}.json`으로 계산한다. 앱 + labwc + (창의 커널 스레드 − idle 기준선 × 창 길이 비)를 900프레임으로 나눈다.
  - 같은 계산을 앞 회차에 적용하면 정본 값(3.189 / 1.111 / 2.505 / 2.567)이 그대로 나온다.

## 3. 결론

- **거버너를 고정하면 기준 경로의 CPU가 크게 줄고, 감소율도 줄어든다.**
  - 파이프라인 CPU는 2.444 → 2.044 ms/f로 **−16.4%**다. 같은 회차 짝은 −14~−24%다.
  - 앞 회차(ondemand)는 3.189 → 2.505 ms, −21.5%였다.
  - 기준 경로가 3.189에서 2.444로 가장 많이 줄었다. ondemand에서는 부하가 큰 기준 경로가 낮은 주파수 구간에서 더 많은 ms를 썼던 것으로 보인다(**해석**, 앞 회차에는 주파수 기록이 없다).
  - 방향("표시를 켜고도 기준보다 호스트 CPU가 낮다")은 5회 짝 모두 유지된다.
- **실행 간 흔들림이 크게 줄었다.**
  - 기준 경로 앱 CPU의 범위가 앞 회차 3.067~3.544에서 2.356~2.600으로 좁아졌다.
  - 최대속도 + 표시의 전처리 중앙값도 안정적이었다.
- 처리량·검출·드롭·GPU 예산·인터럽트는 앞 회차와 같은 자리다.
  - 표시 지연 중앙값의 회차 차이는 수직동기 양자화 범위 안이다.
- 민감도(미계수 인터럽트):
  - 표시로 늘어난 인터럽트는 프레임당 약 55회다.
  - 회당 5 µs가 모두 유휴 중에 쓰였다고 가정하면 미계수 몫은 0.275 ms다. 그 경우 감소율은 약 −5%로 줄고, 방향은 유지된다.
  - 감소가 사라지려면 회당 약 7.3 µs 이상이어야 한다. 회당 처리 시간은 재지 않았다.

## 4. 주의

- **performance 고정은 평소 운용 조건(ondemand)과 다르다.** 프레임당 ms는 2.4 GHz에서 잰 값이다.
- 대기 중인 에이전트 CLI의 CPU 몫(프레임당 약 0.5 ms)은 끄지 못했다. 이름 기준으로 파이프라인 합에서 뺐지만, 캐시·메모리 경합으로 주는 영향은 가르지 않았다.
- 앞 회차의 "세 회차 응용 CPU 비교"(ondemand)와 이 회차의 값은 거버너가 달라 직접 비교하지 않는다.
- GPU 구간·지연·e2e는 `raw/<run>/stdout.log`의 해당 줄을 실행별로 읽고 5회 중앙값을 낸 것이다. 앞 회차 summary에는 이 표가 없었다(7차 심사 지적). 이 회차부터 summary에 남긴다.

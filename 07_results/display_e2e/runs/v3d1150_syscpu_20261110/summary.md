# 표시 통합 e2e — 헤드라인 설정을 거버너 ondemand로, 현재 바이너리(dc447c5)에서 (2026-11-10)

논문은 거버너를 performance로 고정한 회차를 헤드라인으로 쓰고, 고정하지 않은(ondemand) 회차의 감소율을 함께 적어 "감소율의 크기는 측정 조건에 따라 달라진다"고 말합니다. 그 ondemand 값([`v3d1150_syscpu_20261016`](../v3d1150_syscpu_20261016/summary.md), −21%)은 이전 코드 `2f2d3d0`의 것이라, 현재 헤드라인([`v3d1150_quiet_perfgov_20261109`](../v3d1150_quiet_perfgov_20261109/summary.md), dc447c5, −25%)과 나란히 놓으면 코드가 달라 비교가 성립하지 않습니다(paper-reviewer 지적). 그래서 같은 설정을 현재 바이너리·ondemand로 다시 쟀습니다. 결정: 현재 코드로 ondemand 회차를 재측정한다 (사용자 결정, 2026-11-10).

**결론부터 적습니다.**
- 파이프라인 CPU는 기준 3.549 → 제안 2.478 ms/f, 감소율 **−30.2%**입니다(같은 회차 짝 −28.9~−31.7%).
- 같은 코드의 performance 회차(−25.0%)보다 감소율이 큽니다. 이전 코드에서도 ondemand −21%가 performance −16%보다 컸으므로, "거버너를 고정하지 않으면 감소율이 커진다"는 관찰은 현재 코드에서도 그대로입니다. 다만 이 회차의 창 평균 주파수는 기준 경로가 가장 높았으므로(약 1,594 MHz), 기준 경로의 CPU 증가는 주파수만으로 설명되지 않습니다. 원인은 가르지 않았습니다.

## 3. 결론

**1. 같은 코드에서 거버너를 고정하면 감소율이 작아집니다.** ondemand −30.2% 대 performance −25.0%입니다. 기준 경로가 3.549 → 2.460 ms/f로 가장 크게 줄기 때문입니다(제안 경로는 2.478 → 1.844). 이전 코드의 짝(−21% 대 −16%)과 방향이 같습니다.

**2. 현재 코드에서는 ondemand 회차의 기준 경로 CPU가 이전 코드보다 큽니다(3.189 → 3.549).** 기준 경로는 `c97c274`의 영향을 받지 않으므로, 거버너가 고른 주파수나 백그라운드 차이(`lxtask` 유무 등)로 봅니다. 이전 회차에는 주파수 기록이 없어 가르지 않았습니다. 거버너가 다른 회차의 CPU는 서로 비교하지 않고, 감소율만 같은 회차 안에서 씁니다.

## 4. 주의·남은 일

- 3회입니다(헤드라인 회차는 5회).
- 측정 중 다른 명령 1회(Jetson SSH, 원격 세션 종료)가 있었고, `disp_source` 두 실행의 무관 프로세스 몫이 컸습니다. 파이프라인 집계(앱 + 컴포지터 + 커널 스레드 − 유휴 기준선)에서는 빠지지만, 캐시·메모리 경합 영향은 가르지 않았습니다.

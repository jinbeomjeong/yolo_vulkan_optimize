## 1. 경계 규약 (계획서 부록 A.12 가 요구한 것)

A.12 는 P5 테스트 패턴이 기대 400×300 대신 **399×299** 를 그린 포함/배제 off-by-one 을 근거로,
오버레이는 GPU 와 CPU 가 경계 규약을 **정확히 같게** 정의해야 한다고 경고했다.
그래서 **규칙을 먼저 글로 쓰고**(`01_src/display/overlay_reference.hpp` 상단 R0~R8 블록)
GPU 셰이더와 CPU 기준 구현을 그 글에 맞춰 작성했다. 요약:

| # | 규칙 |
|---|---|
| R0 | 원본 좌표 → 캔버스 좌표는 push constant affine `(sx, sy, tx, ty)` 하나로만. 캔버스 1920×1080이면 **항등** |
| R1 | `i = int(floor(clamp(f, -32768, 32767) + 0.5))` (round half up). 사각형은 **닫힌 범위** `[ix1,ix2]×[iy1,iy2]`, 폭 = `ix2-ix1+1`. 뒤집힌 입력은 min/max 로 정규화 |
| R2 | 좌표에 NaN/Inf 가 있으면 **그 검출을 통째로 건너뛴다** |
| R3 | 테두리는 **안쪽으로만** 자란다: `(x-ix1<w)‖(ix2-x<w)‖(y-iy1<w)‖(iy2-y<w)`. 2w 보다 얇은 사각형은 꽉 찬다 |
| R4 | 면적 0(`x1==x2`)은 버리지 않는다 → 1 px 선/점이 그려진다 |
| R5 | 정수 사각형은 **클리핑하지 않은 좌표로** 계산하고 쓰기 직전에 화면으로 자른다 |
| R6 | 라벨 = `"<class_name> <score>"`, score 는 **정수 도메인**에서 `q=floor(clamp(s,0,1)*100+0.5)` → `"0.87"`. 원점은 박스 좌상단 **위** `iy1-16*s`, 공간이 없으면 박스 **안쪽 상단**. 가로 넘침은 화면 클리핑에 맡긴다. **라벨 배경 상자는 그리지 않는다** |
| R7 | 색 = `class_color(clamp(cid,0,79))` RGB, 알파 **항상 255**. HUD 는 흰색, 원점 (4,4) 고정 |
| R8 | CPU 는 검출 인덱스 오름차순. **GPU 는 검출당 워크그룹 하나라 순서가 없다** → 겹치는 박스의 교차 픽셀 색은 **순서 의존(허용 한계)** |

글리프 렌더링(행·비트 순서, 정수 배율, 진행폭 8·s, 줄 높이 16·s, 배경 미터치)은
`01_src/common/glyph_font_8x16.hpp` 의 규약 1)~8) 을 그대로 따랐다. **그 헤더는 고치지 않았고
고쳐야 할 이유도 없었다** — `static_assert` 6개가 규약을 이미 자기검증한다.

## 3. GPU 시간 — ③ 이 실패한 이유와 실제 의미

오프스크린 연속 스트림 300프레임, depth 3, `local_size_x = 128`, `line_width 2`, `text_scale 2`.
**NPU 유휴 + 다른 부하 없음에서 3회 반복**(부록 A.8 의 규율). `px` 는 CPU 기준 렌더가 실제로 바꾸는
픽셀 수이고 `ns/px` 는 median ÷ px 다. 원본: `verification/p07_overlay_timing_idle.txt`

| 크기 | 검출 | 라벨 | median (3회) | p90 | px | ns/px |
|---|---:|---|---:|---:|---:|---:|
| 1920×1080 | 80 | on | **1.024 / 1.022 / 1.021** | 1.04~1.06 | 180,754 | 5.66 |
| 1920×1080 | 80 | off | 0.466 / 0.468 / 0.466 | 0.49~0.53 | 92,480 | 5.04 |
| 1920×1080 | 40 | on | 0.553 / 0.554 / 0.555 | 0.56~0.63 | 91,772 | 6.04 |
| **1920×1080** | **5** | **on** | **0.151 / 0.151 / 0.151** | 0.153 | 16,856 | 8.95 |
| 1920×1080 | 0 | on (HUD만) | 0.043 / 0.043 / 0.044 | 0.044~0.051 | 1,608 | 26.8 |
| 640×640 | 80 | on | 0.931 / 0.931 / 0.931 | 0.94~0.98 | 87,977 | 10.6 |
| 640×640 | 40 | on | 0.506 / 0.505 / 0.506 | 0.51~0.52 | 44,653 | 11.3 |
| 640×640 | 5 | on | 0.138 / 0.138 / 0.140 | 0.14~0.15 | 10,676 | 13.0 |

(CPU 부하가 있을 때 — 빌드·ctest 동시 실행 — 같은 수치가 1.22~1.30 ms 까지 올라갔다.
GPU 가 놀면 DVFS 로 시간이 부푸는 것이 여기서도 보인다. **위 표는 유휴 상태 값이다.**)

**판정을 그대로 적는다: 검출 80개 + 라벨은 0.7 ms 안에 들어가지 않는다.** 근거와 맥락:

1. **이것은 구현 비효율이 아니라 픽셀 처리량 바닥에 가깝다.** 오버레이는 얇은 테두리와 글리프를
   흩뿌려 쓰므로 px 당 **5.0~5.7 ns** 가 든다. 같은 GPU 에서 `display_convert.comp` 가 1920×1080 을
   순차로 덮어쓸 때가 **2.05 ns/px**(4.23 ms / 2,073,600 px)다. 180,754 px 을 0.7 ms 안에 쓰려면
   **3.87 ns/px** 가 필요한데, 이 GPU 는 흩뿌린 쓰기에서 그 속도를 내지 않는다
   (테두리만 그리는 가장 단순한 경우도 5.04 ns/px 다).
2. **최적화는 이미 두 번 했다** (같은 조건, local_size 128):
   | 단계 | 1080p 검출 80개 + 라벨 |
   |---|---:|
   | 최초 (셀 단위 분배, 기본 local_size 64) | 2.41 ms |
   | 글리프를 **(문자, 글리프 행) 단위**로 분배 (문자·글리프 로드 8배 감소) | 1.53 ms |
   | 글리프 가로 경계 검사 제거 (범위 밖 `imageStore` 는 Vulkan 이 버린다) | **1.03 ms** |
   워크그룹 크기 스윕(같은 셰이더): 16 → 7.27 / 32 → 3.96 / 64 → 2.09 / **128 → 1.03** / 256 → 1.03 ms.
   → `OverlayConfig::local_size_x` 기본값을 **128** 로 정했다(계획서 §5.4 의 64 에서 변경, 근거는 실측).
3. **계획서 §5.4 자신의 추정과 비교하면 어긋나지 않는다.** §5.4 는 "검출 40개 최악에도 **0.7 ms**"라고
   썼고, 실측 40개는 **0.554 ms** 로 그 추정 안에 들어간다. P7 표의 "0.7 ms(검출 80개)"가
   §5.4 의 40개 추정과 서로 맞지 않는 수치였다.
4. **실제 동작점은 검출 5.21개/frame**(1816프레임 9457검출 실측)이고 그때 **0.151 ms** 다 —
   기준의 4.6배 여유다. 그리고 1080p 화면에 80개의 라벨을 동시에 그리면 텍스트가 화면을 덮어
   가시화로서 의미가 없다.
5. **예산에 위협이 없다.** 최악(80개 + 라벨)을 다 내도 변환 4.23 + 오버레이 1.03 = **5.3 ms** 로
   b4 NPU 주기 22.5 ms 의 23%, 실시간 33.3 ms 의 16% 다(4절 온스크린 실측이 이것을 확인한다).

## 4. 온스크린 통합 — 같은 커맨드 버퍼에 이어 기록

`--probe convert --display-fullscreen --with-overlay` 는 **`DisplayConvert` 가 만든 같은 커맨드 버퍼에**
오버레이를 이어 기록한다(계획서 §5.4, 2단계 보고의 권고). present 당 submit 은 여전히 1회다.

| 구성 | convert shader | overlay | 커맨드 버퍼 total | present 간격 | presented / dropped |
|---|---:|---:|---:|---:|---|
| 오버레이 없음 (기준선) | **4.229** ms | – | 4.243 | 16.658 ms | 300 / 0 |
| + 오버레이 검출 **5**개 | **4.234** ms | **0.199** ms | 4.460 | 16.66 ms | 300 / 0 |
| + 오버레이 검출 **80**개 | **4.223** ms | **1.029** ms | 5.278 | 16.659 ms | 300 / 0 |

- **변환 경로는 오버레이 추가로 느려지지 않았다**(4.229 → 4.223/4.234 ms, 2단계 기록 4.22~4.23 ms와 동일).
- 오프스크린 P8 재측정도 그대로다: 1920×1080 1:1 **4.240 ms**(2단계 4.229), 1600×900 7.649, 1280×720 5.278.
- 60.1 fps 로 300프레임 present, `display_dropped=0`, `NOT_READY 0`, `recreates=1`(초기 configure).
- **검증 레이어 errors 0 / warnings 0** — synchronization validation 포함.

### 두 디스패치 사이 배리어 — 필요하다

`display_convert.comp` 와 `overlay_boxes.comp` 는 **같은 이미지의 같은 픽셀에 쓴다(WAW)**.
같은 커맨드 버퍼의 연속한 두 디스패치는 배리어가 없으면 겹쳐 실행될 수 있으므로
`SHADER_STORAGE_WRITE → SHADER_STORAGE_WRITE` 의존성을 넣었다(레이아웃은 GENERAL 유지).
오버레이는 이미지를 **읽지 않으므로** dst 에 `READ` 는 넣지 않았다(알파 블렌딩 없음, R7 이 알파를 항상 255로 쓴다).
`record()` 가 `VkImage` 가 아니라 뷰만 받으므로 이미지 배리어 대신 **전역 `VkMemoryBarrier2`** 를 쓴다
(이미지 배리어의 상위집합이고 같은 큐의 compute→compute 에서 V3D 비용도 같다).
검출 버퍼는 `HOST_WRITE → SHADER_STORAGE_READ | INDIRECT_COMMAND_READ` 하나뿐이다
(staging 버퍼도 transfer 큐도 쓰지 않는다 — 2.7 KB 를 영구 매핑 버퍼에 직접 쓴다).

## 7. 남은 것 / 다음 단계에 넘기는 것

- **P7 ③ 은 검출 80개 + 라벨에서 미달**(1.03 ms). 3절의 근거로 **기준 자체를 §5.4 의 "검출 40개에서
  0.7 ms"로 읽는 것이 맞다**고 본다(40개 실측 0.554 ms). 최종 판단은 조정자에게 맡긴다.
  더 줄이려면 남은 레버는 ① 라벨을 상위 N개만 그리기 ② `text_scale 1`(단, 글리프 비용이 픽셀 수보다
  **작업 단위 수**에 더 묶여 있어 80개에서 이득이 거의 없었다: 1.09 ms) ③ 라벨 배경 없이 유지(이미 그렇다).
- **겹치는 박스의 교차 픽셀은 순서 의존**이다(R8). 필요하면 호스트에서 score 오름차순으로 정렬해
  "높은 점수가 위"를 보장할 수 있다 — 지금은 하지 않았다.
- **`grim` 화면 캡처는 이번에 얻지 못했다.** 측정 중 데스크톱 세션(Task Manager 창)이 떠 있어
  `grim -o HDMI-A-1` 이 우리 전체화면 창 대신 데스크톱을 찍었다. present 통계
  (`presented=300, dropped=0, present_wait 16.659 ms`)와 P5 단계의 픽셀 검증으로 대신한다.
  화면 도달 확인은 [7]/[8] 단계에서 다시 한다.
- **`main.cpp` 통합과 `wp_viewporter` 적용은 이번 범위가 아니다**([7]/[8]단계).
  `wp_viewporter` 를 쓰면 스왑체인 extent 가 항상 1920×1080 이므로 **오버레이 affine 도 항등으로 고정**된다.
- 오버레이 `local_size_x` 최적값 128 은 **1920×1080·640×640 두 크기에서만** 확인했다.
  `--overlay-local N` 으로 다시 잴 수 있다.

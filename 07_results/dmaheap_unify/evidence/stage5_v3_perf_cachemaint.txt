## 해석

세 경로가 **장치 쪽에서** 캐시 관리를 한다 — 우리가 sync ioctl 을 부르지 않아도 실행된다:

  (1) system_heap_map_dma_buf → dma_map_sgtable → __dma_map_sg_attrs → dcache_clean_inval_poc
      = dma-buf attach 시점의 clean+invalidate
  (2) system_heap_unmap_dma_buf → dma_unmap_sg_attrs → dma_direct_unmap_sg → dcache_inval_poc
      = detach 시점의 invalidate (hailo_desc_list_release_ioctl 아래)
  (3) hailo_vdma_buffer_map → __dma_sync_single_for_device → dcache_clean_poc
      = **Hailo 드라이버가 전송 전에 직접 clean 한다** (hailo_desc_list_program_ioctl 아래)

→ **Hailo DMA 방향에서는 CPU 쪽 DMA_BUF_IOCTL_SYNC 가 중복이다.** V3 의 세 변종이 전부
  재현에 실패한 이유가 이것으로 설명된다. 디바이스 트리에 dma-coherent 가 0건인 것과 모순되지 않는다 —
  비일관 장치이므로 **드라이버가 스트리밍 DMA API 로 캐시 관리를 하고 있는 것**이다.

## 그래도 sync 를 유지하는 이유 (3가지)

  a) 이것은 **HailoRT 4.24.0 + hailo_pci 드라이버 구현에 의존하는 관찰**이다. 스펙도 계약도 아니다.
     드라이버가 바뀌면 조용히 깨진다 — 그리고 그때 증상은 "간헐적 오검출"이라 추적이 거의 불가능하다.
  b) **V3D 방향은 이 증거가 덮지 못한다.** V3D 는 import 시점에 attach 를 한 번 하고 그 뒤
     프레임마다 다시 map 하지 않는다 → 위 (1)(3) 에 해당하는 프레임별 캐시 관리가 없다.
     그런데도 GPU 바이트 합이 항상 맞았다. 기제 미확정이다(축출이 이미 끝났을 가능성 / V3D 스누핑 가능성).
  c) 앞으로 heap 버퍼를 **장치가 아닌 다른 소비자**(녹화 스테이징, 트래킹)가 쓰면 (3) 이 사라진다.
     그때 sync 가 없으면 규약이 아니라 우연에 의존하게 된다.

## 남은 결정적 실험 (하지 않았다)

ftrace 로 `arch_sync_dma_for_cpu`/`for_device` 를 프레임 단위로 세어 **전송마다** 부르는지
**매핑 때 한 번만** 부르는지 가른다. 전자면 드라이버가 완전히 보장하는 것이고 후자면
우리가 본 것은 우연에 더 가깝다. tracepoint 는 root 가 필요해 이 세션에서 하지 않았다.

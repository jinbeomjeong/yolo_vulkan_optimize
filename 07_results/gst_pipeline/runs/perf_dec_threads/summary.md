# 인과 실험: 앱의 FFmpeg 프레임 스레드를 1개로 줄이면 CPU 차이가 사라지는가

상위 실험 [`gst_pipeline`](../../summary.md)의 회차다. 앞 회차 [`perf_breakdown`](../perf_breakdown/summary.md)의 해석을 검증한다.
앞 회차는 앱 대 GStreamer의 CPU 차이 +637k cycles/frame 가운데 약 70%가 HailoRT NMS 루프에서 나온다고 봤다. 그 원인은 FFmpeg 프레임 스레드가 늘린 메모리 지연으로 추정했다.

## 조건
- 측정 일시: 2026-09-29 09:42~10:25 KST
- 환경: 부트로더 2026-09-25(V3D 1150 MHz), PCIe Gen3, gst-plugins-bad rpt4, git `1b9be7f`. 자세한 값은 [`env_bench.txt`](env_bench.txt)에 있다.
- 설정 3개(모두 b8/s16, 전체 1816프레임, 상위 실험과 같은 인자)
  - `app_t0`: 기본값, FFmpeg `thread_count=0`(자동, `av:hevc:df0~4` 5개)
  - `app_t1`: `YVO_DEC_THREADS=1`(프레임 스레딩 끔). 1b9be7f에서 `main.cpp:629`에 붙인 연구용 환경변수다.
  - `gst`: `yvo_gst_pipeline --sink hailo`
- 방법은 앞 회차와 같다.
  - 설정마다 3회를 인터리브한다. 실행마다 `perf stat`과 `perf record -e cycles -F 2999`를 `-D -1 --control fifo` + `perf_window`로 도구의 CPU 구간과 같은 구간에서 뜬다.
  - 실행 전마다 칩을 65 °C 이하로 식힌다. 18회 모두 exit 0, `hailort.log` warning 0이다.
- **판정 기준(측정 전에 정함)**
  - 확정: `app_t1`의 NMS 루프(`0x30ffac`) cycles가 gst의 ±5% 안이고, 앱 대 gst의 총 cycles 차이가 `app_t0` 대비 70% 이상 줄어든다.
  - 부분 확정: NMS만 내려간다.
  - 기각: NMS가 그대로다.

## 결론
1. **FFmpeg 프레임 스레드가 CPU 차이의 원인이다(확정).**
   - 앱의 스레드를 1개로 줄이면 cycles/frame이 gst보다 오히려 조금 낮아지고(5.63 M 대 5.78 M), CPU 차이가 74% 줄어든다.
   - FPS(51.66)와 검출(9457)은 그대로다.
   - 사전 기준으로도 두 조건(NMS가 gst의 ±5% 안: −1.3%, 총 cycles 차이 70% 이상 감소)을 모두 만족한다.
2. **다만 앞 회차가 제시한 메커니즘("NMS 루프의 메모리 지연이 늘어난다")은 이 회차에서 재현되지 않았다.**
   - 이 회차에서는 기본 앱(t0)의 NMS 루프도 gst와 같다(중앙값 2732 대 2732).
   - 따라서 앞 회차의 NMS 차이(+456k)는 FFmpeg 스레드 때문이 아니라 실행 사이의 변동이다. 두 회차 사이에는 바이너리 재빌드와 시간 경과가 있었다.
   - 그 변동의 원인(예: 출력 버퍼의 메모리 배치)은 가르지 못했다(**미확인**).
3. **FFmpeg 프레임 스레딩 자체의 비용**은 t0 − t1 기준 약 490k cycles/frame(≈0.26 ms)이다. 구성은 다음과 같다.
   - `av:hevc:df*` 스레드의 일(565k). 스레드를 끄면 그 일의 일부(+64k)는 메인 스레드로 옮겨 간다.
   - `memset`(+56k), 커널 스케줄링(+109k), libhailort(+127k, 경합으로 추정)
   - 1080p 한 프레임에 HW 디코드를 쓰는 경우, 프레임 스레드는 이득 없이 부담만 준다. 디코드 처리량 상한(1스레드 266 FPS)이 NPU 상한(51.7 FPS)보다 훨씬 높아서다.
4. GStreamer 경로가 CPU가 낮았던 이유는 디코드 코드가 가벼워서가 아니다. **FFmpeg 같은 프레임 스레드가 없기 때문**이다. 디코드 쪽 호스트 비용 자체는 GStreamer가 더 크다(≈290k 대 136~206k).

## 주의
- 앞 회차와 이 회차의 NMS 루프 값이 다르다. 같은 설정(기본 앱)이 3100대에서 2700대로 바뀌었다. **perf 수치의 회차 간 변동이 최대 약 15%**라는 뜻이라, 한 회차만으로 메커니즘을 결론 내리면 안 된다. 앞 회차 summary의 결론 3·5(NMS 메모리 지연)는 이 회차로 대체된다(결과 파일은 고치지 않았다).
- perf를 켠 상태의 값이다. 비교는 같은 회차 안에서만 한다.
- 앱의 기본값(`thread_count=0`)은 바꾸지 않았다. 바꿀지는 따로 정한다. 표시 경로나 다른 모드에서 1스레드의 영향은 재지 않았다.

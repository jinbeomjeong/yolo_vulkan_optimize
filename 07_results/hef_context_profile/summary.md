# HEF 컨텍스트별 NPU 시간 분해 — `yolov11m.hef` (목적 ③ 1단계)

`T(B) = 24.8 + 16.2·B ms`의 고정비와 프레임당 몫이 **컨텍스트 4개 중 어디에서 생기는지**를 펌웨어 액션 타임스탬프로 나눴다.
최소 지연 운용점 O2(b1)의 NPU 시간 가운데 고정비가 얼마인지, 컨텍스트가 더 적은 HEF가 줄일 수 있는 상한도 함께 구했다.
**모델·HEF는 바꾸지 않았다.** 액션 이름에는 공식 문서가 없으므로, 이름으로 한 해석은 모두 **추정**이다.

## 3. 결론

1. **T(B)가 재현된다.** 펌웨어 타임스탬프로 잰 배치 구간은 9회 적합 `24.79 + 16.23·B`(rms 0.27 ms)다.
   파이프라인 모델 `24.8 + 16.2·B`와 0.03 ms/B 안에서, 10-08 비정식 프로브 `24.68 + 16.23·B`와 0.11 ms 안에서 같다.
   B마다 3회 범위가 대부분 0.01 ms 안이라, 컨텍스트 시간은 펌웨어 수준에서 결정적이다.
2. **고정비가 가장 큰 컨텍스트는 `dynamic_3`이다(a 10.03 ms, 고정비의 40%).** 다음은 `dynamic_1`(7.40 ms, 30%)이다.
   dynamic_3은 마지막 경계 출력을 마친 뒤에도 `module_config_done_interrupt`를 기다린다. b1에서 7 ms가 넘고, config형 몫은 9.03 − 0.80·B다.
   각 컨텍스트 끝의 `enable_lcu_default` 개수가 9회 모두 **다음** 컨텍스트의 LCU 수와 같다(91 → 105 → 38 → 72 → dyn0).
   이것을 보면 **컨텍스트 i가 계산하는 동안 i+1의 config를 미리 적재하고, dynamic_3은 다음 배치 dynamic_0의 config(8.15 MB)를 적재하는 것**으로 보인다(**추정**).
   preliminary가 활성화 때 한 번 받는 8.28 MB가 이 8.15 MB와 거의 같다는 점도 이 해석과 맞는다. B가 커지면 이 적재가 계산 뒤에 숨어 −0.80·B로 줄어든다.
3. **바이트와 시간이 컨텍스트 단위에서도 맞는다**(후보 조사와 정합). 고정 a는 그 컨텍스트가 받는 config 바이트에 대응하고(합계 20.52 MB / 24.78 ms = **0.83 GB/s**),
   프레임당 b는 컨텍스트 사이 텐서와 경계 데이터 중 더 큰 방향의 바이트에 대응한다(12.84 MB / 16.23 ms = **0.79 GB/s**).
   후보 조사가 배치 전체로 보인 "고정비 ↔ config 20.5 MB 재적재, 프레임당 ↔ 컨텍스트 텐서 PCIe 왕복"이 **컨텍스트마다** 성립한다.
   컨텍스트별 실효 대역폭은 0.65~1.00 GB/s로 흩어진다. 계산과 겹치는 정도가 컨텍스트마다 다르기 때문으로 보인다(추정).
   그래서 바이트로 시간을 예측할 수 있는 단위는 컨텍스트가 아니라 합계다.
4. **O2(b1)의 NPU 시간 중 고정비는 약 45~48%다.** 칩 쪽 프레임 지연(dyn0 시작 → 마지막 출력)은 **32.57 ms**로, 냉각 상태 `hailortcli` HW 지연 32.513 ms와 같다.
   이 중 **고정 15.71 ms(48%) + 프레임당 16.86 ms**다. 파이프라인이 잰 O2의 NPU 34.6 ms에 대면 고정비는 **45%**다.
   차이 약 2 ms는 호스트 쪽 제출과 콜백 비용으로 보인다(추정).
   여기에 더해 마지막 출력 뒤의 **꼬리 8.35 ms**(다음 배치 config 적재로 추정)는 그 프레임의 지연에는 들어가지 않지만 **주기**에는 들어간다.
   b1 주기 41.1 ms 가운데 고정비는 24.8 ms(60%)다. **O2가 30 fps(33.3 ms)를 못 따라가 입력의 18.6%를 버리는 이유가 이 고정비다.**
   frame_log의 제출 → NPU 완료 37.59 ms는 GPU 전처리 약 1.8 + 32.57 + 꼬리 중 호스트 후처리와 다음 제출 사이에 숨지 못한 약 3.2 ms로 분해된다. 수치는 맞지만 해석은 추정이다.
5. **컨텍스트 수가 적은 HEF가 줄일 수 있는 상한**(2단계는 모델 교체라 사용자 결정 사항이고, 여기서는 상한만 적는다):
   - **컨텍스트 전환 자체의 비용은 0에 가깝다**(전환 간격 3회 합 0.01 ms). 컨텍스트 수를 줄여서 얻는 것은 전환이 아니라 **바이트**다.
     배치마다 다시 받는 config는 1 MB당 약 1.21 ms, 프레임마다 오가는 컨텍스트 사이 텐서는 더 큰 방향 1 MB당 약 1.26 ms다.
   - 극단 상한은 가중치가 모두 칩에 상주하는 단일 컨텍스트다. 이 모델은 가중치가 칩에 다 안 들어가 4개로 나뉜 것이므로 현재 모델로는 불가능하다. 이 경우 고정비 24.8 ms가 모두 사라진다.
     b1 주기는 41.1 → 약 16.4 ms(≤ 61 FPS)로, 칩 지연은 32.6 → 약 16.9 ms(**−15.7 ms, −48%**)로 줄어든다.
     O2는 30 fps를 따라가게 돼 버림 18.6% → 0, 입력 큐 대기도 준다. 컨텍스트 사이 텐서 왕복(13.8 MB/프레임)도 없어지므로 프레임당 16.2 ms 역시 줄어든다. 이 몫의 크기는 새 HEF 없이는 정할 수 없다.
   - 현실적인 중간안(예: 3개)의 이득은 "배치당 다시 받는 config 바이트 × 1.21 ms/MB + 프레임당 없어지는 왕복 바이트 × 1.26 ms/MB"로 어림한다. 단 컨텍스트가 줄어도 칩에 상주하지 못하는 가중치는 여전히 배치마다 다시 받는다.

## 4. 주의·남은 일

- **액션 이름의 해석(LCU = 계산 대기, config 선적재, 꼬리 = 다음 배치 dyn0 config)은 모두 추정이다.** 공식 문서가 없다. 근거는 액션 순서, 개수 대응, 바이트 대응이다.
- **JSON의 `fps`는 인용하지 않는다.** b8 3회 가운데 2회가 47.9로, stdout의 마지막 줄(50.61~50.64)과 다르다. stdout 진행 표시의 앞 구간 값(47.94·47.97)과 같아, 마지막 값이 아니라 중간 표본이 기록된 것으로 보인다.
  그래서 `fw_actions_breakdown.py`가 JSON fps로 계산한 `fps_period` 적합(23.21 + 17.57·B, rms 2.53)은 왜곡돼 있다. 주기는 §2.3의 stdout 기준(24.39 + 16.71·B)을 쓴다.
- 주기에서 배치 구간을 뺀 나머지(b8에서 3.44 ms)는 배치 사이 시간인데 액션 목록에 없다(`batch_switching`은 타임스탬프가 0). 원인은 확인하지 않았다.
- `hailortcli`에는 영상 디코드·GPU 전·후처리가 없다. 파이프라인의 NPU 시간과 비교할 때 호스트 쪽 차이(약 2 ms)는 추정이다.
- B = 4와 PCIe Gen2는 재지 않았다. 3 s 짧은 실행이라 칩이 데워진 연속 운용(`thermal_soak`, 클럭 강하)과는 조건이 다르다.
- 드라이버가 `hailortcli --version`을 스크립트 CWD(`evidence/`)에서 실행해 0바이트 `hailort.log`가 생겼다. 정보가 없어 지웠다. 실행 로그는 모두 `raw/<설정>_run<N>/`에 있다.

## 5. 결정

- 결정: 이 실험에서 모델·HEF는 바꾸지 않는다 — 승인된 계획 ②의 범위 (사용자 결정, 2026-10-12).
- 2단계(컨텍스트가 더 적은 HEF나 다른 모델로 교체)를 할지는 **미결**이다. 모델 교체는 사용자가 결정한다(`CLAUDE.md` §사용자 확인). 판단 근거는 §3의 5다.

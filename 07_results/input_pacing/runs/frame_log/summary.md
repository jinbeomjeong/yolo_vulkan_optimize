# 프레임별 타이밍 로그 — batch 2 짝 완료, 페이싱 지연 꼬리, O2 지연 구성

`input_pacing` 실험의 회차다. 평균·백분위만 남던 지연을 `yvo_pipeline --frame-log`(커밋 `292a277`)로 **프레임마다** 남겨,
본 폴더 summary 의 "주의·남은 일"에 남긴 질문 셋을 답한다.
(1) batch 2 결과가 정말 약 66.7 ms 마다 두 장씩 나오는가, (2) 페이싱 b2 의 `e2e_arr` max 136~142 ms 꼬리는 무엇인가,
(3) 최소 지연 운용점 O2(b1/s1 + 페이싱 큐 1)의 58 ms 는 어떻게 구성되는가.

## 2. 결과 (3회 합산, 2700 도착 프레임)

### 2.1 batch 2 의 완료 박자 — 페이싱이면 "둘씩"이 아니다

| 설정 | NPU 실행 수 | 2장 묶음 | **1장 단독** | 완료 간격 < 5 ms | 25~45 ms | 45~60 ms |
|---|---:|---:|---:|---:|---:|---:|
| asap b2/s4 | 1353 | 1347 | 6 | 49.9% | 0% | 49.8% |
| **페이싱 b2/s4** | 1868 | 832 | **1036** | 28.0% | 38.1% | 29.6% |

- **asap** 은 거의 항상 2장 묶음이고 결과가 "약 2 ms 간격 2장 → 약 54 ms 쉼"으로 나온다(짝 완료가 깔끔한 이봉).
- **페이싱** 에서는 NPU 실행의 **55%(1036/1868)가 1장 단독**이다. 두 번째 프레임이 33.3 ms 뒤에야 도착하므로
  HailoRT 가 짝을 기다리지 않고 한 장으로 출발하는 경우가 절반을 넘는다. 그래서 완료 간격이 짝(<5 ms)·약 40 ms·약 57 ms 세 무리로 나뉜다.
  ("batch 2 는 늘 66.7 ms 마다 두 장씩"이라는 이전 추정은 asap 에서만 맞다.)
- 묶음 안 위치별 도착 기준 지연(중앙값): 짝의 **첫째 99.6 ms**, 둘째 70.7 ms, 단독 75.7 ms. 짝 대기(제출 간격) 중앙값 32.3 ms 는 도착 간격 33.3 ms 와 같다.

### 2.2 페이싱 b2 의 `e2e_arr` 꼬리 — 실행 끝 drain 현상이다

| 설정 | 평균 | 중앙값 | p90 | p99 | max | max 프레임 |
|---|---:|---:|---:|---:|---:|---|
| 페이싱 b2/s4 | 81.47 | 75.72 | 104.20 | 105.20 | 152.45 | src 897(끝 3프레임 안) |

- 합산 상위 8개 중 6개가 **마지막 두 프레임**(src 897·898, 세 회차 모두)이고, 그 프레임들은 `gpu_post`(관찰 기준)가 41~81 ms 다(평상시 중앙값 1.4 ms).
  같은 현상이 asap 의 마지막 프레임(src 897, `gpu_post` 42.8 ms)에도 있다 → **실행 종료 때 남은 프레임을 drain 하는 경로의 관찰 지연**이지 정상 상태의 꼬리가 아니다.
- 마지막 프레임을 빼면 최댓값은 약 107 ms 이고, 그것은 짝의 첫째 프레임이 33 ms 를 기다린 경우다(p99 105.2 ms 와 같다).
- 본 폴더 summary 가 남긴 "b2 페이싱 max 136~142 ms 꼬리 원인 미분리"의 답이다.

### 2.3 O2(b1/s1 + 페이싱 큐 1)의 58 ms 구성

| 구간(평균, ms) | 값 | 뜻 |
|---|---:|---|
| 도착 → 디코드 끝 | 2.64 | 도착 처리 늦음 + 디코드 |
| 디코드 끝 → 제출 | **14.54**(p90 26.9) | 입력 큐에서 NPU 가 비기를 기다림 |
| 제출 → NPU 완료 | **37.59** | GPU 전처리 + NPU(배치 1) |
| NPU 완료 → 후처리 완료(관찰) | 3.36 | GPU 후처리 약 0.5 ms + 메인 스레드 관찰 지연 |
| **합 = `e2e_arr`** | **58.14**(p90 72.53, max 75.37) | 버림 501/2700 = 18.6%, 연속 버림 최대 1 |

- 완료 간격은 39.5~42.3 ms(q10~q90)로 고르다 — NPU 주기 약 41 ms 그대로. 꼬리가 없다(max 75.4 ms).
- 큐 대기 14.5 ms 는 도착 시각과 NPU 주기(41 ms)의 위상 차이에서 온다(0~33 ms 사이에 고르게 퍼짐).

## 3. 결론

1. **페이싱된 batch 2 는 반 이상을 1장으로 실행한다.** 그래서 결과 박자가 "2장씩 66.7 ms"가 아니라 불규칙하고, 짝의 첫 프레임만 약 100 ms 로 길다.
   asap 의 깔끔한 2장 묶음은 파일을 앞서 읽어 늘 두 장이 대기하기 때문이다.
2. **페이싱 b2 의 136~152 ms 최댓값은 실행 끝의 drain 현상**이다. 정상 상태의 최댓값은 약 107 ms(짝 첫째의 33 ms 대기)다.
3. **O2 의 58 ms 는 NPU 37.6 + 입력 큐 대기 14.5 + 후처리 관찰 3.4 + 도착 처리 2.6** 이다. 줄일 수 있는 몫은
   후처리 관찰 지연(실제 GPU 후처리 약 0.5 ms 대비 약 3 ms — 메인 스레드 폴링)과 NPU 자체(HEF, 별도 실험 `hef_context_profile`).
   입력 큐 대기는 도착과 NPU 주기의 위상 차이라 큐 정책으로는 줄지 않는다.

## 4. 주의·남은 일

- `gpu_post_done` 은 관찰 시각이라 실제 GPU 완료보다 늦다. 3.4 ms 중 실제 GPU 시간과 관찰 지연의 몫은 이 로그로 가를 수 없다(GPU timestamp 와 대조 필요).
- 단독 실행 비율(55%)을 HailoRT 스케줄러의 어떤 규칙(시간 제한·임계값)이 정하는지는 확인하지 않았다.
- 표시 on 은 재지 않았다(present 시각 열 없음 — 표시 결합은 다음 단계).
- 이 회차로 본 폴더의 열린 질문 "페이싱 b2 꼬리"는 닫힌다. 색인(`07_results/README.md`) 열린 항목 표의 해당 행은 규칙상 그대로 두고 색인 행에 이 회차를 적는다.

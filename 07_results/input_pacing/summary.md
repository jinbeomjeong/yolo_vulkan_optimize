# 입력 페이싱 + leaky 입력 큐 — 큐 크기 N = 1·2·3

디코드 뒤 버퍼를 GStreamer `queue leaky=downstream max-size-buffers=N` 처럼(넘치면 가장 오래된 프레임을 버림, FIFO) 바꾸고,
프레임이 소스 시각(30 fps → 33.3 ms 간격)에 "도착"하게 하는 입력 페이싱(`--input-pace source`)과 함께 쟀다.
질문은 둘이다: **(1) 페이싱하면 지연이 얼마나 줄어드나, (2) 지터 대비로 N 을 2~3 으로 키울 가치가 있나**(사용자 요청, 2026-10-12).

## 3. 결론

1. **입력 페이싱만으로 지연이 크게 줄어든다.** 30 fps 를 따라가는 설정(b2/s3·b2/s4)에서 도착 기준 e2e 가 **평균 81.5 ms, p90 104 ms** 다.
   asap 의 디코드 기준 e2e(128.0 / 139.6 ms)보다 짧다 — asap 은 파일을 앞서 읽어 슬롯 큐가 늘 차 있었고, 페이싱하면 큐가 비어 있다(큐 대기 평균 0.02~0.25 ms).
   중앙값 75.6 ms 와 평균 81.5 ms 의 차이는 batch 2 의 첫 프레임이 짝(다음 프레임, 33.3 ms 뒤)을 기다리는 몫이다.
2. **b2/s3 와 b2/s4 는 페이싱에서 구별되지 않는다**(81.6 대 81.3 ms, 버림 둘 다 0). asap 에서 s3 가 12 ms 짧던 차이는 큐 깊이 차이였고, 페이싱하면 큐가 비어 사라진다.
   → 페이싱 입력이면 slots 를 3 으로 줄일 이유가 없다. b2/s4 가 처리량 여유(35 FPS)를 유지하며 같은 지연을 낸다.
3. **큐 크기 N 은 30 fps 를 따라가는 설정에서 아무 효과가 없다.** b2 두 설정 모두 큐 최대 깊이가 N 과 무관하게 **1** 이고 버림이 0 이다.
   하류의 빈 슬롯이 지터를 이미 흡수하므로 입력 큐에 두 번째 프레임이 쌓일 일이 없었다. **"N=1 은 지터에 약하다"는 우려는 이 측정에서 나타나지 않았다.**
4. **처리가 소스보다 느린 b1/s1 에서는 N 이 지연만 늘린다.** N 이 1 → 2 → 3 일 때 도착 기준 e2e 가 58.3 → 91.4 → 124.6 ms 로
   **한 단계마다 정확히 +33 ms**(한 프레임 간격) 늘고, 버림률은 18.6 → 18.3% 로 거의 그대로다(처리량 24.41 FPS 가 정한다: 1 − 24.41/30 = 18.6%).
   연속 버림은 최대 1프레임 — 버림이 고르게 퍼진다.
5. 따라서 **기본값 N=1 이 맞다**(구현 기본값, 사용자 결정 2026-10-12). 최저 지연이 필요하면 b1/s1 + 페이싱 N=1(평균 58.3 ms, 프레임 약 19% 버림),
   30 fps 를 다 처리하려면 b2/s4 + 페이싱(평균 81.3 ms, 버림 0)이다.

## 4. 주의·남은 일

- **디코드 늦음 max 약 10.7 ms**(p90 4.2 ms): 메인 스레드가 GPU 대기·후처리 중일 때 도착한 프레임을 늦게 디코드한 것이다. 늦음은 `e2e_arr` 에 그대로 들어가 있다.
  p90 이 10 ms 아래라 디코더 전용 스레드는 필요하지 않다고 판단한다(계획의 기준).
- b2 설정의 `e2e_arr` **max 136~142 ms**(p90 104 ms 와 차이 큼)는 원인을 가르지 않았다 — 시작 직후 프레임인지, 드문 꼬리인지 프레임별 분포를 보지 않았다.
- 페이싱은 **파일 입력을 카메라처럼 흉내** 낸 것이다. 실제 카메라(CSI)는 촬영 타임스탬프·ISP 지연이 더해지고, 지금 디코더는 HEVC 파일만 받는다(열린 항목 "카메라 입력").
- 표시 on 은 v1 범위 밖이다(`--display on` + `--input-pace source` 는 종료 코드 2). 표시까지 넣으면 glass-to-glass 가 이 값보다 표시 경로만큼 길어진다.
- 열 조건: 냉각 게이트 사이 30 s 실행이라 칩이 데워진 연속 운용(thermal_soak)과는 다르다. b1 은 처리량이 NPU 클럭에 비례하므로 데워지면 버림률이 늘 수 있다.
- 결정: 기본 `--input-pace` 는 asap 으로 둔다(기존 측정·벤치와 호환), 페이싱 기본 큐 N=1 유지. 둘 다 이 측정으로 바꿀 이유가 없다 (사용자 결정 N=1, 2026-10-12. asap 유지는 계획 승인, 2026-10-12).

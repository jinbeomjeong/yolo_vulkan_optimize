# 1부 — 전처리 단계 측정 + 화질 비교

계획 3·4단계. **전처리 단계만** 잰 결과다(NPU 미사용). 전체 파이프라인은 2부에 있다.

## 측정 조건

- 날짜: 2026-09-20 14:07~14:13 (KST)
- 하드웨어: Raspberry Pi Compute Module 5 Rev 1.0 (BCM2712_D0, hw_revision `0x2252701`), 커널 6.18.50+rpt-rpi-2712
- PCIe: **8.0 GT/s x1 = Gen3** (이 단계는 NPU를 쓰지 않지만, 기준선 51.7 FPS와 같은 보드 상태임을 남긴다)
- libpisp 1.7.0, ARM 2.4 GHz, 시작 SoC 68.6 °C / Hailo 54.1 °C, `throttled=0x80000`(과거 기록 비트, 현재 스로틀링 아님)
- 입력 영상: `04_data/videos/video_h265.mp4` (1080p30 HEVC, 1816프레임 전체)
- 반복 3회(반복이 바깥 루프), 설정당 **중앙값** + min/max. 워밍업 앞 60프레임 제외 → **n = 1756**
- 냉각: SoC 72 °C 초과 시 66 °C까지 대기(최대 120 s). 실제 대기 25~80 s, `results_raw.csv`의 `cool_wait_s`에 기록
- NPU를 쓰지 않으므로 `hailort_warnings`/`hailort_errors`는 전 행 **0**이다(신뢰 불가 행 없음)
- 스크립트: `06_tools/bench/isp_bench.sh`

### 시간 축이 두 개다 — 섞어 읽으면 안 된다

| 축 | 무엇 | 누가 |
|---|---|---|
| `wall` | 호스트 wall-clock. `BackendDevice::Run()` 직전/직후(ISP는 동기) | ISP |
| `device` | Vulkan timestamp query가 준 GPU 디바이스 시간. 호스트 제출·대기가 빠져 있다 | GPU |

그래서 GPU는 두 설정으로 쟀다. `gpu_nhcw_d1`(depth 1 = 동기)의 `submit + wait` 중앙값이
ISP의 wall-clock과 같은 축의 값이다.

이건 libpisp의 1024 스케일 고정소수점 반올림에서 오는 계통 편차다. `max|err| ~ 80`은 선명한 에지에만
나타나며(0.1~0.2 %), 리샘플 커널이 bilinear(셰이더) vs michel-netravali(ISP)로 다르기 때문이다.

## 결론

1. **ISP는 같은 축(wall-clock)에서 GPU보다 빠르다: 1.594 ms vs 2.081 ms (-23 %).** V3D는 완전히 비게 된다.
2. **A안(NHWC 그대로)의 CPU 비용은 GPU 경로와 똑같다: 0.436 ms/frame로 동일.**
   즉 ISP로 바꾸는 것만으로는 CPU가 전혀 나빠지지 않는다.
3. **계획의 핵심 미지수 — "ISP 출력을 CPU가 읽는 비용" — 은 싸다.**
   1.2 MB memcpy가 캐시 매핑 dma-heap에서 **0.229 ms**, V3D 메모리에서 **1.045 ms**로 **4.6배** 차이다.
   과거 NHWC 경로의 CPU 14 ms가 전치 연산이 아니라 V3D 메모리 읽기 비용이었다는 가설이 수치로 확인됐다.
   전치까지 직접 하면(C안) +0.57 ms/frame(0.436 -> 1.01)이고, 그중 0.35 ms가 전치, 0.06 ms가 dma-buf sync다.
4. **NEON 전치는 의미 없다.** 컴파일러가 이미 `ld3`로 자동 벡터화했고 루프 안에서는 메모리 대역폭이 상한이다.
   C안을 쓴다면 스칼라 구현으로 충분하다.
5. **화질은 통합에 지장 없는 수준이다.** MAE <= 1.08 LSB, 패딩 완전 일치. 다만 에지에서 max|err| 80이
   나오므로 **검출 결과 비교(계획 3단계의 진짜 판정 기준)는 아직 하지 않았다.**
6. 처리량은 ISP 경로가 270~292 FPS로 GPU 389 FPS보다 낮지만, **NPU 상한 51.7 FPS의 5배 이상**이라
   병목이 되지 않는다. 차이는 ISP `Run()`이 동기라 파이프라이닝이 없기 때문이다.

**조기 중단 게이트 판정:** `t_isp_ms` median 1.594 ms <= 6 ms, CPU 0.436 ms/frame(= GPU 재측정값과 동일).
**둘 다 통과 -> 전체 파이프라인 측정으로 진행할 근거가 있다.**

## 주의 · 남은 일

- 표 2의 전치 비용(0.35 ms)은 HailoRT 내부 CPU 입력 변환의 **대리 측정**이었다.
  **2부에서 실측했다: HailoRT 내부 전치는 +1.50 ms/frame, 우리 전치는 +0.89 ms/frame.**
- 검출 비교도 **2부에서 했다**(표 5). 화질 통계는 통과했지만 검출 게이트는 통과하지 못했다.
- GPU 쪽 `cpu_ms_per_frame`을 같은 세션에서 다시 쟀다: **0.436**(과거 기록 0.371과 다르다).
  슬롯·depth·측정 구간이 달라서이며, 이 문서의 비교는 전부 같은 세션 값끼리만 했다.
- `decode_only` run3의 CPU가 0.482로 튀었다(다른 두 회 0.243/0.275). 중앙값 0.275를 쓴다.
- **동시 작업 주의.** 측정 창(14:07:43~14:13:19) 안에 같은 저장소의 `01_src/display/`·`02_shaders/overlay_boxes.comp`를
  다른 세션이 고치고 있었다(파일 mtime 14:12:13, 14:12:23). run 3의 `decode_only` CPU(0.482)와
  `gpu_nhcw_d1` fps(371.6)가 튄 것이 이것과 관련 있을 수 있다. 다만 핵심 수치는 3회 모두 안정적이다:
  ISP `Run()` median 1.598 / 1.594 / 1.566 ms, GPU submit+wait 2.083 / 2.082 / 1.946 ms.
  결론을 뒤집을 만한 오염은 보이지 않지만, 재인용 전에 단독 상태에서 한 번 더 재는 것을 권한다.
- ISP 경로는 입력 노드에 쓰이지 않는 V4L2 버퍼를 `buffer_count`만큼 잡는다(12 x 2.0 MB = 약 25 MB).
  libpisp API에 끄는 수단이 없다.
- 리샘플 필터 비교는 **2부에서 했다**(4종 전부, 기본값이 최선).
- 5단계(B안 하이브리드 셰이더 `rgb_to_nhcw.comp`)는 착수하지 않았다.

## 측정 조건

- 날짜: 2026-09-20 14:52~15:33 (KST). 두 번 돌렸다(1차 14:52~15:09, 2차 15:17~15:33) → **설정당 6회**
- 하드웨어·커널·영상은 1부와 같다. PCIe **8.0 GT/s x1 = Gen3**, HEF `03_models/yolov11m.hef`

- 반복이 바깥 루프. 냉각: 칩 75 °C 초과 또는 직전 실행에 hailort 경고가 있으면 65 °C까지 대기(최대 120 s).
  실제 대기 40~120 s. `results_raw.csv`의 `cool_wait_s`에 기록
- **`hailort.log` 온도·스로틀 경고: 전 18행 0건, 에러 0건 → 신뢰 불가 행 없음**

- 스크립트: `06_tools/bench/isp_pipeline_bench.sh`

### 계획의 핵심 미지수 — HailoRT 내부 전치 비용

| 항목 | CPU ms/frame |
|---|---|
| 현행 기준선(GPU, NHCW — HailoRT 변환 없음) | 3.218 |

**예상이 맞았다. A안의 HailoRT 내부 전치는 14 ms가 아니라 1.50 ms다.**

같은 전치가 1.50 ms로 끝난다(**약 9배 감소**).

C안이 A안보다 0.61 ms 싸다. 우리 전치(0.89 ms)가 HailoRT 것(1.50 ms)보다 빠르다.

### 왜 떨어지는가 — 원인은 점수 임계 부근의 약한 검출이다

매칭 실패 1388건을 뜯어보면:

- 미매칭 참조 검출 **1388건의 중앙 점수 0.229**, 90 %가 0.3 미만
- 그중 **1337건(96 %)은 상대 쪽에 대응 박스가 아예 없다**(best IoU = 0). 즉 박스가 어긋난 게 아니라
  **검출이 NMS 점수 임계(0.2)를 넘느냐 마느냐가 갈린 것**이다
- 반대쪽(ISP에만 있는) 여분 검출 1168건도 중앙 점수 0.229로 대칭이다

임계 비대칭 인위성을 제거하고 **"강한 검출이 상대 쪽에서 재현되는가"**만 보면
(`detections/strong_match_diagnostic.txt`):

| 참조 점수 하한 | IoU 0.5: GPU→ISP | IoU 0.5: ISP→GPU | IoU 0.7: GPU→ISP |
|---|---|---|---|
| ≥ 0.2 (전체) | 0.8532 | 0.8734 | 0.8446 |
| ≥ 0.3 | 0.9774 | 0.9816 | 0.9720 |
| **≥ 0.4** | **0.9948** | **0.9967** | 0.9918 |
| ≥ 0.5 | 0.9989 | 0.9989 | 0.9978 |
| ≥ 0.6 | 0.9997 | 0.9997 | 0.9997 |

**점수 0.4 이상 검출은 99.5 % 이상 양쪽에서 재현된다.** 박스 위치는 문제가 아니다.
흔들리는 것은 0.2~0.3 구간의 경계 검출뿐이고, ISP 출력이 CPU 기준보다 평균 -0.5 LSB 어두워
(1부 표 3) 그 구간 신뢰도가 조금씩 내려간 결과로 보인다.

### 리샘플 필터를 바꿔도 나아지지 않는다

| 필터 | 검출 수 | 비고 |
|---|---|---|
| smart selection (기본) | 9237 | **lanczos3와 바이트 단위로 동일** |
| lanczos3 | 9237 | smart가 고르는 필터가 이것이다 |
| michel-netravali | 7791 (-17.6 %) | 훨씬 나쁘다 |
| bicubic-spline | 7399 (-21.8 %) | 가장 나쁘다 |

계획서에는 3배 축소라 michel-netravali 구간일 것이라고 적었지만 **실제로는 lanczos3**다.
`SetSmartResize`가 downscale 블록으로 1920→960을 처리한 뒤 리샘플러는 960→640(1.5배)만 맡는데,
smart selection은 출력/입력 비(0.333)로 필터를 고르므로 `[0.5, ...]` 구간의 첫 항목 lanczos3가 선택된다.
**libpisp이 제공하는 4개 필터 중 현재 기본값이 이미 최선이다.**

## 결론 — A안 vs C안 vs 현행

**권고: 지금 통합하지 않는다(보류).** 근거는 아래 순서다.

1. **얻는 것은 확실하다.** V3D 전처리 점유가 **2.718 ms → 0**으로 완전히 사라진다.
   표시 경로(`display_convert.comp` 4.23 ms)와 검토 중인 GPU 후처리에 그만큼 여유가 생긴다.
   전처리 자체도 같은 축(wall)에서 ISP가 23 % 빠르다(1부 표 1).
2. **대가도 확실하다.** CPU가 **+0.89 ms/frame(C안)** 또는 **+1.50 ms/frame(A안)** 늘어난다.
   3.218 → 4.112(C안, +28 %) / 4.720(A안, +47 %). FPS·지연은 변하지 않는다(NPU 병목).
3. **막는 것은 검출이다.** 합의한 게이트(총 검출 ±1 %, 매칭 ≥ 0.99)를 **둘 다 넘지 못했다**
   (-2.33 %, 0.7940). 다만 **원인은 박스 정확도가 아니라 점수 임계 부근의 경계 검출**이고,
   점수 0.4 이상에서는 99.5 % 이상 일치한다. 어느 쪽이 "더 맞는지"는 정답 라벨이 없어 판정할 수 없다.

**둘 중 하나를 고른다면 C안이다.** CPU가 0.61 ms 싸고(4.112 vs 4.720), NHCW를 유지하므로
HailoRT 입력 경로가 현행과 같아 되돌리기도 쉽다. A안의 유일한 장점은 코드가 더 단순하다는 것뿐이다.

**통합을 다시 검토할 조건**(하나라도 충족되면 값어치가 생긴다):
- V3D가 실제로 부족해질 때(표시 경로 + GPU 후처리를 동시에 돌려 프레임 예산을 넘길 때).
  지금은 2.1 ms를 아끼려고 CPU 0.9 ms를 쓰는 교환인데, V3D가 남아도는 상태에서는 남는 장사가 아니다.
- 정답 라벨(또는 더 큰 영상에서의 mAP)로 "9237 vs 9457 중 어느 쪽이 맞는지" 판정이 된 뒤.
- 카메라 입력(CSI)으로 갈 때. 그때는 ISP가 경로상 자연스럽고 V3D를 아예 안 거칠 수 있다.

## 주의 · 남은 일 (2부)

- **`IspResizer::process()`가 동기다.** `BackendDevice::Run()`에 비동기 API가 없어 디코드와 겹치지 않는다.
  b8 운용점에서는 NPU 큐 대기가 지배해 e2e가 오히려 ISP 쪽이 3~4 ms 짧게 나왔지만, batch 1이나
  저지연 운용점에서는 불리할 수 있다. 전용 스레드로 감싸는 것은 하지 않았다.
- **오염 기록(1차 측정).** 1차 창(14:52~15:09) 안에 다른 세션이 `01_src/vulkan/tools/postproc_probe.cpp`를
  만들었고(15:05:50), `vcgencmd get_throttled`가 `0x80000` → **`0xe0000`**로 바뀌었다
  (비트 17·18 = "arm 주파수 제한 발생", "스로틀링 발생"이 새로 섰다. 현재 스로틀링 비트(하위 4비트)는 0).
  `isp_C` 1차 run3의 CPU 5.880이 그 영향으로 보인다. 그래서 **조용한 상태에서 2차(15:17~15:33)를 다시 돌렸고
  그 창은 오염 없음(md5 일치)**이다. 두 차수의 중앙값이 0.13 ms 안에서 일치해 결론은 바뀌지 않는다.
  표 4는 18행 전체(6회)의 중앙값이다.
- **검출 비교는 GPU 경로를 기준으로 한 상대 비교다.** 정답 라벨이 없어 "어느 쪽이 더 정확한가"는 답하지 못한다.
- b1/b4 운용점은 재지 않았다(합의).
- 5단계(B안 하이브리드 셰이더 `rgb_to_nhcw.comp`)는 착수하지 않았다.

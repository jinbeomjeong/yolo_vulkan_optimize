그 표는 칩이 92.7 °C 까지 올라 `HEF was compiled assuming clock rate of 400 MHz, while the device
clock rate is 250 MHz` 경고가 찍힌 상태에서 잰 값이라 "신뢰 불가"로 표시돼 있었다.

## 4. 결론

1. **과열 상태 측정은 지연을 4~7% 부풀렸다.** 클럭 400 → 250 MHz 강등의 영향이며, 방향과 크기가 모두 일관된다.
2. **gen3 summary 가 남긴 불일치가 해소됐다.** 그 문서는 "`run` 의 HW 지연(b1 34.62 / b8 133.35)이
   benchmark 의 HW 지연(b1 32.51 / b8 126.33)보다 크게 나왔다"를 의문으로 남겼다.
   냉각 상태에서 재니 **`run` 이 32.513 / 126.390 으로 benchmark 와 사실상 같아졌다**(차이 0.01% / 0.05%).
   → 두 도구가 다른 값을 낸 것이 아니라, **`run` 쪽 측정이 뒤에 실행되어 더 뜨거웠던 것**이다.
3. **큐 모델 계수를 정상 클럭에서 재확정했다.** FPS 에서 프레임 주기를 역산하면
   `T(2)=57.26`, `T(4)=89.86`, `T(8)=154.70 ms` 이고 선형 적합은

   > **T(B) = 24.8 + 16.2·B (ms)** — 배치당 고정비 24.8 ms + 프레임당 16.2 ms

   점근 상한은 **61.6 FPS** 다. 기존 계수 `25 + 16.2·B` 가 정상 클럭에서도 유효함이 확인됐다.
   이 계수가 운용점 스윕(M1)의 "모델 적합 / 이탈" 판정 기준이다.
4. **Overall − HW 는 배치에 비례한다**(b1 8.4 ms → b8 18.5 ms). 배치가 커질수록 호스트 구간
   (입력 변환 + 호스트 NMS + 출력 변환)이 프레임당이 아니라 배치당으로 쌓인다는 뜻이다.

## 5. 주의 · 남은 일

- 이 값은 **CLI 의 랜덤 입력 경로**다. 실제 파이프라인(`yvo_pipeline`)의 지연은 디코드·GPU 전처리와
  HailoRT 큐 대기를 포함하므로 **정의가 다르다. 섞어 쓰면 안 된다.**
- batch 1 의 benchmark FPS 는 이번에 재지 않았다(명령 A 는 2/4/8 만). 필요하면 추가한다.
- `get_throttled = 0xe0000` 은 과거 기록 비트다(측정 중 스로틀링 아님).
- 냉각 대기 합계는 약 625 초였다(실행 합계 약 11분 + 대기 약 10분).

## 3. 결론

1. **최저 지연은 그대로 e2e 약 79.2 ms(p90 약 81.8 ms), 24.42 FPS 다.** 2026-10-08 격자의 `g_b1s1`(79.16 / 81.85)과
   0.03 ms 안에서 같다 — argmax 지름길과 2026-10-11 리팩터는 최저 지연 경로에도 영향이 없다. 3회 범위가 0.03 ms 안이라 매우 안정적이다.
2. **host 후처리와 GPU 후처리의 e2e 는 같다(79.12 대 79.19).** NPU 지연은 host 가 3.1 ms 길다(37.68 대 34.55) —
   host 경로는 HailoRT 콜백 안에서 CPU NMS 를 하므로 그 시간이 NPU 지연에 들어간다. 그런데 b1/s1 은 직렬이라
   처리량(24.4 FPS = NPU 주기)이 같고, 그 3 ms 는 다음 프레임의 슬롯 대기에서 상쇄된다. **GPU 후처리의 이득은 지연이 아니라 CPU −71%(3.25 → 0.94 ms/f)** 다.
3. **gpu-depth 1 과 3 은 구별되지 않는다**(79.19 대 79.19, CPU 범위 겹침). §5.5 의 "gpu_depth 는 지연 레버가 아니다"가 GPU 후처리 경로에서도 맞다.
4. 지연 분해(gpu, 평균): `79.2 ≈ 슬롯 대기 약 42 + GPU 전처리 1.8 + NPU 34.6 + GPU 후처리 약 0.5`.
   **절반 넘게가 슬롯 대기다** — 파일 입력을 최대 속도로 디코드해 다음 프레임이 앞 프레임의 슬롯이 비기를 기다리기 때문이다(§5.5 결론 1과 같은 구조).

## 4. 주의·남은 일

- **b1/s1 은 30 fps 를 못 따라간다**(24.42 FPS, 30 fps 소스에서 약 19% 드롭). 30 fps 를 유지하는 최저 지연은 `b2/s3`(128.0 ms, 여유 +1.8%,
  격자 회차) — 연속 운용은 `b2/s4`(139.6 ms) 권고가 그대로다([`thermal_soak`](../../../thermal_soak/summary.md)).
- 남은 지렛대는 **입력 페이싱**이다. 소스 속도로 입력이 들어오면(카메라) 슬롯 대기 약 42 ms 가 줄 것으로 보이나,
  b1 은 NPU 주기(약 41 ms)가 프레임 간격(33.3 ms)보다 길어 30 fps 입력에서는 대기가 다시 쌓인다. 앱에 입력 페이싱 옵션이 없어 **미측정**이다.
- 표시 on(glass-to-glass)은 재지 않았다.
- `env_bench.txt` 에 V3D 클럭 줄이 없다(이 스크립트는 기록하지 않는다). 1150 MHz 는 같은 부팅의 `vcgencmd get_config v3d_freq`(2026-10-12 00:28 점검) 값이다.
- 결정: 표시 on·입력 페이싱·b2/s3 는 이번 범위에서 제외 (사용자 결정, 2026-10-12).

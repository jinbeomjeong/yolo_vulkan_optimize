## 4. 결론 — 지배하는 변수는 batch 가 아니라 slots 다

### 4.1 슬롯 = HailoRT 큐 깊이 (정량 확인)

| slots | FPS | 프레임 주기 (ms) | NPU 지연 (ms) | **지연 ÷ 주기** |
|---:|---:|---:|---:|---:|
| 2 | 24.41 | 40.97 | 79.52 | **1.94** |
| 4 | 34.97 (b2) / 33.42 (b4) | 28.60 / 29.92 | 111.53 / 107.60 | **3.90 / 3.60** |
| 8 | 44.55 (b8) / 44.44 (b4) | 22.45 / 22.50 | 172.59 / 173.12 | **7.69 / 7.69** |
| 16 | 51.49 | 19.42 | 301.64 | **15.53** |

**지연 ≈ slots × 프레임 주기**다. 슬롯 수가 곧 큐 깊이라는 기존 기술이 수치로 확인됐다.

### 4.2 같은 slots 에서 batch 는 거의 무의미하다

- `b4/s8` 44.440 vs `b8/s8` 44.550 — **차이 0.25%. 사실상 동률이고 지연도 173.1 vs 172.6 으로 같다.**
- `b2/s4` 34.970 vs `b4/s4` 33.420 — 오히려 **작은 배치가 4.6% 빠르다**(p90 도 168.7 vs 185.8 로 낫다).

> **계획서의 F1 가설("`b8/s8` 이 `b4/s8` 을 파레토 지배한다")은 기각됐다.** 둘은 동률이다.
> 이 가설은 `yvo_hailo_selftest` 의 보정값(b8/s8 ≈ 48.8 FPS @ 126 ms)에서 나왔는데,
> **그 값은 파이프라인 수준으로 이전되지 않는다.** selftest 는 CPU 전처리 + malloc 버퍼 경로이고
> 측정 창 정의도 다르다. 앞으로 selftest 수치로 운용점을 논하지 않는다.

### 4.3 `hailortcli` 의 배치 모델은 파이프라인에 적용되지 않는다

`latency_gen3_cooled/summary.md` 가 확정한 `T(B) = 24.8 + 16.2·B` 는 **CLI 의 랜덤 입력 경로**를 설명한다.
파이프라인에서는 batch 가 아니라 slots 이 처리량을 정하므로 이 식으로 `b4/s4`·`b8/s8` 을 예측하면 틀린다
(예측 44.5 vs 실측 33.4 / 44.55). **두 모델을 섞지 마라.**

## 5. 운용점 판정

| 정의 | 확정 운용점 | 수치 | 비고 |
|---|---|---|---|
| **O1 최대 처리량** | **`b8/s16`** | **51.49 FPS**, e2e 325 ms | NPU/PCIe 상한. 표시 matched 는 `slots+gpu_depth=19 > 10` 이라 **불가** |
| **O2 최소 지연** | **`b1/s1`** | 24.38 FPS, NPU **38.6 ms**, **e2e 81.6 ms** | §5.5 추가 측정으로 확정. **30 FPS 미달** — 약 19% 드롭 |
| **O3 30 FPS 실시간 표시** | **`b2/s4`** ← **권고** | **34.97 FPS**, NPU 111.5 ms, **e2e 142.2 / p90 168.7 ms**, `slots+gpu_depth=6` | 30 FPS 대비 **+16.6% 여유**, 표시 제약(≤10)에 **여유 4** |
| **O4 최소 CPU** | **`--postproc gpu`** (운용점 무관) | **1.12~1.15 ms/f** | 운용점 차이는 ±3% 뿐이고 **호스트 NMS 고정비가 지배**했다. GPU 후처리가 그것을 제거한다 — §5.6 |

### O3 가 `b2/s4` 인 이유

표시 경로의 목표는 **처리량이 아니라 30 FPS 추종 + 최소 지연**이다.
30 FPS 를 넘는 설정 중 지연이 가장 낮은 것이 `b2/s4` 다.

| 30 FPS 이상인 설정 | FPS | e2e mean | e2e p90 |
|---|---:|---:|---:|
| **`b2/s4`** | 34.97 | **142.17** | **168.74** |
| `b4/s4` | 33.42 | 142.81 | 185.80 |
| `b8/s8` | 44.55 | 199.05 | 261.52 |
| `b4/s8` | 44.44 | 199.58 | 260.87 |
| `b8/s16` | 51.49 | 325.26 | 443.90 |

`b8/s8` 을 쓰면 처리량이 27% 늘지만 **지연이 40% 나빠진다**(199 vs 142 ms). 소스가 30 fps 인데
44 FPS 는 쓸 데가 없으므로 지연을 사는 쪽이 맞다.
덤으로 `b2/s4` 는 `slots+gpu_depth = 6` 이라 13프레임 제약에 **여유가 4**다
(`b8/s8` 은 10 으로 **경계에 딱 붙는다** — 여유 0).

## 5.5 지연 최소화 스윕 (추가 측정, `latency_sweep/`)

O2(최소 지연)를 제대로 답하기 위해 슬롯·`gpu_depth` 를 더 줄여 재측정했다.
600프레임 ×3회, `--postproc host`, 15회 전부 경고 0·에러 0, **검출 2090 전 설정 동일**.
반복 편차는 e2e 기준 **0.01 ms** 수준이다.

| 설정 | FPS | NPU 지연 ms | **e2e mean ms** | e2e p90 ms | 30 fps |
|---|---:|---:|---:|---:|:---:|
| **`b1/s1` gpu_depth 1** | 24.38 | **38.59** | **81.59** | 81.78 | ✗ |
| `b1/s2` gpu_depth 1 | 24.39 | 79.48 | 122.39 | 122.72 | ✗ |
| `b2/s2` gpu_depth 1 | 24.40 | 79.47 | 122.38 | 122.73 | ✗ |
| `b2/s3` gpu_depth 2 | 30.49 | 95.64 | 130.40 | 154.28 | ⚠ +1.6% |
| `b2/s4` gpu_depth 1 | 34.91 | 111.44 | 142.06 | 168.72 | ✓ +16% |

**결론 3가지**

1. **지연 최소는 `b1/s1` 의 e2e 81.59 ms** 다(기존 최소 `b2/s2` 122.4 ms 대비 −33%). 분해가 정확히 맞는다:
   `81.6 = 41.0(앞 프레임 슬롯 비기 대기) + 2.1(GPU 전처리) + 38.6(NPU)`.
   → **슬롯이 1이어도 한 프레임분 대기가 남는다.** 파일을 최대 속도로 읽어 디코드가 앞서 달리기 때문이다.
   이 41 ms 를 없애려면 입력이 소스 속도로 페이싱돼야 한다(= 실제 카메라). **미측정**.
2. **`gpu_depth` 는 지연 레버가 아니다.** `b2/s4` 를 depth 1 과 3 으로 재니 142.06 vs 142.17 ms 로 차이가 없다.
   GPU 전처리(2.1 ms)가 NPU 주기 대비 너무 빨라 몇 장을 물려 두든 지연에 나타나지 않는다. 이 축은 더 볼 필요 없다.
3. **`b1/s2` 와 `b2/s2` 가 완전히 같다**(122.39 vs 122.38). 슬롯이 2면 배치가 뭐든 두 프레임분 큐가 생기고
   batch 2 는 s2 에서 파이프라이닝을 못 해 이득이 0이다. §4.1 의 "슬롯이 지배 변수"가 다시 확인된다.

**새 중간 지점 `b2/s3`**: 30.49 FPS @ 130.4 ms 로 `b2/s4` 보다 12 ms 짧지만 **여유가 +1.6% 뿐**이다.
발열로 클럭이 조금만 떨어져도 30 아래로 내려가므로 **연속 운용에는 권하지 않는다.**

**운용점 표 갱신**: O2(최소 지연) = **`b1/s1`**(e2e 81.6 ms, 24.4 FPS — 30 fps 소스에서 약 19% 드롭).
O3(30 FPS 실시간 표시) = **`b2/s4`** 로 변동 없다.

## 5.6 GPU 후처리 A/B — O4 의 답 (`07_results/raw_runner_backpressure/`)

`--postproc gpu` 통합 후 host 와 **같은 세션에서 인터리브**해 잰 값이다(900프레임 ×3회 중앙값).

| 설정 | FPS | host 대비 | **CPU ms/f** | 절감 | NPU mean ms | 검출 |
|---|---:|---:|---:|---:|---:|---:|
| host `b2/s4` | 34.97 | — | 2.921 | — | 111.33 | 3369 |
| **gpu `b2/s4`** | **34.96** | **−0.03%** | **1.122** | **−1.80 ms** | 110.31 | 3369 |
| host `b8/s16` | 51.51 | — | 3.135 | — | 301.24 | 3369 |
| **gpu `b8/s16`** | **51.48** | **−0.06%** | **1.152** | **−1.98 ms** | 297.16 | 3369 |

**GPU 후처리는 처리량을 사실상 깎지 않으면서 CPU 를 1.8~2.0 ms/frame 줄인다.**
정확도는 1816프레임 전체에서 match @ IoU 0.9 **0.9990**, 검출 총수 **9457 로 host 와 완전 동일**이다.
`perf` 에서 호스트 NMS 심볼이 45.10% → **0건**, 총 사이클 **−49.4%**.

> **주의 — 중간에 발견·수정된 결함이 있다.** 초기 통합 측정에서 gpu `b2/s4` 가 24.48 FPS(−30%)로 나왔는데,
> 후처리 비용이 아니라 `HailoRawRunner` 의 백프레셔 이중 계수였다(수동 `increase_ongoing_callbacks()` 가
> `infer_async` 내부 계수와 겹쳐 프레임당 +2 → in-flight 상한이 슬롯의 절반). 수동 쌍을 제거해 해소했다.
> **그 이전에 기록된 gpu 경로 수치(FPS·지연)는 인용하지 마라.**

## 5.7 표시 통합 e2e — O3 최종 확정 (`07_results/display_e2e/`)

운용점 **`b2/s4 --postproc gpu`** 에 HDMI 표시를 켜고 900프레임 ×3회 측정했다(전체화면 고정).

| 설정 | FPS | CPU ms/f | 검출 | **glass-to-glass** | dropped | held_max |
|---|---:|---:|---:|---:|---:|---:|
| `disp_off` | 34.950 | 1.115 | 3369 | – | – | 3 |
| `disp_asap` (표시 on) | **34.870** (−0.23%) | 1.842 | **3369** | 131.4 | **0** | **4** |
| `disp_source` (30 fps 페이싱) | 29.910 | 2.179 | **3369** | **101.1** (p90 118.4) | **0** | **4** |

- **표시를 켜도 검출이 한 건도 변하지 않는다**(3369 동일). 처리량 손실 **0.23%**.
- **GPU 4패스 합 median 6.995 ms** = 주기 28.6 ms 의 **24.5%**. 계획서 예산(7.1 ms / 25%)과 일치한다.
  네 구간 모두 NPU 유휴 기준선(M5a)보다 **같거나 빠르다** — NPU 경합에 의한 GPU 저하는 관측되지 않았다.
- `held_frames_max = 4` 로 13프레임 제약에 **여유 6**. `slot_timeout` 0, `display_dropped` 0.
- 유일한 미달은 **표시 CPU +0.727 ms**(기준 ≤0.5). `perf` 로 `vkQueuePresentKHR` 자체임을 확인했고
  회수 가능한 낭비가 아니다. **절대값으로는 오늘의 배포 경로 3.314 → 1.842 ms/f 로 오히려 싸다.**

→ **O3 운용점 `b2/s4` 가 표시를 켠 상태에서도 성립함이 확인됐다.**

## 6. 주의 · 남은 일

- ~~O4 는 이 스윕으로 답이 안 나온다~~ → **§5.6 에서 해소.** `--postproc gpu` 가 CPU 를 1.12~1.15 ms/f 로 낮춘다.
- **O3 확정은 잠정이다.** 표시를 켜면 GPU 가 4패스(전처리+후처리+변환+오버레이)를 돌고
  디코더 프레임 보유가 늘어난다. **M4 에서 `b2/s4` 가 30 FPS 를 유지하는지 재확인해야 한다.**
  30 FPS 여유가 +16.6% 뿐이라 여유가 크지 않다.
- `b4/s4` 의 GPU 셰이더 시간이 4.868 ms 로 다른 설정(2.1~3.0)보다 **60% 높다.** 원인 미확인
  (DVFS 또는 NPU 경합으로 추정). `b2/s4` 를 권고하는 부차적 이유이기도 하다. 재현 여부는 M4 에서 본다.
- 이 스윕은 전부 `--postproc host --display off` 다. 표시·GPU 후처리를 켠 값이 아니다.
- 720p·다중 스트림은 측정하지 않았다(계획서 §4 "측정하지 않는 것" 참조 — 결정을 바꾸지 않는다).

O2 는 30 fps 소스를 못 따라가 약 19% 를 버린다. 모든 프레임을 검출해야 하면 쓸 수 없다.

⚠ **O3 의 두 행은 서로 다른 실행이다.** `display_e2e/summary.md` §3 의 `disp_source` / `disp_asap` 이고,
FPS·CPU·glass 를 행 사이에서 섞어 인용하면 안 된다(이 표의 이전 판이 34.87 FPS 와 glass 101 ms 를
한 행에 적어 그 혼동을 만들었다). §8.3 이 배포하는 커맨드는 `--display-pace source` 이므로
**배포 경로의 값은 29.91 FPS / glass 101.20 ms / CPU 2.179 ms/f** 다.

### 8.2 기록해 둘 네 문장

1. **처리량을 지배하는 것은 batch 가 아니라 slots 다.** 지연 ≈ `slots × 프레임 주기` 가 네 지점에서
   성립하고, 같은 slots 에서 batch 차이는 0.25% 뿐이다(§4). 배치의 천장에 닿은 뒤로 slots 는
   **순수하게 지연만 사는 손해 레버**다(`b2/s8` 은 `b2/s4` 와 FPS 가 같고 NPU 지연만 110 → 224 ms).
2. **계획서의 F1 가설("`b8/s8` 이 `b4/s8` 을 파레토 지배한다")은 기각됐다.** 둘은 동률이다(44.55 vs 44.44,
   지연 172.6 vs 173.1). 그 가설은 `yvo_hailo_selftest` 보정값에서 나왔는데 **그 수치는 파이프라인
   수준으로 이전되지 않는다.** 앞으로 selftest 수치로 운용점을 논하지 않는다.
3. **glass-to-glass 실측 101 ms 는 계획서 추정 217 ms 의 절반 이하다.** 표시 경로가 더하는 지연은
   약 26 ms 뿐이다(변환 4.2 + present 1~2 vsync). `--display-sync latest` 는 28.2 ms 까지 내려간다.
4. **다중 스트림은 NPU 상한 때문에 불가능하다.** 1080p30 두 개 = 60 FPS 가 필요한데 상한이 51.7 이다.
   **확보한 CPU 여유(3.3 → 1.1 ms/f)는 이 한계를 풀지 못한다** — 병목이 아닌 자원의 여유이기 때문이다.

### 8.3 최종 실행 커맨드

```bash
XDG_RUNTIME_DIR=/run/user/1000 WAYLAND_DISPLAY=wayland-0 \
build/01_src/pipeline/yvo_pipeline \
  --video 04_data/videos/video_h265.mp4 --hef 03_models/yolov11m.hef \
  --mode dmabuf --layout nhcw --postproc gpu \
  --batch 2 --slots 4 \
  --display on --display-fullscreen --display-sync matched --display-pace source
```

### 8.4 이 작업으로 바뀐 것

| | 이전 (배포 경로) | 이후 |
|---|---|---|
| 파이프라인 | 디코드 → GPU 전처리 → NPU(호스트 NMS) | **디코드 → GPU 전처리 → NPU(원시) → GPU 후처리 → 오버레이 → HDMI** |
| CPU | 3.31 ms/f | **2.18 ms/f** (표시 포함, `pace source` = §8.3 커맨드) / 1.84 (`pace asap`) / 1.12 (표시 없이) |
| 가시화 | 없음 (간헐 PNG 저장) | **실시간 HDMI, glass 101 ms, 드롭 0** |
| 파이프라인에 연결된 셰이더 | 1개 | **4개** |
| 검출 | 3369 | **3369 (변화 없음)** |

**처리량은 안 올랐다**(34.96 → 34.87, 둘 다 `pace asap` 기준). 원래 그럴 예정이었다 — 병목이 PCIe/NPU다.
얻은 것은 **CPU 절반과, CPU 비용 없이 도는 실시간 가시화 경로**다.

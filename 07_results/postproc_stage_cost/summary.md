# GPU 디코딩 단계별 비용 — `yolo_decode.comp` ①~⑤ + NMS

"디코딩 → NMS" 순서를 "NMS → 디코딩"으로 바꾸자는 제안을 따져 보려고 단계별 비용을 쟀다.
NMS의 IoU는 디코딩(DFL)이 만든 박스 좌표가 있어야 계산할 수 있다. 그래서 NMS 뒤로 옮길 수 있는 단계는 ④(레터박스 역변환·clamp)뿐이다.
이 실험은 순서를 바꿨을 때 얻을 수 있는 이득의 상한과, 실제로 줄일 가치가 있는 단계를 확인한다.

| 단계 | 하는 일 (`02_shaders/yolo_decode.comp`) |
|---|---|
| ① + ② | 그룹(4앵커)마다 80클래스 바이트를 스캔해 최댓값을 구하고, 정수 임계값을 넘지 못한 그룹은 끝낸다 |
| ③ | 통과한 그룹만 DFL(16-bin softmax × 4변)로 거리를 구한다 |
| ④ | 640 레터박스 좌표를 원본 1920×1080 좌표로 되돌리고 clamp한다 |
| ⑤ | 통과 앵커마다 80클래스를 다시 읽어, 임계값을 넘는 클래스마다 `atomicAdd(count)`로 32 B 후보를 기록한다(emit) |
| NMS | `efficient_nms.comp`(별도 디스패치) |

## 1. 측정 조건

- 날짜 2026-10-08, Raspberry Pi 5, V3D 7.1 **1150 MHz**(부트로더 2026-09-25), Mesa 26.2.2, git `dcee8ad`. NPU는 쓰지 않았다(저장한 원시 텐서 픽스처). 환경: [`env_bench.txt`](env_bench.txt).
- **방법(차분법)**: 같은 셰이더를 단계마다 멈추게 컴파일한 진단 변형 S1(② 뒤 종료), S2(③ 뒤), S3(④ 뒤)와 운영 셰이더 Full의 pass1 GPU 시간(타임스탬프)을 잰다.
  - 단계 비용: ①② = S1, ③ = S2 − S1, ④ = S3 − S2, ⑤ = Full − S3.
  - 멈춘 지점의 값은 `text[31]`에 atomicXor로 남긴다. 컴파일러가 결과를 쓰지 않는 계산을 지우지(DCE) 못하게 하는 장치다.
  - 변형은 `-DYVO_DECODE_STOP=N`으로 같은 원본에서 만든다. 정의가 없으면 운영 SPIR-V가 바이트 단위로 같다(md5 `2bb79b8b…` 전후 동일, `env_bench.txt`).
  - 도구는 `yvo_postproc_probe --probe stages`이고, 커밋 `dcee8ad`의 `01_src/tools/vulkan/postproc_probe.cpp` `run_stages`다.
- **반복**: 조건마다 프로세스 3회. 각 회차 안에서 변형 4개를 라운드 3회 교차하고, 라운드마다 warmup 50 + 500프레임을 연속 스트림으로 돌린다. 실행 스크립트는 [`evidence/run_stages.sh`](evidence/run_stages.sh), 콘솔은 [`evidence/console.log`](evidence/console.log)다.
  - 표의 값은 회차 3개 중앙값의 중앙값이다. 회차 사이 편차는 0.01 ms 이내다.
- **입력**
  - 기존 영상 픽스처 `04_data/raw_tensors/`(5프레임)
  - 혼잡 영상 픽스처 `build/out/crowd_fixtures/mot20_{02,05}/`(10프레임, 만든 방법은 [`nms_crowd_stress/evidence/inputs.txt`](../nms_crowd_stress/evidence/inputs.txt))
  - 점수 임계값은 0.2가 기본이고, mot20_05만 0.02와 0.003(양자화 바닥)을 더했다. 0.02 이하는 부하를 만들기 위한 설정이다.
- **신뢰성**: 15회 모두 `[RESULT] stages PASS`였다. Full의 후보 수는 CPU 기준 구현 `cpu_yolov8_candidates()`와 모든 프레임에서 같았고, S1~S3은 후보를 내지 않았다. 이로써 주입한 변형이 실제로 쓰였음을 확인했다.
  - validation errors 0. warnings 1은 V3D가 아닌 장치를 훑을 때 나오는 알려진 줄이다.
  - SoC 온도 70~75 °C, 현재 스로틀 비트 0.

## 3. 결론

1. **④를 NMS 뒤로 옮겨도 얻을 것이 없다.** ④는 모든 조건에서 0.001~0.007 ms(pass1의 1% 미만)로 측정 잡음 수준이다.
   통과한 그룹 수십~수백 개에 곱셈과 clamp 몇 번이 전부라서다. 순서 변경으로 얻을 수 있는 성능 이득의 상한은 사실상 0이다.
   순서를 바꿀 이유가 있다면 성능이 아니라 의미 문제다. HailoRT처럼 clamp 전 좌표로 IoU를 계산하게 맞추는 것인데, 그러면 화면 경계 박스의 검출이 바뀐다.
2. **①②(클래스 스캔)는 후보 수와 무관한 고정비 약 0.30 ms다.** 셰이더 주석의 "비용의 거의 전부"는 기존 영상에서만 맞다(60%).
   혼잡 장면에서는 40% 안팎(38~40%)으로 내려간다.
3. **후보 수에 따라 늘어나는 것은 ⑤ emit이고, ③ DFL이 그다음이다.**
   - ⑤는 23 → 1582개에서 0.13 → 1.06 ms로 늘었다. 증가분은 고르지 않다. 기존 영상에서 혼잡 0.2(후보 169~202개)까지는 후보 하나에 1.0~1.6 µs이고,
     후보가 많은 구간(169 → 1582개)에서는 0.5~0.7 µs다. ③은 0.06 → 0.31 ms다.
   - 혼잡 장면(점수 0.2)에서 ⑤는 pass1의 41~45%로 가장 크다.
   - ⑤가 비싼 이유로 추정하는 것은 두 가지다. 후보마다 한 주소(`count`)에 장치 범위 atomicAdd를 하므로 직렬화되고, 통과 앵커마다 80클래스를 다시 읽는다. 둘을 나눠 재지는 않았다.
4. **디코딩 + NMS 합계**: 혼잡 장면 점수 0.2에서 약 0.94~0.97 ms/frame이다(mot20_02 0.749 + 0.190, mot20_05 0.802 + 0.168). 기존 영상은 0.50 + 0.05 ms다.
   GPU 예산(표시 off)에는 여유가 크다. 표시 on 경로에서는 V3D를 표시 변환과 나눠 쓴다.

## 4. 주의·남은 일

- **차분법의 한계**: 멈춘 뒤의 코드가 사라지므로 변형마다 레지스터 할당과 스케줄이 다를 수 있다. 단계 비용은 근사다.
  - sink는 통과 그룹마다 atomicXor를 1회 더하므로 ⑤를 약간 작게 잡는다.
  - ④처럼 0.01 ms 아래인 값은 "무시할 만하다" 이상으로 해석하지 않는다.
- 2.1절은 10프레임(기존 영상 5프레임)을 순환한 연속 스트림이고, 2.2절 NMS는 앞 5프레임 스트림이다. 두 표의 후보 수는 같은 조건이 아니다.
- 파이프라인 안(디코드·전처리·표시와 V3D 공유)의 단계 비용은 재지 않았다. 이 값은 단독 스트림 값이다.
- **줄일 후보**(구현하지 않음, 결정 필요)
  - ⑤의 atomic을 워크그룹 단위로 모은다. 공유 메모리 카운터로 모은 뒤 전역 atomicAdd를 워크그룹당 한 번만 한다.
  - 클래스 재스캔을 없앤다. ①에서 통과 클래스의 비트마스크를 남겨 두는 방식이다.
  - 둘 다 출력 순서가 바뀔 수 있다. 다만 NMS가 (점수, anchor_key) 전순서로 정렬하므로 최종 검출은 바뀌지 않아야 하고, 이것을 검증해야 한다.
  - 기대 이득은 혼잡 장면에서 pass1의 최대 약 40%(0.3 ms/frame)다. 기본 운용(기존 영상)에서는 0.13 ms 이하다.

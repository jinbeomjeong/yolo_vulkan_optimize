# 후보 축소 방식(앵커별 max · topK) 오프라인 비교

**제안된 방식**

```
score = cls_logit.sigmoid().max(-1).values   # 앵커별 최고 점수
idx   = score.topk(K).indices                # 상위 K개 앵커만 남김
```

이 방식이 현재 기준과 비교해 결과·후보 수·NMS 비용을 얼마나 바꾸는지 저장된 원시 텐서로 쟀다.
- 현재 기준: 점수 T 이상인 **모든 클래스**를 후보로 → 클래스별 greedy NMS(IoU 0.7, 클래스당 100).
- 제안된 방식은 PCIe를 건넌 뒤 호스트에서 도는 방식이므로 PCIe 양은 바뀌지 않는다([`candidate_reduction_survey`](../candidate_reduction_survey/summary.md)).

## 1. 조건

- 2026-10-08, Raspberry Pi 5(Cortex-A76 2.4 GHz, governor ondemand), git `683d184`. 환경은 [`env_bench.txt`](env_bench.txt)에 있다. SoC 온도는 70~77 °C였고, `throttled=0xe0000`은 과거 기록 비트만 켜진 상태다(현재 비트 0).
- **도구**: `yvo_postproc_probe --probe topk`(CPU 전용, 커밋 `683d184`).
  - 모든 경우를 기준 구현 `cpu_yolov8_candidates()` 출력에서 만든다. 그래서 디코드와 좌표는 기준과 바이트 단위로 같고, **후보를 고르는 방식만** 다르다.
  - 매칭은 (class, anchor_key)가 정확히 같은지로 본다.
  - 자체 검사 7개가 9회 실행 모두 PASS였다. 예: REF == `cpu_yolov8_postprocess`, 매칭된 검출의 비트 차이 0.
- **입력**: 영상마다 앞 60프레임(25/30 fps에서 약 2초)의 원시 텐서. `yvo_hailo_raw_probe --dump-frames 60`으로 `build/out/topk_fixtures/<v>/`(git 밖)에 덤프했다.
  - 기존 영상 `video_h265.mp4`(default), 혼잡 영상 `mot20_02_h265.mp4`·`mot20_05_h265.mp4`.
  - 덤프 로그는 [`evidence/fixture_dump_p1_*.txt`](evidence/fixture_dump_p1_mot20_05.txt)에 있다. HailoRT NMS 대 CPU 기준 일치율은 1.0000 / 0.9993 / 0.9993이다.
  - `hailort_fixture_dump_*.log`의 error 7건은 NHCW로 NMS 경로를 만들려다 의도적으로 실패한 configure다(온도 경고 0).
- **반복**: 영상 3개 × 3회. 실행 스크립트는 [`evidence/run_topk.sh`](evidence/run_topk.sh)이다.
  - 정확도 열(후보·검출·lost·extra)은 3회 모두 같다.
  - 시간 열은 프레임마다 5회 반복한 중앙값의, 프레임 사이 중앙값이고, 그것을 다시 3회 중앙값으로 냈다.
  - CPU 시간은 단독 실행 값이라 원인 분석용 참고값이다.
- **비교한 경우**
  - **REF(T)**: 현재 기준(다중 클래스).
  - **MAX(T)**: 앵커마다 최고 클래스 하나만 남긴다(`max(-1)`).
  - **SNIP(K)**: 제안 코드 그대로. 앵커별 최고 점수 상위 K개이고, **임계값이 없다**.
  - **SNIP_T(T,K)**: SNIP(K)에 점수 T 이상 조건을 더한다.
  - **MC_HIST(T,K)**: 앵커 선택은 topK로 하되 다중 클래스를 유지한다. 컷 = max(T, 앵커 최고 점수의 K번째 값)이고, 컷을 넘은 앵커의 T 이상 클래스를 모두 후보로 둔다. 8비트 점수 히스토그램으로 GPU에 옮길 수 있는 형태다.
- 점수 T는 0.2(운용값), 0.05, 0.02, 0.003(양자화 바닥)이고, K는 100, 300, 1024다. 0.05 이하는 부하를 만들려는 설정이다.

## 3. 결론

1. **제안 코드를 그대로 쓰면(임계값 없는 topK) 결과가 망가진다.**
   - 한산한 장면(default)은 T 이상 앵커가 프레임당 13개뿐이다. 그래서 K개를 채우려고 점수 0에 가까운 앵커까지 후보가 된다. 검출이 101 → 4495개로 늘고, 거의 전부 쓰레기다. CPU NMS도 0.4 → 18~678 µs로 오히려 비싸진다.
   - 혼잡 장면에서 K=100이면 실제 검출의 26~38%를 잃는다.
   - topK는 반드시 **점수 임계값과 함께** 써야 한다. TensorRT EfficientNMS도 "임계값 → 상위 K"로 둘을 겹쳐 쓴다([`08_learn/11_tensorrt_efficient_nms.md`](../../08_learn/11_tensorrt_efficient_nms.md)).
2. **임계값을 더해도(SNIP_T) 운용값 0.2에서는 줄일 것이 없다.**
   - 손실을 없애는 데는 K = 300이면 충분했다(혼잡 장면 앞 60프레임의 후보 최대 216개). K = 100은 손실이 났고, 217~299는 시험하지 않았다.
   - 그러면 후보가 그대로라 MAX와 같아진다. K=100처럼 줄이면 사람 검출을 잃는다.
3. **`max(-1)`(앵커당 클래스 하나)는 결과를 바꾼다.**
   - 운용값 0.2에서는 작다(default 1%, 혼잡 0%).
   - 임계값을 낮추면 커진다(0.02에서 9~15%, 0.003에서 22~25%). 지금 디코더와 HailoRT NMS가 내는 다중 클래스 결과와 달라진다.
4. **다중 클래스를 유지하는 MC_HIST는 K ≥ (T 이상인 앵커 수)면 기준과 정확히 같다**(T=0.2에서 K = 300·1024이면 세 영상 모두 같음).
   - 다만 앵커 수를 자르는 것이라 **후보 수(다중 클래스 포함)의 상한은 보장하지 않는다.** T=0.02에서 K=1024여도 1024 초과 프레임이 26개 그대로였다.
5. **낮은 임계값에서 GPU NMS 용량(1024)을 지키는 안전장치로 쓰면 손실이 크다.**
   - 후보 수를 직접 자르는 SNIP_T(1024)는 1024 초과 프레임을 0으로 만든다.
   - 대신 T=0.02에서 검출의 8.7%(717개), T=0.003에서 41%를 잃는다.
   - 얻는 것은 그런 프레임의 CPU 억제 약 0.8~1.5 ms/f(최대 2.8 ms)다([`nms_crowd_stress`](../nms_crowd_stress/summary.md) 2.3절). 처리량에는 원래 영향이 없었다.
6. **판단: 채택하지 않는다.**
   - 운용값에서는 효과가 없다(K ≥ 300이면 기준과 같고, 작은 K는 손실).
   - 낮은 임계값에서는 손실이 이득보다 크다.
   - 쓴다면 다중 클래스를 유지하는 MC_HIST에 K ≥ 300을 두어 **앵커 수의 상한**으로만 쓴다(후보 수의 상한은 아니다).
     운용값 T=0.2, 앞 60프레임 기준으로는 결과가 바뀌지 않았다. 다만 T=0.05에서는 K = 300도 4500개 중 1775개를 잃었고, 여유도 267개 대비 300개뿐이다.

## 4. 주의·남은 일

- 각 영상의 **앞 60프레임**만 썼다(연속 2초 남짓). 장면 전체의 분포가 아니다. 결론(K ≥ 300이면 손실 0)은 이 구간 기준이며, 혼잡 장면 전체 900프레임의 후보 최대값은 267개였다([`nms_crowd_stress`](../nms_crowd_stress/summary.md)).
- 정확도는 **기준 구현과 같은지**로만 판정했다. 정답 라벨 기준 mAP가 아니다. 예를 들어 MAX가 버린 비최고 클래스 검출이 실제로 맞는 검출인지는 판정하지 않았다.
- sel 열(선택 비용)은 CPU 에뮬레이션(partial_sort·nth_element)이라 GPU 구현 비용을 대표하지 않는다. GPU에서는 8비트 히스토그램 방식이 될 것이다.
- 클래스당 100개 상한과의 상호작용은 따로 분리하지 않았다.

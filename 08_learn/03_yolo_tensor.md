## 3.0 이 챕터가 답하는 질문

[01_big_picture.md](01_big_picture.md) §1.4 ④에서 이렇게 적었다.

> NPU가 준 숫자는 아직 "박스"가 아니다. 8400개쯤 되는 격자칸마다 "여기에 뭔가 있을 확률"과
> "박스가 어느 방향으로 얼마나 뻗어 있는지"가 들어 있다.

이 챕터는 그 한 문장을 끝까지 푼다. 다 읽으면 **1,221,120 바이트짜리 숫자 덩어리가
어떻게 "화면 왼쪽 위에 사람이 있다"로 번역되는지**를 손으로 계산할 수 있게 된다.

## 3.1 텐서(tensor)란 무엇인가

**텐서 = 숫자를 여러 차원으로 늘어놓은 배열.** 그게 전부다. 수학에서 말하는 텐서에는 더
엄밀한 정의가 있지만, 딥러닝에서 "텐서"는 그냥 **다차원 배열**을 가리킨다.

```
0차원 (스칼라)  : 3.14                      숫자 하나
1차원 (벡터)    : [3, 1, 4, 1, 5]           줄 하나
2차원 (행렬)    : [[3, 1],                  표 하나
                   [4, 1],
                   [5, 9]]
3차원          : 표를 여러 장 겹쳐 놓은 것
```

### 이미지가 왜 3차원인가

컬러 사진 한 장을 생각하자. 가로 640, 세로 640 픽셀이고 각 픽셀은 빨강(R)·초록(G)·파랑(B)
세 값을 갖는다. 그러면 숫자의 개수는

```
640 × 640 × 3 = 1,228,800 개
```

이고, 이 숫자들을 "세로 위치 h, 가로 위치 w, 색 채널 c"라는 **세 개의 축**으로 주소를 매겨
찾는다. 그래서 이미지는 3차원 텐서다.

딥러닝에서는 보통 여기에 축이 하나 더 붙는다. **여러 장을 한꺼번에 처리**하기 때문이다.
그 장수를 **N**(batch, 배치)이라고 하고, 전체는 4차원 `N × H × W × C`가 된다.
네 글자의 뜻은 다음과 같다. 이 챕터 내내 쓴다.

| 글자 | 뜻 | 이 프로젝트의 입력에서 |
|---|---|---|
| **N** | batch — 한 번에 몇 장 | 1~8 (→ [04_npu_hailort.md](04_npu_hailort.md) §4.4) |
| **H** | height — 세로 픽셀 수 | 640 |
| **W** | width — 가로 픽셀 수 | 640 |
| **C** | channel — 채널(색이나 특징) 수 | 3 (R, G, B) |

여기서 **채널(channel)** 이라는 말을 한 번 풀어 둔다. 채널은 "같은 위치에 겹쳐 있는 값들의
목록"이다. 입력 이미지에서는 채널이 R·G·B 3개지만, 신경망 중간에서는 채널이 80개, 256개가
되기도 한다. 그때 채널은 색이 아니라 **"이 위치에 세로선이 있는가", "이 위치가 바퀴처럼
생겼는가"** 같은 각각 다른 성질의 점수다.

## 3.2 레이아웃 — 같은 숫자인데 순서가 다르다

여기가 **이 프로젝트 전체를 지배하는 주제**다. 천천히 읽어야 한다.

컴퓨터 메모리는 사실 **1차원**이다. 0번지, 1번지, 2번지... 일렬로 늘어선 칸일 뿐이다.
그런데 우리가 다루는 이미지는 3차원이다. 그러니 **3차원 좌표 (h, w, c)를 1차원 주소로
바꾸는 규칙**이 반드시 필요하다. 그 규칙을 **레이아웃(layout)** 또는 **메모리 배치 순서**라고
한다.

규칙이 하나가 아니라는 것이 문제다.

### NHWC — "픽셀 하나를 통째로 붙여 놓기"

```
idx = (h · W + w) · C + c
```

읽는 법: 먼저 (h, w) 픽셀 하나를 정하고, 그 픽셀의 R·G·B 3개를 **연달아** 쓴다.
다음 픽셀로 넘어가서 또 R·G·B를 쓴다.

```
메모리:  R G B | R G B | R G B | R G B | ...
         (0,0)  (0,1)   (0,2)   (0,3)
```

우리가 흔히 "RGB 이미지 파일"이라고 부르는 형식이 이것이다. PNG를 읽거나 OpenCV로 이미지를
열면 대체로 이 순서다(OpenCV는 BGR이지만 배치 규칙은 같다).

### NCHW — "빨강 사진, 초록 사진, 파랑 사진을 따로 쌓기"

```
idx = (c · H + h) · W + w
```

읽는 법: **빨강만 모아 640×640 한 장**, 그 뒤에 **초록만 모아 한 장**, 그 뒤에 파랑 한 장.

```
메모리:  [R 채널 640×640 전체] [G 채널 640×640 전체] [B 채널 640×640 전체]
```

PyTorch나 Caffe 계열이 기본으로 쓰는 순서다.

### NHCW — "행 하나 안에서만 채널별로 나누기"

```
idx = (h · C + c) · W + w
```

이것이 **Hailo-8 장치가 실제로 요구하는 순서**다. 처음 보면 기괴하게 느껴지는데,
NCHW와 NHWC의 중간이라고 생각하면 된다.

읽는 법: **한 행(h)을 고른다. 그 행의 빨강 640개를 쭉 쓰고, 그 행의 초록 640개, 그 행의
파랑 640개를 쓴다. 그리고 다음 행으로 넘어간다.**

```
메모리:  [h=0 의 R 640개][h=0 의 G 640개][h=0 의 B 640개]
         [h=1 의 R 640개][h=1 의 G 640개][h=1 의 B 640개]
         ...
```

세 레이아웃을 3×2 픽셀, 채널 3개짜리 아주 작은 예로 늘어놓으면 이렇다.
`Rhw` = 행 h, 열 w 의 빨강 값이라는 뜻이다.

```
원본 (H=2, W=3, C=3)
      w=0    w=1    w=2
h=0  R00G00B00  R01G01B01  R02G02B02
h=1  R10G10B10  R11G11B11  R12G12B12

NHWC : R00 G00 B00 | R01 G01 B01 | R02 G02 B02 | R10 G10 B10 | R11 G11 B11 | R12 G12 B12
NCHW : R00 R01 R02 R10 R11 R12 | G00 G01 G02 G10 G11 G12 | B00 B01 B02 B10 B11 B12
NHCW : R00 R01 R02 | G00 G01 G02 | B00 B01 B02 ‖ R10 R11 R12 | G10 G11 G12 | B10 B11 B12
                                              ↑ 여기서 행이 바뀐다
```

**숫자는 셋 다 똑같이 18개다. 값도 똑같다. 순서만 다르다.**

### 순서가 왜 문제인가 — 두 가지 이유

**이유 1: 소비자가 요구하는 순서가 정해져 있다.**

Hailo-8은 NHCW를 받는다. 우리 GPU 전처리 셰이더가 NHWC로 써 놓으면, 런타임이 CPU로
**순서를 바꿔 주는 일(전치, transpose)** 을 대신 한다. 공짜가 아니다. 이 프로젝트에서
그 비용은 프레임당 약 **14 ms**였다
([`10_paper/paper_ko.md`](../10_paper/paper_ko.md) §4.3.2, CPU 17.6 → 3.5 ms).

**이유 2: 읽는 방향에 따라 속도가 10배까지 달라진다.**

메모리는 한 바이트씩 읽는 게 아니라 **캐시 라인**이라는 덩어리(보통 64바이트)로 읽어 온다.
연속된 주소를 읽으면 한 번 읽어 온 덩어리를 다 쓰지만, 주소를 건너뛰며 읽으면 매번
덩어리 하나를 가져와 1바이트만 쓰고 버린다.

NHWC로 놓인 데이터에서 "빨강만" 뽑으려면 3칸씩 건너뛰어야 한다(stride 3). 위 14 ms의
정체가 바로 이것이었다. 자세한 사정과 그것이 GPU 메모리에서 왜 10배로 증폭됐는지는
[10_why_this_design.md](10_why_this_design.md) 와 [06_zerocopy_dmabuf.md](06_zerocopy_dmabuf.md) 가 다룬다.

> **여기서 기억할 한 문장**: 레이아웃은 "취향"이 아니라 **성능과 정확성을 동시에 정하는
> 계약**이다. 이 프로젝트는 GPU 셰이더가 **처음부터 NHCW로 쓰게** 만들어 전치를 없앴다.

## 3.3 CNN과 객체 검출 — 무엇을 하는 것인가

### 합성곱(convolution)의 직관

**CNN**(Convolutional Neural Network, 합성곱 신경망)은 이미지를 다루는 신경망의 한 종류다.
핵심 연산인 **합성곱**은 말은 어렵지만 하는 일은 단순하다.

작은 도장(보통 3×3)을 이미지 위에서 한 칸씩 옮겨 가며 찍는다. 도장이 찍힌 자리의
9개 픽셀에 각각 정해진 가중치를 곱해 더하고, 그 결과 하나를 출력 자리에 적는다.

```
입력 한 조각        도장(커널)        결과
┌───┬───┬───┐     ┌───┬───┬───┐
│ 10│ 12│ 11│     │ -1│ 0 │ +1│    (10·-1 + 12·0 + 11·+1)
├───┼───┼───┤  ×  ├───┼───┼───┤  = + (20·-1 + 22·0 + 21·+1)  =  3
│ 20│ 22│ 21│     │ -1│ 0 │ +1│    + (30·-1 + 31·0 + 33·+1)
├───┼───┼───┤     ├───┼───┼───┤
│ 30│ 31│ 33│     │ -1│ 0 │ +1│
└───┴───┴───┘     └───┴───┴───┘
```

이 도장은 "왼쪽보다 오른쪽이 밝으면 큰 값"을 내므로 **세로 경계선 탐지기**다.
도장의 9개 숫자를 바꾸면 가로선 탐지기도, 대각선 탐지기도 된다.
**학습(training)이란 이 숫자들을 데이터로부터 자동으로 정하는 과정**이다.
이 프로젝트는 이미 학습이 끝난 모델을 쓰므로 학습 이야기는 하지 않는다.

### 특징맵(feature map)과 깊이

도장 하나를 이미지 전체에 찍으면 결과도 이미지 모양의 2차원 배열이 나온다. 이것을
**특징맵(feature map)** 이라고 한다. 도장 80개를 쓰면 특징맵 80장이 나오고, 이것이 곧
**채널 80개**다. 3.1에서 "중간에서 채널은 색이 아니다"라고 한 것이 이 뜻이다.

레이어를 쌓으면 뒤로 갈수록 추상적인 것을 본다.

```
레이어 1~2 :  경계선, 색 덩어리          ← 3×3 도장이 보는 범위: 원본 몇 픽셀
레이어 중반 :  바퀴, 창문, 눈, 귀         ← 보는 범위가 수십 픽셀로 넓어진다
레이어 후반 :  "자동차 같은 것", "사람 같은 것"  ← 수백 픽셀을 종합한다
```

동시에 **해상도는 줄인다.** 640×640으로 끝까지 가면 계산량이 감당이 안 되기 때문이다.
2칸씩 건너뛰며 도장을 찍으면 출력이 절반 크기가 되는데, 이 "몇 칸씩 건너뛰는가"를
**stride(스트라이드, 보폭)** 라고 한다.

### 분류가 아니라 검출

- **분류(classification)**: "이 사진은 고양이다" — 답이 하나
- **검출(detection)**: "여기(x=120, y=40, 너비 80, 높이 150)에 사람, 저기에 차" — 답이
  **개수도 모르는 여러 개**이고, 각각 **위치까지** 답해야 한다

개수를 미리 모른다는 것이 설계를 어렵게 만든다. YOLO의 답은 이것이다.

> **화면을 격자로 나누고, 격자칸마다 "너 담당 구역에 뭐 있니?"를 전부 물어본다.**

칸이 8400개면 답도 8400개가 나오고, 그중 점수가 높은 것만 남긴다. 개수를 미리 정할
필요가 사라진다. **YOLO**라는 이름 자체가 You Only Look Once(한 번만 본다)의 약자로,
이미지를 한 번 통과시켜 모든 후보를 한꺼번에 낸다는 뜻이다.

## 3.4 anchor-free 그리드와 3스케일

### 격자가 몇 개인가

입력은 640×640이다. 마지막 특징맵의 stride가 8이라면 격자는 640/8 = 80칸씩, 즉 80×80이다.
그런데 YOLOv8/v11은 **격자를 세 벌** 만든다.

| 이름 | stride | 격자 크기 | 칸 수 | 한 칸이 담당하는 원본 영역 |
|---|---:|---|---:|---|
| **P3** | 8 | 80 × 80 | 6400 | 8 × 8 픽셀 |
| **P4** | 16 | 40 × 40 | 1600 | 16 × 16 픽셀 |
| **P5** | 32 | 20 × 20 | 400 | 32 × 32 픽셀 |
| | | | **8400** | |

`80² + 40² + 20² = 6400 + 1600 + 400 = 8400`. [01_big_picture.md](01_big_picture.md)에서
"8400개쯤 되는 격자칸"이라고 한 숫자가 여기서 나온다.

```
 P3 (stride 8, 80×80)      P4 (stride 16, 40×40)    P5 (stride 32, 20×20)
 ┌┬┬┬┬┬┬┬┬┬┬┬┬┬┬┬┬┐        ┌─┬─┬─┬─┬─┬─┬─┬─┐        ┌───┬───┬───┬───┐
 ├┼┼┼┼┼┼┼┼┼┼┼┼┼┼┼┼┤        ├─┼─┼─┼─┼─┼─┼─┼─┤        │   │   │   │   │
 ├┼┼┼┼┼┼┼┼┼┼┼┼┼┼┼┼┤        ├─┼─┼─┼─┼─┼─┼─┼─┤        ├───┼───┼───┼───┤
 └┴┴┴┴┴┴┴┴┴┴┴┴┴┴┴┴┘        └─┴─┴─┴─┴─┴─┴─┴─┘        └───┴───┴───┴───┘
  촘촘 = 작은 물체용          중간                     성긴 = 큰 물체용
```

### 왜 세 벌인가

격자 한 칸은 자기 담당 구역 주변의 물체만 제대로 볼 수 있다.

- **작은 물체**(멀리 있는 보행자, 20×40 픽셀)를 32칸짜리 성긴 격자로 보면 한 칸 안에
  다 들어가 버려서 위치를 정밀하게 못 짚는다. 촘촘한 P3가 맡아야 한다.
- **큰 물체**(가까운 버스, 600×400 픽셀)를 8칸짜리 촘촘한 격자로 보면 한 칸이 버스의
  극히 일부만 보게 되어 "이게 버스의 어디쯤인지" 판단할 근거가 부족하다. 또 그 칸에서
  박스를 뻗어 나가야 하는 거리가 너무 멀다. 성긴 P5가 맡아야 한다.

그래서 **크기가 다른 격자 세 개를 동시에 돌리고, 물체 크기에 맞는 격자가 답하게 둔다.**

### anchor-free 란

예전 검출기(YOLOv3, SSD 등)는 칸마다 **미리 정해 둔 박스 모양 여러 개**(앵커 박스,
anchor box)를 두고 "그 박스를 얼마나 늘이고 줄일지"를 예측했다. 앵커 박스의 크기와
비율을 사람이 데이터셋마다 튜닝해야 해서 번거로웠다.

**anchor-free** 방식은 그 미리 정한 박스를 없앴다. 칸의 중심에서 **상·하·좌·우 네 방향으로
얼마나 뻗어 있는지**만 직접 답한다.

```
        ↑ top
        │
 left ──●── right       ● = 격자칸의 중심 (w + 0.5, h + 0.5)
        │                   네 거리(left, top, right, bottom)만 예측한다
        ↓ bottom
```

이 프로젝트 코드에서 쓰는 식은 이렇다
([`cpu_yolov8_decode.hpp`](../01_src/ref/cpu_yolov8_decode.hpp) 주석 5).

```
x1 = (w + 0.5 - d_left ) · stride        y1 = (h + 0.5 - d_top   ) · stride
x2 = (w + 0.5 + d_right) · stride        y2 = (h + 0.5 + d_bottom) · stride
```

`+0.5`는 칸의 좌상단이 아니라 **중심**을 쓴다는 뜻이고, `· stride`는 격자 좌표를
640×640 픽셀 좌표로 되돌리는 것이다. P5의 (w=3, h=2) 칸의 중심은 `(3.5×32, 2.5×32)
= (112, 80)`이다.

이 문서에서는 격자 한 칸을 계속 **앵커(anchor)** 라고 부른다. anchor-free에서도 "예측
하나가 나오는 자리"라는 뜻으로 이 단어를 쓰는 것이 관례다.

## 3.5 DFL 박스 디코드 — 왜 좌표 4개를 그냥 안 주는가

### 문제 제기

앵커마다 필요한 값은 거리 4개(left, top, right, bottom)다. 그러면 출력 채널이 4개면
충분할 것 같은데, 이 모델의 box 텐서는 **채널이 64개**다. `64 = 4 × 16`이다.
왜 16배로 부풀렸는가?

### 분포로 답하기

숫자 하나로 "거리 = 3.7"이라고 답하면 **확신의 정도를 표현할 방법이 없다.**
3.7이 확실한 건지, 3과 5 사이 어딘가인데 평균을 낸 건지 구분되지 않는다.
물체 경계가 흐릿하거나 가려져 있으면 모델은 실제로 확신이 없다.

**DFL**(Distribution Focal Loss, 분포 초점 손실)은 답을 **하나의 숫자 대신 확률 분포**로
내게 한다. 구체적으로는 거리를 0, 1, 2, ..., 15의 **16개 칸(bin, 빈)** 으로 쪼개고,
각 칸에 얼마나 무게가 실리는지를 답하게 한다. 이 16이라는 수를 **`reg_max`** 라고 하고,
이 프로젝트에서는 [`cpu_yolov8_decode.hpp`](../01_src/ref/cpu_yolov8_decode.hpp)의
`kDflRegMax = 16`으로 박혀 있다.

```
왼쪽 거리(left)의 분포 예시

 무게
  │        ▄▄
  │      ▄▄██▄▄
  │    ▄▄██████▄
  └──┬──┬──┬──┬──┬──┬──┬──┬── bin
     0  1  2  3  4  5  6  7 ... 15
                ↑
        기대값 ≈ 3.7  ← 이것이 최종 거리

확신이 있으면 한 칸에 몰리고, 없으면 넓게 퍼진다.
숫자 하나로 답했다면 이 차이가 사라진다.
```

### softmax와 기대값

모델이 내놓은 16개 값은 그냥 실수라 합이 1이 아니다. 이것을 확률로 바꾸는 함수가
**softmax(소프트맥스)** 다.

```
e[b] = exp(v[b])                       ← 전부 양수로 만들고 큰 값을 더 키운다
p[b] = e[b] / (e[0] + ... + e[15])     ← 합이 1이 되도록 나눈다  → 확률
```

그리고 **기대값**(각 칸 번호에 그 확률을 곱해 더한 것)이 최종 거리다.

```
d = Σ b · p[b]      (b = 0 .. 15)
```

이 프로젝트 구현은 나눗셈을 한 번만 하려고 합쳐서 쓴다
([같은 헤더](../01_src/ref/cpu_yolov8_decode.hpp) 주석 4).

```
m = max(v)                             ← ⚠ 반드시 최댓값을 빼고 시작한다
e[b] = exp(v[b] - m)
d = Σ b·e[b] / Σ e[b]
```

**`m`을 빼는 이유**: 역양자화된 값이 최대 19.1까지 올라가는데 `exp(19.1)`은 2억쯤 된다.
float32의 유효 자릿수를 낭비해 정밀도를 잃는다. 모든 값에서 같은 수를 빼도 softmax 결과는
수학적으로 완전히 같으므로(분자·분모에서 `exp(-m)`이 약분된다) 안전하게 쓸 수 있다.
이것은 softmax를 구현하는 사실상 모든 코드가 쓰는 표준 기법이다.

### 채널 번호를 어떻게 매기는가

거리 4개 × 빈 16개 = 채널 64개인데, **어떤 순서로 늘어놓았는지**가 문제다. 두 가지가 가능하다.

```
CoordMajor : ch = coord · 16 + bin     left의 16빈, top의 16빈, right의 16빈, bottom의 16빈
             ch:  0..15    16..31   32..47   48..63
                  left      top     right   bottom

BinMajor   : ch = bin · 4 + coord      bin0의 4방향, bin1의 4방향, ...
             ch:  0 1 2 3   4 5 6 7   ...
                  L T R B   L T R B
```

모델 문서에 적혀 있지 않아서 **이 프로젝트는 실측으로 판정했다.** 결과는 §3.8에서 다룬다.

## 3.6 INT8 양자화 — 8비트로 줄인다는 것

### 무엇을 하는가

학습된 신경망의 가중치와 중간 값은 보통 **float32**(32비트 부동소수점)다. 이것을
**INT8**(8비트 정수, 0~255 또는 −128~127)로 바꾸는 것이 **양자화(quantization)** 다.

바꾸는 규칙은 1차 함수 하나다.

```
실제 값 = (q − zero_point) × scale
```

- **q** — 실제로 메모리에 들어 있는 0~255 사이의 정수
- **scale**(스케일) — 정수 1칸이 실제 값 얼마에 해당하는지
- **zero_point**(영점) — 실제 값 0이 정수로 몇 번인지

예를 들어 `scale = 0.0034697596`, `zero_point = 0` 이면

```
q = 0   → 0.0
q = 57  → 57 × 0.0034697596 = 0.19778
q = 58  → 58 × 0.0034697596 = 0.20124
q = 255 → 255 × 0.0034697596 = 0.88478
```

이 값들은 이 프로젝트 모델의 P3 클래스 텐서 실제 값이다
([`10_paper/paper_ko.md`](../10_paper/paper_ko.md) §3.2 표).
0 ~ 0.885 구간을 **256단계로 쪼갠 눈금자**라고 생각하면 정확하다.

```
실제 값   0.0 ─────────────────────────────────── 0.885
          │    │    │    │    ...    │    │    │
q         0    1    2    3          253  254  255
          └ 한 칸 = 0.00347 (이보다 세밀한 값은 표현 못 한다)
```

### 왜 8비트로 줄이는가

세 가지 모두 이 프로젝트에 직결된다.

1. **메모리가 4분의 1** — 가중치가 4배 작아지면 칩 안에 더 많이 들어간다.
2. **전송량이 4분의 1** — 이 프로젝트의 병목은 PCIe 전송이다
   ([01_big_picture.md](01_big_picture.md) §1.2 (5)). float32였다면 출력이 1.22 MB가 아니라
   4.88 MB이고 처리량이 4분의 1 근처로 떨어졌을 것이다.
3. **연산기가 훨씬 작고 빠르다** — 8비트 정수 곱셈기는 float32 곱셈기보다 회로가 수십 배
   작다. NPU가 "같은 면적에 연산기를 몇천 개" 넣을 수 있는 근거다
   (→ [04_npu_hailort.md](04_npu_hailort.md) §4.1).

### 무엇을 잃는가

**정밀도**를 잃는다. 위 눈금자에서 0.19778과 0.20124 사이의 값은 표현할 방법이 없다.
또 **표현 범위 밖**(여기서는 0.885 초과)의 값은 잘려 나간다.

실제 영향은 "박스 좌표가 소수점 아래에서 조금 달라진다" 정도이고, 검출 결과 자체는
거의 바뀌지 않는다. 이 프로젝트가 GPU 후처리로 옮기고도 **검출 수 3369가 한 건도 변하지
않은 것**([`07_results/display_e2e/summary.md`](../07_results/display_e2e/summary.md))은
양자화된 정수를 양쪽이 똑같이 해석했기 때문이다.

> **주의**: 양자화 파라미터는 **텐서마다 다르다.** 이 모델은 6개 텐서가 각각 다른
> scale·zero_point를 갖는다(§3.8 표). 코드에 상수로 박으면 안 되고 HEF에서 읽어야 한다.

## 3.7 IoU와 greedy NMS — 겹친 박스 정리하기

### 왜 겹치는가

앵커 8400개가 **각자** 답한다. 자동차 한 대가 대여섯 칸에 걸쳐 있으면 그 칸들이 전부
"여기 자동차 있음"이라고 답한다. 그래서 같은 물체에 박스가 여러 개 나온다.

```
       ┌───────────┐
    ┌──┼────────┐  │      같은 자동차 하나에
    │  │ ┌──────┼──┼──┐   박스 3개가 겹쳐 나왔다
    │  └─┼──────┘  │  │
    └────┼─────────┘  │
         └────────────┘
```

### IoU — 겹침의 정의

**IoU**(Intersection over Union, 교집합 나누기 합집합)는 두 박스가 얼마나 겹치는지를
0~1로 재는 값이다.

```
          IoU = 교집합 넓이 / 합집합 넓이

 A ┌──────────┐
   │      ┌───┼──────┐ B        교집합 = 두 박스가 함께 덮은 부분
   │      │▓▓▓│      │          합집합 = 두 박스가 덮은 전체 부분
   └──────┼───┘      │
          └──────────┘

 IoU = 0.0  완전히 떨어져 있다
 IoU = 0.5  절반쯤 겹친다
 IoU = 1.0  완전히 같은 박스다
```

이 프로젝트 구현은 [`cpu_yolov8_decode.hpp`](../01_src/ref/cpu_yolov8_decode.hpp)의
`iou_xyxy()`다.

### greedy NMS

**NMS**(Non-Maximum Suppression, 비최대 억제)는 겹친 박스 중 최고점만 남기는 알고리즘이다.
**greedy**(탐욕적)라는 말은 "매 단계에서 지금 제일 좋아 보이는 것을 고른다"는 뜻이다.

```
1. 모든 후보를 점수 높은 순으로 정렬한다.
2. 아직 안 죽은 것 중 점수가 가장 높은 것 하나를 고른다 → 채택.
3. 그것과 IoU가 임계값(이 모델은 0.7)을 넘는 나머지를 전부 죽인다(억제).
4. 남은 게 있으면 2로 돌아간다.
```

예시:

```
후보 (점수 순)         처리
A 0.91  ─────────────  채택 ✔
B 0.88  IoU(A,B)=0.82  0.7 초과 → 억제 ✘
C 0.85  IoU(A,C)=0.12  낮다 → 살아남음 → 다음 라운드에서 채택 ✔
D 0.60  IoU(C,D)=0.75  0.7 초과 → 억제 ✘
```

**클래스별로 따로 한다**(by class)는 점이 중요하다. 사람과 자전거가 겹쳐 있는 것은
정상이므로 서로 억제하면 안 된다. 이 프로젝트 함수 이름이
`cpu_nms_greedy_by_class()`인 이유다.

### GPU에서는 어떻게 하나 — 순차 알고리즘을 병렬로

greedy NMS는 본래 **순차적**이다. B가 억제되는지는 A가 살아남았는지에 달려 있고,
A가 살아남았는지는 그보다 앞선 후보들에 달려 있다. 그래서 GPU로 옮길 때는
"한 번에 한 후보씩 판정하되, **그 판정을 받은 뒤의 IoU 비교는 모두가 동시에**" 하는 구조를 쓴다.
TensorRT EfficientNMS의 방식이고([11장](11_tensorrt_efficient_nms.md) §5.4),
이 프로젝트의 [`efficient_nms.comp`](../02_shaders/efficient_nms.comp)가 그것을 Vulkan으로 옮긴 것이다.

```
워크그룹 1개(256 invocation) = 프레임 1장
1. 후보를 shared memory에 올려 (score, anchor_key) 순으로 정렬한다   (bitonic sort)
2. i = 0, 1, 2, ... 순서로:
     i를 맡은 invocation(리더)이 판정을 방송한다
       생존(1)  → 나머지 전원이 "살아 있는 같은 클래스의 뒤쪽 후보"와 IoU를 동시에 비교
       탈락(-1) → 아무도 계산하지 않는다
3. 생존자만 정렬 순서대로 모아 쓴다
```

결과는 CPU 함수와 **비트 단위로 같아야** 한다(`--nms verify`가 매 프레임 비교한다).
단 IoU가 임계값 0.7에 **아주 가까운**(±4e-6) 쌍은 CPU와 GPU의 부동소수 반올림 차이로 판정이
갈릴 수 있어서, 그런 쌍이 있는 프레임만 CPU 함수로 처리한다(보호대, guard band).

## 3.8 이 프로젝트에서는

여기부터는 이 프로젝트 고유의 사실이다. 전부 측정이나 소스로 확인된 것이고 링크를 달았다.

### (1) HEF가 실제로 내놓는 6개 텐서

정본은 [`10_paper/paper_ko.md`](../10_paper/paper_ko.md) §3.2 표다. 값이 바뀌면 그쪽을 고친다.

| 스트림 | 역할 | hw_shape | 바이트 | zero_point | scale |
|---|---|---|---:|---:|---|
| `conv74_178` | cls (P3) | 80×80×80 | 512,000 | 0 | 0.0034697596 |
| `conv71_178` | box (P3) | 80×80×64 | 409,600 | 88 | 0.1145507 |
| `conv90_178` | cls (P4) | 40×40×80 | 128,000 | 0 | 0.0037657837 |
| `conv87_178` | box (P4) | 40×40×64 | 102,400 | 74 | 0.079821944 |
| `conv105_178` | cls (P5) | 20×**24**×80 | 38,400 | 0 | 0.0038187786 |
| `conv102_178` | box (P5) | 20×**24**×64 | 30,720 | 81 | 0.074821874 |
| | **합계** | | **1,221,120** | | |

읽는 법:

- **스케일마다 텐서가 2개**다. `cls`는 클래스 점수(채널 80 = COCO 80개 클래스),
  `box`는 DFL 값(채널 64 = 4방향 × 16빈).
- 레이아웃은 전부 **UINT8 NHCW**다(§3.2). 즉 주소는
  `idx = ((h · C) + c) · W + w` 로 계산한다.
- 클래스 텐서의 zero_point가 전부 0인 것은 §3.8 (4)의 논거가 된다.

### (2) 수식의 단일 진실 원천 (single source of truth)

이 프로젝트에는 같은 디코드 수식이 **두 벌** 있다. CPU 기준 구현과 GPU 셰이더다.
두 벌이 어긋나면 결과가 달라지므로, 수식의 **원문을 한 곳에만 둔다**는 규칙을 세웠다.

> **원문은 [`01_src/ref/cpu_yolov8_decode.hpp`](../01_src/ref/cpu_yolov8_decode.hpp)
> 상단 주석 1)~7) 이다.**

- 1) NHCW 인덱싱 — 모든 텐서 접근은 `nhcw_index()` 하나만 쓴다
- 2) 역양자화 `value = (q − qp_zp) × qp_scale`
- 3) 클래스 점수와 threshold 비교
- 4) DFL softmax 기대값
- 5) letterbox 640×640 좌표
- 6) 원본 좌표 역변환
- 7) `anchor_key` (→ (6))

[`02_shaders/yolo_decode.comp`](../02_shaders/yolo_decode.comp) 머리 주석은
**"수식의 원문은 저 헤더다. 수식을 바꿀 때는 저 헤더를 먼저 고친다"** 라고 명시하고,
`yvo_postproc_probe --fixture` 가 두 구현을 자동으로 대조한다. 실측 결과는
5프레임에서 **CPU 115개 / GPU 115개 완전 일치, 점수 비트 불일치 0, 좌표 최대 오차
0.000122 px**였다([`07_results/gpu_postprocess/summary.md`](../07_results/gpu_postprocess/summary.md) P3 ①).
남은 오차는 `exp()` 구현 차이뿐이다.

### (3) P5 텐서의 폭 패딩 20 → 24

표를 다시 보면 P5만 `20×**24**×80`이다. 격자는 분명히 20×20인데 **메모리상의 폭이 24**다.
하드웨어가 폭을 4의 배수 등으로 맞추려고 **패딩(padding, 채워 넣기)** 한 결과다.

```
        w=0 .. w=19          w=20..23
 h=0  [ 유효한 값 20개 ][ 쓰레기 4개 ]
 h=1  [ 유효한 값 20개 ][ 쓰레기 4개 ]
 ...
       ↑ 주소 계산에는 24를 쓰고, 순회는 20까지만 한다
```

**두 숫자를 구분해서 써야 한다.**

- **주소 계산의 W** = `w_padded` = 24  (`idx = ((h·C)+c)·w_padded + w`)
- **순회 조건** = `w < 20`  (`grid_w`)

[`hailo_raw_runner.hpp`](../01_src/hailo/hailo_raw_runner.hpp)의 `RawTensorMeta`가 이 둘을
따로 들고 있고(`grid_w` / `w_padded`), 하나는 `shape.width`, 하나는 `hw_shape.width`에서 온다.

**왜 반드시 건너뛰어야 하는가**: `w = 20`이면 중심 x 좌표가 `(20+0.5)×32 = 656`이 되어
**640 입력 밖**이다. 게다가 패딩 값은 정의되지 않았으므로 우연히 큰 수가 들어 있으면
유령 검출이 생긴다.

> ⚠ **이 규칙의 증거는 약하다는 점을 그대로 적어 둔다.**
> 실측에서는 포함/제외가 같은 결과였는데, 이 영상에서 **P5 클래스 텐서의 패딩 열이 전부
> 0이었기 때문**이다(box 텐서는 최대 q=147까지 있었다)
> ([같은 summary](../07_results/gpu_postprocess/summary.md) "P1 ⑤는 약한 증거다").
> 다른 영상에서도 0이라는 보장은 없으므로 규칙은 유지한다.

### (4) 확정된 텐서 해석 4가지

모델이 내놓는 숫자를 어떻게 읽을지에 **문서로 답이 없는 변수가 4개** 있었다.
이 프로젝트는 40프레임에 대해 **2×2×2×2 = 16가지 조합을 전수 시도**해서 판정했다.
근거는 [`07_results/gpu_postprocess/summary.md`](../07_results/gpu_postprocess/summary.md) 결론 2와
그 증거 파일 `evidence/p1_combination_sweep.txt`다.
기준은 HailoRT 내장 NMS의 검출 81개와 얼마나 일치하는지(IoU ≥ 0.9)였다.

| 변수 | 확정값 | 어떻게 갈렸는가 |
|---|---|---|
| **DFL 채널 순서** | `ch = coord × reg_max + bin` (CoordMajor) | 반대로 하면 일치율 **0.0000**. 박스가 81개 → 462개로 폭발한다. 가장 확실하게 갈린다 |
| **sigmoid** | **적용하지 않는다** | 다시 적용하면 후보가 프레임당 15.1개 → **16800개**. 즉 전 앵커 통과 |
| **앵커당 클래스** | **다중 클래스** (threshold 넘는 것 전부) | 최고점 하나만(argmax) 쓰면 81개 중 1개를 놓쳐 0.9877. **2개 이상이 0.2를 넘는 앵커가 실재한다** |
| **threshold 비교** | `>=` | **원리적으로 구분 불가** (아래) |

**sigmoid를 적용하지 않는 이유**를 조금 더 풀어 둔다. **sigmoid**는 임의의 실수를 0~1로
눌러 확률로 만드는 함수다. 신경망의 클래스 출력은 보통 이 함수를 통과시켜야 한다.
그런데 이 모델의 클래스 텐서는 **이미 통과한 뒤의 값**이다. 근거 두 가지가
[`cpu_yolov8_decode.hpp`](../01_src/ref/cpu_yolov8_decode.hpp) 주석 2에 적혀 있다.

1. sigmoid 이전의 값(로짓)이라면 음수가 있어야 하므로 표현 범위의 최솟값이 음수여야 하는데,
   클래스 텐서는 `zero_point = 0`, 최솟값 0.0이다. box 텐서는 실제로 최솟값이 음수다.
2. 호스트가 sigmoid를 한 번 더 걸면 역양자화 값 0이 `sigmoid(0) = 0.5`가 되어
   threshold 0.2를 넘는다. 그러면 **8400 × 80개 앵커·클래스가 전부 통과**한다.
   실제 검출은 프레임당 5.21개다.

**`>` 와 `>=` 가 구분되지 않는 이유**도 재미있다. threshold 0.2를 정수 격자로 옮기면
`0.2 / qp_scale`이 P3에서 **57.6409**, P4에서 **53.1098**, P5에서 **52.3728** 이다.
**어느 스케일에서도 정수가 아니다** → 점수가 정확히 0.2인 경우가 원리적으로 존재하지 않는다
→ 두 비교가 같은 결과를 낸다. HailoRT 관례에 맞춰 `>=`를 기본값으로 뒀다.

### (5) 정수 도메인 사전필터 — 비용의 대부분을 없앤 최적화

**문제**: 프레임마다 훑어야 하는 값이 `8400 앵커 × (클래스 80 + DFL 64) ≈ 120만 개`다
([`07_results/nms_host_cost/summary.md`](../07_results/nms_host_cost/summary.md) §2).
살아남는 후보는 십여 개인데, **몇 개가 살아남든 훑는 비용은 똑같다.** 그래서 이 비용이
검출 수와 무관한 고정비다.

**순진한 방법**: 값마다 `(q − zp) × scale` 로 float을 만들고 `>= 0.2` 인지 본다.
클래스 값만 세어도 프레임당 672,000번의 float 곱셈과 비교다.

**최적화**: 부등식을 **정수 쪽으로 옮긴다.**

```
(q − zp) × scale  >=  thr          (클래스 텐서는 zp = 0)
         q × scale  >=  thr
                 q  >=  thr / scale            ← scale > 0 이므로 부등호 방향이 유지된다
                 q  >=  ceil(thr / scale)

  느슨하게:      q  >=  floor(thr / scale)  =  q_thr_low
```

`q_thr_low` 값은 **P3 = 57, P4 = 53, P5 = 52**다
([`07_results/gpu_postprocess/summary.md`](../07_results/gpu_postprocess/summary.md) 결론 3,
[`yolo_decode.comp`](../02_shaders/yolo_decode.comp)의 `q_thr_low` push constant).

**왜 성립하는가**가 핵심이다. 두 가지가 필요하다.

- **`scale > 0`** — 양수로 나누므로 부등호 방향이 뒤집히지 않는다. 양자화 스케일은
  정의상 양수이므로 항상 참이다.
- **`floor`를 써서 일부러 느슨하게 만든다** — `ceil` 대신 `floor`를 쓰면 경계에서
  한 칸을 더 통과시킨다. 이것은 **필요조건**(통과해야만 진짜 후보일 가능성이 있다)이지
  충분조건이 아니다. 통과한 소수의 값만 float으로 정확히 다시 검사하면 되므로
  **최종 결과는 정확히 같고**, 탈락시킨 값은 100% 확실하게 탈락이 맞다.

이 한 줄로 672,000회의 float 곱·비교가 **바이트 비교**로 바뀐다. GPU pass 1 비용의 거의
전부가 여기서 사라진다. 실측 중앙값은 **0.562 ms**다
([같은 summary](../07_results/gpu_postprocess/summary.md) P3 ⑥).

> **가설로만 남은 것**: 이 셰이더는 워크그룹 60 invocation(10×6)이 256 invocation보다 빠르고,
> 16의 배수인 32·64·128이 20·40·60·120보다 느리다. **이유는 설명하지 못했다.**
> "유효 invocation이 2,100개뿐이라 큰 워크그룹에서는 워크그룹 수가 8개까지 떨어져 코어에
> 덜 퍼진다"는 담당자 가설이 있지만 **측정치만이 근거인 미확정 가설**이다
> ([같은 summary](../07_results/gpu_postprocess/summary.md) 결론 9).
> 전처리 셰이더는 정반대로 invocation이 클수록 빨랐다.

### (6) `anchor_key` — GPU의 비결정성을 없앤 장치

**문제**: GPU에서 후보를 모을 때 `atomicAdd(det.count, 1)`로 출력 자리를 예약한다.
수천 개의 invocation이 동시에 달려들므로 **누가 먼저 자리를 잡는지는 실행할 때마다 다르다.**
같은 입력을 두 번 넣으면 후보의 **내용은 같지만 순서가 다르다.**

순서가 다르면 그 뒤 greedy NMS(§3.7)의 결과가 달라질 수 있다. 점수가 완전히 같은 두 박스가
있으면 먼저 온 쪽이 채택되기 때문이다. 즉 **같은 영상을 두 번 돌리면 결과가 미묘하게
달라진다.** 회귀 테스트가 불가능해진다.

**해결**: 후보마다 **그 후보가 어디서 왔는지를 유일하게 가리키는 정수**를 함께 들고 간다.

```
anchor_key = (scale_id << 21) | (h << 14) | (w << 7) | class

  비트:   [ scale_id ][   h   ][   w   ][ class ]
           2비트       7비트     7비트    7비트
           0..2        0..79     0..79    0..79
```

h, w, class가 전부 0~79라 각각 7비트에 들어가고 scale_id는 0~2다. 그래서 **서로 다른
(스케일, 행, 열, 클래스)는 절대로 같은 키를 갖지 않는다.**

그다음 정렬·억제·출력이 **`(score, anchor_key)` 전순서(total order)만** 쓰도록 한다.
"전순서"란 **임의의 두 원소에 대해 어느 쪽이 앞인지가 항상 유일하게 정해지는 순서**를
말한다. 점수가 같아도 `anchor_key`로 갈리므로 동점이 없다.

> GPU NMS([`efficient_nms.comp`](../02_shaders/efficient_nms.comp))의 정렬 키도 이 전순서다.
> int64가 없는 V3D에서는 score 비트와 `anchor_key`를 두 단계로 비교한다.
>
> 결과: 출력 순서가 실행마다 달라도 **정렬 후에는 항상 같은 배열**이 된다.
> 실측으로 **10회 반복 전부 바이트 단위 동일**이 확인됐다
> ([`07_results/gpu_postprocess/summary.md`](../07_results/gpu_postprocess/summary.md) P3 G6).
> 근거 코드는 [`cpu_yolov8_decode.hpp`](../01_src/ref/cpu_yolov8_decode.hpp) 주석 7이다.

### (7) 마지막 한 걸음 — 원본 좌표로 되돌리기

지금까지 나온 좌표는 **letterbox된 640×640 안의 좌표**다. 화면에 그리려면 원본
1920×1080 좌표로 돌려야 한다. letterbox는 비율을 유지한 채 축소하고 남는 부분을 회색으로
채우는 것이었으므로([01_big_picture.md](01_big_picture.md) §1.4 ②), 역변환은 단순하다.

```
x = clamp((x_640 − pad_x) / scale, 0, src_w)
y = clamp((y_640 − pad_y) / scale, 0, src_h)
```

한 가지 **의도된 차이**가 있다. 이 프로젝트는 **클램프를 NMS 이전에** 적용하고
HailoRT는 정규화 좌표로 NMS한 뒤 클램프한다. 균일 축소 + 평행이동은 IoU를 보존하므로
대부분 차이가 없고, **프레임 경계에 걸친 박스에서만** IoU가 미세하게 달라질 수 있다
([`cpu_yolov8_decode.hpp`](../01_src/ref/cpu_yolov8_decode.hpp) 주석 6).
이런 것을 **모르고 넘어가지 않고 적어 두는 것**이 이 프로젝트의 규율이다.

## 3.9 전체 흐름 한 장

```
NPU 원시 출력 6텐서 (UINT8 NHCW, 합계 1,221,120 B)
   │
   │  스케일별로 (cls, box) 한 쌍씩, 3번 반복
   ▼
① 정수 사전필터        q >= q_thr_low (57 / 53 / 52)        ← 여기서 99.9%가 탈락
   │                   float 곱셈 없이 바이트 비교만
   ▼
② 역양자화             score = (q − zp) × scale
   │                   sigmoid 적용 안 함
   ▼
③ threshold            score >= 0.2 인 클래스를 **전부** emit (다중 클래스)
   │
   ▼
④ DFL 디코드           v[16] 역양자화 → softmax 기대값 → 거리 4개
   │                   ch = coord·16 + bin
   ▼
⑤ letterbox 좌표       x1 = (w + 0.5 − d_left) · stride  ...
   │
   ▼
⑥ 원본 좌표 역변환     x = clamp((x_640 − pad_x)/scale, 0, 1920)
   │                   + anchor_key 부여
   ▼
   후보 ~16개 (약 1.6 KB)  ← 1.22 MB 가 여기서 1/800 로 줄었다
   │
   ▼
⑦ greedy NMS (클래스별, IoU 0.7)   ← GPU(efficient_nms.comp). 드문 경계 프레임만 CPU
   │
   ▼
   최종 검출 (프레임당 약 5개)
```

①~⑥은 GPU 셰이더([`yolo_decode.comp`](../02_shaders/yolo_decode.comp)),
⑦은 같은 커맨드 버퍼의 GPU 셰이더([`efficient_nms.comp`](../02_shaders/efficient_nms.comp))이고,
그 기준 구현은 CPU 함수([`cpu_nms_greedy_by_class`](../01_src/ref/cpu_yolov8_decode.hpp))다(`--nms cpu`로 그 함수를 쓸 수도 있다).
⑦을 한동안 CPU에 두었던 이유와 GPU로 옮긴 경위는
[05_vulkan_compute.md](05_vulkan_compute.md)와 [10_why_this_design.md](10_why_this_design.md)에서 다룬다.

## 3.10 자가 점검

**Q1. 같은 640×640 RGB 이미지를 NHWC로 저장한 것과 NHCW로 저장한 것은 바이트 수가 다른가?
다르다면 왜, 같다면 왜 구분해야 하는가?**

바이트 수는 **같다**(640 × 640 × 3 = 1,228,800 B). 값도 같다. **순서만** 다르다.
그런데 소비자가 요구하는 순서가 정해져 있어서 구분해야 한다. Hailo-8 장치는 NHCW를
요구하므로, NHWC로 넘기면 런타임이 CPU에서 전치해 주고 이 프로젝트에서는 그 비용이
프레임당 약 14 ms였다([`10_paper/paper_ko.md`](../10_paper/paper_ko.md) §4.3.2, CPU 17.6 → 3.5 ms).
게다가 잘못된 순서로 해석하면 결과가 완전히 망가진다.

**Q2. YOLO가 격자를 80×80 / 40×40 / 20×20 세 벌 만드는 이유는?**

격자 한 칸이 잘 볼 수 있는 물체 크기가 정해져 있기 때문이다. 촘촘한 P3(stride 8)는 작은
물체를, 성긴 P5(stride 32)는 큰 물체를 맡는다. 세 격자를 합치면 앵커가
`80² + 40² + 20² = 8400`개다(§3.4).

**Q3. DFL은 왜 거리 하나를 숫자 하나가 아니라 16개 값으로 답하게 하는가?
그 16개에서 최종 거리를 어떻게 얻는가?**

숫자 하나로는 **확신의 정도**를 표현할 수 없기 때문이다. 16개 빈에 실린 무게로 답하면
경계가 뚜렷할 때는 한 칸에 몰리고 흐릿할 때는 퍼진다. 최종 거리는 **softmax를 거친 확률의
기대값** `d = Σ b·e[b] / Σ e[b]` (`e[b] = exp(v[b] − max(v))`)다. 최댓값을 빼는 것은
역양자화 값이 최대 19.1까지 가서 `exp()`가 부풀기 때문이다
([`cpu_yolov8_decode.hpp`](../01_src/ref/cpu_yolov8_decode.hpp) 주석 4).

**Q4. `q >= floor(thr/scale)` 사전필터가 결과를 바꾸지 않는 이유는? 어떤 전제가 필요한가?**

전제는 **`scale > 0`** 이다. 양수로 나누므로 `(q−zp)·scale >= thr` 와 `q >= thr/scale + zp`가
동치다(클래스 텐서는 `zp = 0`). `ceil` 대신 `floor`를 써서 일부러 느슨하게 만들었으므로
이것은 **필요조건**이고, 탈락시킨 값은 확실히 탈락이 맞다. 통과한 소수만 float으로 다시
정확히 검사하므로 최종 결과는 같다. 값은 P3 57 / P4 53 / P5 52이고
프레임당 672,000회의 float 곱·비교가 바이트 비교로 바뀐다
([`07_results/gpu_postprocess/summary.md`](../07_results/gpu_postprocess/summary.md) 결론 3).

**Q5. GPU에서 `atomicAdd`로 후보를 모으면 순서가 실행마다 달라진다. 그런데도 결과가
매번 똑같으려면 무엇이 필요한가?**

**동점이 없는 전순서**가 필요하다. 이 프로젝트는 후보마다
`anchor_key = (scale_id << 21) | (h << 14) | (w << 7) | class`를 붙이고 정렬·억제·출력이
`(score, anchor_key)` 쌍만 보게 했다. 서로 다른 앵커·클래스는 절대 같은 키를 갖지 않으므로
점수가 같아도 순서가 유일하게 정해진다. 실측으로 10회 반복 전부 바이트 동일이 확인됐다
([같은 summary](../07_results/gpu_postprocess/summary.md) P3 G6).

**Q6. P5 텐서를 순회할 때 `w < 24`로 돌면 무슨 일이 생기는가?**

`w = 20..23`은 하드웨어 패딩 열이고 값이 정의돼 있지 않다. 그 칸에서 박스를 만들면
중심 x가 `(20+0.5) × 32 = 656`으로 **640 입력 바깥**이 되어 유령 검출이 생긴다.
주소 계산에는 `w_padded = 24`를 쓰되 **순회는 `w < 20`** 으로 해야 한다.
(다만 이 규칙을 뒷받침하는 실측 증거는 약하다 — 테스트 영상에서 P5 클래스 텐서의 패딩 열이
우연히 전부 0이었다. §3.8 (3) 참고.)

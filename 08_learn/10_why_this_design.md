## 사슬 1 — GPU 메모리에 캐시가 없다 → 셰이더가 NHCW로 직접 쓴다

### 배경지식

CPU에는 **캐시**가 있다. 메모리에서 한 번 읽은 것을 가까운 곳에 두고 재사용한다.
그런데 메모리를 CPU 말고 다른 장치도 만진다면, 캐시에 든 낡은 값과 메모리의 새 값이 어긋날 수 있다.
그래서 장치와 공유하는 메모리는 **캐시를 끄고(uncached) 매핑**하기도 한다.
(→ [06_zerocopy_dmabuf.md](06_zerocopy_dmabuf.md))

Vulkan에서는 이걸 **메모리 타입**으로 고른다. `HOST_CACHED` 가 있으면 캐시된 매핑을 쓸 수 있다.

### 관측

V3D GPU가 노출하는 메모리 타입은 `DEVICE_LOCAL | HOST_VISIBLE | HOST_COHERENT` **하나뿐이다.**
`HOST_CACHED` 가 **없다.** 즉 **GPU가 쓴 버퍼를 CPU가 캐시된 상태로 읽을 방법이 드라이버에 없다.**

실측하면 이렇게 나온다
([`pipeline_ffmpeg_vulkan_hailo/summary.md`](../07_results/pipeline_ffmpeg_vulkan_hailo/summary.md)):

| 접근 방식 | 1.2 MB 읽는 시간 | 속도 |
|---|---:|---|
| 순차 읽기 | 0.826 ms | **1.479 GB/s** |
| **3바이트 간격 읽기(stride-3)** | 약 14 ms(역산) / **12.69 ms(직접 측정)** | **약 0.088 / 0.097 GB/s** |
| 1바이트씩 **순차** 읽기 | 12.82 ms(직접 측정) | 0.096 GB/s |

> 순차 값에는 측정이 둘 있다 — 할당처를 나란히 잰 P2 프로브가 **1.479 GB/s**,
> 파이프라인 버퍼를 잰 `yvo_preproc_bench` 가 **약 1.41 GB/s** 다. 조건이 다르니 섞지 마라.
> 비교 맥락에서는 P2를 쓴다([`07_results/README.md`](../07_results/README.md) 2번).

**약 15~16배 차이 난다**(직접 측정 기준. 역산값 14 ms로는 17배). 그리고 이 제약은 **방향이 비대칭**이다 —
쓰기는 write-combine 버퍼링으로 빠르고, 읽기만 비싸다.

### 이게 왜 문제였나

YOLO 모델의 장치 입력 형식은 **NHCW** 인데, 처음에는 GPU 셰이더가 **NHWC** 로 출력하고
HailoRT가 CPU에서 변환하게 두었다. 그 변환이 **프레임당 약 14 ms**를 먹었다.

처음에는 "전치 연산이 원래 비싼가 보다"라고 생각했다. **아니었다.**
같은 전치를 평범한 `malloc` 버퍼에서 하면 약 1.2 ms다(2026-10-16 직접 측정 0.95 ms).

비쌌던 진짜 이유: HailoRT가 **V3D가 준 캐시 없는 메모리를 3바이트 간격으로 읽고 있었다.**
위 표의 stride-3 경로에 정확히 해당한다. 2026-10-16 직접 측정([`stride_read`](../07_results/gpu_postprocess/runs/stride_read/summary.md))으로 보면 1바이트씩 **순차로** 읽어도 같은 값이라,
비싼 것은 간격이 아니라 **캐시 없는 메모리를 바이트 단위로 읽는 것** 자체다(같은 전치가 malloc에서는 0.95 ms).

### 결정

**GPU 셰이더가 처음부터 NHCW로 쓴다.** CPU가 GPU 메모리를 읽을 일 자체를 없앤다.
[`sand_letterbox.comp`](../02_shaders/sand_letterbox.comp) 에 `kOutNhcw` 라는 스위치가 있고,
켜면 픽셀 계산은 그대로인 채 **쓰는 주소만** 바뀐다.

결과: **CPU 17.6 → 3.5 ms/프레임.** FPS는 51.55 → 51.63으로 거의 그대로다(병목이 NPU이므로).
검출 결과는 완전히 동일.

> 이 장의 CPU·e2e 수치는 따로 적지 않으면 **FFmpeg 자동 5스레드** 디코드 조건이고, GPU ms는 **V3D 960 MHz** 조건이다.
> 디코더 1스레드 기본값(2026-09-29) 뒤에는 이 쌍이 16.97 → 2.93 ms/프레임이다(b8, [`dec_threads`](../07_results/dec_threads/summary.md)).
> 차이(약 14 ms)와 결론은 그대로다.

### 일반화 — 이게 이 프로젝트 전체를 지배한다

> **이 파이프라인에서 GPU가 쓴 버퍼를 CPU로 훑는 설계는 겉보기보다 약 10배 비싸다.**
> 새 기능을 설계할 때 이것부터 따진다.

**근거**: [`07_results/pipeline_ffmpeg_vulkan_hailo/REPORT.md`](../07_results/pipeline_ffmpeg_vulkan_hailo/REPORT.md) §4.3

## 사슬 2 — 내장 NMS가 온칩이 아니다 → 원시 출력 + GPU 후처리

### 배경지식

YOLO의 원시 출력은 격자칸마다의 숫자 덩어리이고, 그걸 박스 목록으로 바꾸는 후처리가 필요하다.
(→ [03_yolo_tensor.md](03_yolo_tensor.md))

Hailo 모델 파일(HEF)에는 `yolov8_nms_postprocess` 라는 후처리가 들어 있어서,
쓰면 박스 목록이 바로 나온다. **편하다.** 그래서 처음에는 이걸 썼다.

### 관측

그런데 이 후처리가 **NPU 칩 위에서 도는 게 아니라 호스트 CPU에서 돌고 있었다.**
디버거로 확인했다([`nms_host_cost/summary.md`](../07_results/nms_host_cost/summary.md)).

더 이상한 것은 **비용이 검출 수와 무관한 고정비**라는 점이다:

| 조건 | 검출 수 | CPU 시간 |
|---|---:|---:|
| 점수 임계 0.2 | 2090 | 3.256 ms |
| 점수 임계 0.99 | **0** | 3.363 ms |

검출이 하나도 없어도 같은 시간이 든다. 정직한 범위로 **프레임당 2.2~3.2 ms**다.

### 결정적 논증

"그럼 원시 출력으로 바꾸자"는 자연스럽지만, 걱정이 하나 있다:
**원시 텐서는 크다. PCIe로 더 많이 보내야 하는 것 아닌가?** PCIe가 병목인데?

실제로 세어 보면 **아니다.**

```
지금 이미 일어나는 일:
  NPU  ──[ 원시 6텐서 1,221,120 B ]──▶  호스트 CPU  ──▶  160,320 B 박스 목록
       └──────── PCIe를 건넌다 ────────┘        └─ CPU에서 줄인다 ─┘
```

**원시 텐서는 이미 매 프레임 PCIe를 건너오고 있다.** 호스트가 받아서 줄이는 것뿐이다.
따라서 원시 출력으로 바꿔도 **PCIe 트래픽은 1바이트도 늘지 않는다.**

### 결정

원시 6텐서를 받아서 **GPU가 후보를 뽑고(`yolo_decode.comp`), CPU가 겹침만 정리한다.**

왜 NMS 전체를 GPU로 옮기지 않았나? 후보가 수십 개뿐이라 CPU 억제가 **3~11 마이크로초**밖에
안 걸리기 때문이다. 완전 GPU NMS는 **서두를 이유가 없다**고 판정했다.

결과([`raw_runner_backpressure/summary.md`](../07_results/raw_runner_backpressure/summary.md)):
CPU **2.921 → 1.122 ms/프레임**, FPS 차이 −0.03%(사실상 동일), 검출 3369 그대로.
`perf`로 보면 호스트 NMS 함수의 CPU 점유율이 **45.10% → 0건**이다.

**근거**: [`nms_host_cost/`](../07_results/nms_host_cost/summary.md),
[`gpu_postprocess/`](../07_results/gpu_postprocess/summary.md),
[`gpu_postproc_e2e/`](../07_results/gpu_postproc_e2e/summary.md)
(⛔ 마지막 문서의 FPS·지연 수치는 결함 상태 값이라 인용 금지 — 정확도와 perf 결과만 쓴다)

### 그 뒤 — 억제도 GPU로 (2026-09-22)

위 판정("서두를 이유가 없다")은 **비용** 기준이었다. 억제까지 GPU로 옮긴 것은 비용이 아니라
**구조** 때문이다. 억제가 디코드와 같은 커맨드 버퍼에 들어가면 CPU는 최종 검출만 읽는다.
그리고 결과가 오버레이 셰이더와 같은 형식(`YoloDetGpu`)으로 GPU 메모리에 남으므로,
호스트를 거치지 않고 오버레이로 바로 잇는 길이 열린다(아직 잇지 않았다).

- **설계**: TensorRT EfficientNMS의 Filter → Sort → 타일+상태 방송 → 결과 기록 구조를
  V3D에 옮겼다([11장](11_tensorrt_efficient_nms.md), [`efficient_nms.comp`](../02_shaders/efficient_nms.comp)).
  Filter는 `yolo_decode.comp`가 이미 하고 있었다.
- **의미론은 TRT가 아니라 이 저장소의 CPU 함수**다. IoU 0.7, 클래스별, 클래스당 100개,
  `(score, anchor_key)` 전순서를 지켜 **CPU 결과와 비트 단위로 같다**. 비트 일치를 보장할 수 없는
  프레임(후보 1024개 초과, IoU가 0.7 ± 4e-6 안)은 셰이더가 알리고 그 프레임만 CPU 함수로 처리한다.
- **아직 모르는 것**: 억제 한 번의 GPU 시간이 CPU 억제(수 µs)보다 **클 수 있다.** 이 교체는
  CPU 시간을 줄이려는 것이 아니다. 2026-10-08 정식 A/B([`gpu_nms_e2e`](../07_results/gpu_nms_e2e/summary.md), 표시 off)에서
  FPS·검출은 같고 CPU·e2e 차이는 실행 간 흔들림 안이었다(회귀 없음, 검출 바이트 동일).
  `efficient_nms`는 0.049~0.050 ms(1150 MHz, 폴백 0)로 CPU 억제(약 2 µs)보다 크다는 가설과 맞는다
  (먼저 [`dec_threads`](../07_results/dec_threads/summary.md) 부산물로 0.036~0.050 ms가 보였고, 정식 A/B가 이를 확인했다).
- **혼잡 장면에서는**([`nms_crowd_stress`](../07_results/nms_crowd_stress/summary.md), MOT20, 후보 약 11배)
  CPU 억제 원가가 약 2 µs에서 40~47 µs/f로 커져, gpu 쪽 CPU가 같은 세션에서 0.02~0.07 ms/f 낮아졌다(실행 간 범위는 일부 겹친다). 이득이 드러나기 시작한 것이다.
  FPS·검출 바이트는 그대로였다. 1024 초과 프레임을 CPU로 넘기는 비상구는 프레임당 약 0.8~1.5 ms로 처리량에 영향이 없다.
  디코딩 버퍼 4096 넘침(조용한 잘림)은 양자화 바닥에서도 최대 1925개라 이 HEF로는 닿지 않아 고치지 않고 남겼다(2026-10-08 결정).

## 사슬 3 — PCIe가 상한을 정한다 → 목표를 FPS가 아니라 CPU로 바꾼다

### 배경지식

NPU는 SoC 안이 아니라 **PCIe로 붙어 있는 별도 칩**이다.
PCIe는 세대(Gen2 / Gen3)와 레인 수(x1)로 대역폭이 정해진다. (→ [02_hardware.md](02_hardware.md))

### 관측

배치 크기 B에 대해 한 묶음 처리 시간을 재면 깔끔한 직선이 나온다(냉각 상태):

> **T(B) = 24.8 + 16.2 · B [ms]**

- `24.8 ms` = 묶음당 고정비
- `16.2 ms` = 프레임당 비용

**결정적 증거**: PCIe를 Gen2에서 Gen3로 바꿨더니 **두 항이 정확히 절반씩 줄었다**
(Gen2 `46 + 32.6·B` → Gen3 `25 + 16.2·B`).

계산 시간이 병목이라면 링크 속도를 바꿔도 안 변해야 한다. 두 항이 다 반으로 줄었다는 것은
**두 항이 모두 전송에 지배된다**는 뜻이다.

이 모델의 점근 상한은 `1 / 0.0162 ≈ 61.6 FPS`, 실측 상한은 **51.7 FPS**다.

### 결정 (둘)

**(1) 이 프로젝트는 FPS를 목표로 삼지 않는다.**
전처리·후처리·표시를 아무리 최적화해도 상한은 그대로다.
그래서 목표를 **CPU 부하 최소화**로 잡았고, 3.31 → 1.12 ms/프레임(표시 없이)을 달성했다.
(자동 5스레드·CPU NMS 조건. 1스레드·GPU NMS 기본값에서 같은 GPU 후처리 b2/s4 설정은 1.05 ms다, [`dec_threads`](../07_results/dec_threads/summary.md).)

**(2) 다중 스트림은 불가능하다 — 측정할 필요도 없다.**
1080p30 영상 두 개면 초당 60프레임이 필요한데 NPU 상한이 51.7이다.
그리고 **확보한 CPU 여유는 이 한계를 풀지 못한다** — 병목이 아닌 자원의 여유이기 때문이다.

> 이 판단이 중요하다. "CPU를 절반으로 줄였으니 스트림을 두 배로 돌릴 수 있겠지"는 틀렸다.
> **병목이 아닌 자원을 아무리 확보해도 병목은 그대로다.**

**근거**: [`npu_benchmark/summary.md`](../07_results/npu_benchmark/summary.md),
[`op_point/runs/latency_gen3_cooled/summary.md`](../07_results/op_point/runs/latency_gen3_cooled/summary.md),
[`op_point/summary.md`](../07_results/op_point/summary.md) §8.2

## 사슬 4 — 지연은 slots가, 처리량의 천장은 batch가 정한다

### 배경지식

NPU에 한 번에 여러 장을 묶어 보내는 것이 **batch**, 동시에 몇 장을 파이프라인에 올려 두는지가
**slots**다. 둘 다 "동시에 처리하는 양"을 늘리는 레버처럼 보인다. (→ [04_npu_hailort.md](04_npu_hailort.md))

### 관측

여섯 설정을 실측했다([`op_point/summary.md`](../07_results/op_point/summary.md)):

| 설정 | FPS | e2e 지연(mean) | 지연 ÷ 프레임 주기 |
|---|---:|---:|---:|
| b2/s2 | 24.41 | 122.5 ms | **1.94** |
| b2/s4 | 34.97 | 142.2 ms | **3.90** |
| b8/s8 | 44.55 | 199.1 ms | **7.69** |
| b8/s16 | 51.49 | 325.3 ms | **15.53** |

맨 오른쪽 열을 보라. **`slots` 값과 거의 같다.**
(자동 5스레드 조건. b8/s16은 `dec_threads`의 같은 회차에서 자동 327.4 → 1스레드 318.6 ms로 약 9 ms 짧고, 비율은 그대로다 — [`dec_threads`](../07_results/dec_threads/summary.md).)

> **지연 ≈ slots × 프레임 주기**

그리고 **같은 slots에서 batch를 바꾸면 차이가 0.25%뿐이다**
(`b4/s8` 44.44 vs `b8/s8` 44.55). 사전에 세웠던 "b8/s8이 b4/s8보다 낫다"는 가설은 **기각됐다.**

**재측정이 해석을 바꿨다(2026-10-08, 15설정 격자 — [`grid_gpu_postproc`](../07_results/op_point/runs/grid_gpu_postproc/summary.md)).**
처리량은 `min(배치 천장 B / T(B), 슬롯 제약)`이고, 천장은 **slots = 2B**에서 닿는다(네 batch 모두 0.6% 안).
`b8/s8`은 slots = B라 슬롯 제약에 걸려 batch 4의 천장과 우연히 겹친 것이다. batch가 무의미한 게 아니었다.

### 결정

**batch로 필요한 처리량 천장을 고르고, slots는 2 × batch로 둔다.** 그보다 큰 slots는 지연만 늘린다.
30 fps 실시간 표시용 최종 운용점은 **`--batch 2 --slots 4`** 다.
지연만 최소로 하는 운용점(O2)은 **`--batch 1 --slots 1 --input-pace source --input-queue 1`**(표시 off)이다 —
입력이 소스 시각에 도착하고 NPU 가 못 따라가는 약 19%는 버린다. 도착 기준 평균 58.4 ms([`code_2f2d3d0`](../07_results/input_pacing/runs/code_2f2d3d0/summary.md), 2026-10-16 재측정. 운용점은 사용자 결정 2026-10-12).
페이싱 없는 b1/s1 의 79 ms 중 약 42 ms 는 파일을 앞서 읽어 생긴 슬롯 대기였다.
화면까지는 Vulkan 합성 표시로 도착 → 화면 평균 70.2 ms 다(사용자 결정 2026-10-12, 값은 2026-10-16 재측정 [`code_2f2d3d0_display_on`](../07_results/input_pacing/runs/code_2f2d3d0_display_on/summary.md)). HVS 평면 백엔드는 slots 1 에서 교착해 쓰지 않는다.

부수적으로 알아낸 것: `--gpu-depth`는 **지연 레버가 아니다**(1 vs 3에서 142.06 vs 142.17 ms).

### 여기서 얻을 교훈

가설을 세우고 측정해서 **기각했다는 것**이 중요하다.
기각된 가설의 출처는 `yvo_hailo_selftest`라는 단독 도구의 수치였는데,
**그 수치가 파이프라인 수준으로 이전되지 않았다.** 그래서 이제 그 도구 수치로 운용점을 논하지 않는다.

**근거**: [`op_point/summary.md`](../07_results/op_point/summary.md) §8.2, [`grid_gpu_postproc`](../07_results/op_point/runs/grid_gpu_postproc/summary.md) §3·§5

## 사슬 5 — 타일 기반 GPU → 오버레이를 컴퓨트로 그린다

### 배경지식

박스와 글자를 화면에 그리는 일은 원래 **그래픽스 파이프라인**(삼각형을 래스터화하는 GPU의 본업)이
할 일이다. 그게 정석이다.

그런데 V3D는 **타일 기반 렌더러(tile-based renderer)** 다.
화면을 작은 타일로 쪼개서 타일 하나씩 칩 안의 작은 메모리에 올려놓고 그린 뒤 메모리로 되쓴다.
모바일·임베디드 GPU에서 흔한 방식으로, 메모리 대역폭을 아끼려는 설계다.

### 관측

문제는 **이미 그려진 그림 위에 덧그릴 때** 생긴다.
타일 기반 렌더러는 렌더패스를 열면 **프레임버퍼 전체를 칩 안으로 로드하고 끝나면 전부 되쓴다**
(load / store). 박스 몇 개만 얹으려는데 1920×1080 전체가 왕복한다.

측정하면 약 3.6 ms가 든다 — 박스를 그리는 비용이 아니라 **왕복 비용**이다.

### 결정

**그래픽스 파이프라인을 쓰지 않는다.** 오버레이를
[`overlay_boxes.comp`](../02_shaders/overlay_boxes.comp) 라는 **컴퓨트 셰이더**로 만들어서,
바꿔야 할 픽셀에만 직접 쓴다.

구조도 재미있다: **검출 하나 = 워크그룹 하나**이고, 검출 개수는 GPU가 정하므로
호스트가 개수를 모른 채 `vkCmdDispatchIndirect` 로 "버퍼에 적힌 만큼 돌려라"고 시킨다.

결과: 검출 5개 0.151 ms / 40개 0.555 ms / 80개 1.023 ms.
최종 파이프라인의 실측은 **0.128 ms**다(V3D 960 MHz. 1150 MHz 현재 기본값에서는 0.119 ms, [`v3d1150_syscpu_20261016`](../07_results/display_e2e/runs/v3d1150_syscpu_20261016/summary.md)의 `disp_source`).

**근거**: [`display_vulkan_hdmi/summary.md`](../07_results/display_vulkan_hdmi/summary.md),
[`10_paper/paper_ko.md`](../10_paper/paper_ko.md) §4.5

## 사슬 6 — 화면을 작게 만들면 오히려 느려진다

### 배경지식

"픽셀이 적으면 빠르다"는 상식이다. 1280×720은 1920×1080의 44%밖에 안 되니 더 빨라야 한다.

### 관측

**반대로 나왔다**([`display_vulkan_hdmi/summary.md`](../07_results/display_vulkan_hdmi/summary.md)):

| 해상도 | 표시 변환 시간 |
|---|---:|
| **1920×1080 (1:1)** | **4.23 ms** |
| 1280×720 | 5.27 ms |
| 1600×900 | 7.64 ms |

(V3D 960 MHz 조건. 1150 MHz에서는 다시 재지 않았다.)

### 왜

해상도가 입력과 같으면 **1:1 경로**로 간다 — 픽셀 하나를 픽셀 하나로 옮기기만 한다.
해상도가 다르면 **스케일 경로**로 가고, 픽셀마다 주변 4개를 읽어 섞는 보간(bilinear)을 한다.

픽셀당 비용이 **2.04 ns → 5.72 ns**(720p 기준)로 2.8배가 된다. 픽셀 수가 44%로 줄어도 픽셀당 2.8배면 진다.

### 결정

**1920×1080 1:1을 기본으로 한다.**

그리고 여기서 **함정**이 하나 나온다. 창 모드로 띄우면 창 관리자가 창 높이를 1080이 아니라
1044 같은 값으로 잡고, 그러면 **조용히 스케일 경로로 샌다.** 에러도 경고도 없이 2.6배 느려진다.

그래서 `--display-fullscreen` 이 **측정과 운용 양쪽에서 필수**다.

**근거**: [`display_vulkan_hdmi/summary.md`](../07_results/display_vulkan_hdmi/summary.md)

### 후기 (2026-09-22) — 이 사슬의 적용 범위

이 사슬은 **V3D가 표시 변환을 하는 경로**(`--display-backend wayland`, 기본)의 이야기다.
이후 두 번째 표시 방식인 HVS 평면 스캔아웃(`wayland-planes` / `kms`)을 만들었다. 이 방식은 디코더 버퍼를 변환 없이
디스플레이 컨트롤러 평면에 올리고, 스케일과 YUV→RGB 를 HVS 하드웨어가 스캔아웃 중에 한다.
그러면 "1:1 경로 대 스케일 경로"라는 갈림 자체가 없다. 정식 측정(2026-10-08)에서 이 경로는 CPU 와 V3D 를 줄이지만
지연은 같고 슬롯을 6개로 늘려야 해서, 기본값과 이 사슬의 결정은 그대로 둔다 → [07장](07_video_display.md) §7.12.

## 사슬 7 — ISP는 더 빨랐지만 쓰지 않는다

### 배경지식

이 SoC에는 **ISP**(PiSP Back End)라는, 원래 카메라 영상 보정용 하드웨어 블록이 있다.
크기 변환도 할 수 있다. 통념은 "Pi 5의 ISP는 카메라 센서 raw 데이터 전용이라 영상엔 못 쓴다"였다.

### 관측 1 — 통념이 틀렸다

ISP 입력이 **디코더 출력 형식(SAND128 NV12)을 그대로 받는다.**
즉 **디코더 → ISP → NPU 전 구간 zero-copy가 성립한다.**

그리고 빨랐다: 전처리 시간 **ISP 1.594 ms vs GPU 2.081 ms (−23%)**,
게다가 **V3D GPU 점유가 완전히 0**이 된다.

### 관측 2 — 그런데 검출이 달라졌다

| | 총 검출 수 |
|---|---:|
| 현행 GPU 전처리 | 9457 |
| ISP 전처리 | **9237 (−2.33%)** |

원인을 파고들었더니 **박스 정확도 문제가 아니었다.**
차이 나는 검출들의 점수 중앙값이 0.229로, 운용 임계값 0.2 **바로 위**에 몰려 있었다.
즉 **경계선에 걸친 검출들이 임계값을 넘느냐 마느냐가 갈린 것**이다.
점수 0.4 이상에서는 두 경로가 99.5% 이상 일치한다.

리샘플 필터를 바꿔 봐도 개선되지 않았다(오히려 더 나빠졌다).

### 결정

**보류한다.** 정답 라벨이 없어서 9237과 9457 중 어느 쪽이 맞는지 **판정할 수 없기 때문이다.**

대신 **재검토 조건 세 개**를 명시해 두었다:
1. 운용 점수 임계값이 0.4 이상이 되면
2. V3D GPU가 실제로 부족해지면
3. **CSI 카메라 입력으로 가면**

코드는 [`01_src/isp/`](../01_src/isp/) 에 남아 있고, 본체와 격리돼 있어서 되살리기 쉽다.

### 여기서 얻을 교훈

> **"빠르다"는 통합의 충분조건이 아니다.**
> 그리고 **"어느 쪽이 맞는지 모르겠다"는 정직한 결론이다** —
> 확인되지 않은 상태에서 더 빠른 쪽을 고르는 게 더 위험하다.

**근거**: [`isp_resize/summary.md`](../07_results/isp_resize/summary.md)

## 사슬 8 — 조용히 절반으로 도는 버그

### 관측

GPU 후처리를 넣었더니 `b2/s4` 설정에서 FPS가 **24.48**이 나왔다. 기존 경로는 34.96이었다.
"GPU 후처리가 느린가?" 싶었지만 **에러는 없었다. 결과도 정확했다.**

### 원인

`in-flight`(동시에 NPU에 걸려 있는 프레임 수)를 세어 보니 **슬롯 수의 절반**이었다.

코드가 `increase_ongoing_callbacks()` 를 직접 호출하고 있었는데,
**`infer_async()` 가 내부에서 이미 같은 계수를 올리고 있었다.**
한 프레임이 두 번 세어지니 백프레셔가 절반에서 걸렸다.

### 결정

수동 호출을 제거했다. 결과: `b2/s4` **24.48 → 34.96 FPS (+42.8%)**,
기존 호스트 경로 대비 −0.03%로 사실상 동일.

### 여기서 얻을 교훈

이 버그의 성질을 보자:

- 에러 없음 ✓
- 결과 정확함 ✓
- **성능만 절반** ✗

[08_method.md](08_method.md)에서 본 주제가 여기 또 나온다:
**조용히 틀린 값을 만드는 문제가 에러를 내는 문제보다 위험하다.**

이걸 잡을 수 있었던 이유는 파이프라인이 `in-flight` 를 **계측해서 CSV에 내고 있었기 때문**이다.
계측하지 않는 값은 틀려도 모른다.

> 같은 성질의 함정이 이 프로젝트에 여럿 있다:
> 디코더가 13프레임 이상 붙잡으면 **에러 없이 정지**,
> `infer_async`에 틀린 크기를 주면 **`HAILO_SUCCESS`를 반환하고 콜백 0회**,
> 창 모드가 **경고 없이 2.6배 느려짐**.
> 그래서 이 프로젝트는 `held_frames_max`, `slot timeout`, `in-flight`, `검출 수` 같은
> **"이상하면 드러날 값"을 늘 기록한다.**

**근거**: [`raw_runner_backpressure/summary.md`](../07_results/raw_runner_backpressure/summary.md)

## 사슬 9 — V3D에는 비디오 엔진도 64비트 정수도 없다 → HW 디코더 + int32 셰이더

### 관측

- V3DV에는 Vulkan Video 확장(`VK_KHR_video_*`)이 하나도 없다. V3D는 3D·컴퓨트 GPU이고, HEVC 회로는 별도의 V4L2 장치다.
- 전용 엔진 없이 compute 셰이더로 푸는 FFmpeg 8.1.3의 Vulkan 코덱(FFv1·ProRes·DPX)을 빌드해 V3D에서 돌려 봤다.
  **모두 실패했다.** 셰이더가 쓰는 `Int64`, 포맷 없는 storage image 쓰기, runtime descriptor array를 V3D가 지원하지 않는다.
  증상은 셰이더 컴파일러 abort, 파이프라인 생성이 끝나지 않음, 그리고 **에러 없는 틀린 출력**이었다.
- 같은 셰이더가 llvmpipe(CPU Vulkan)에서는 맞게 돌지만 CPU 디코더보다 12~170배 느렸다. 돌더라도 이득이 없다.
- HEVC 자체도 GPU에 맞지 않는다. CABAC 엔트로피 디코드는 완전 직렬이고, 인트라 예측은 이웃 블록에 의존한다.

### 결정

**디코드는 전용 HW 디코더(V4L2, DRM_PRIME)에 맡기고, V3D는 자체 int32 셰이더로 전·후처리만 한다.**
지금 구조가 이 보드에서 성립하는 유일한 분업이다. 자체 셰이더를 쓸 때는 64비트 정수와 포맷 없는 image store를 피한다.

**근거**: [`vulkan_compute_codecs/summary.md`](../07_results/vulkan_compute_codecs/summary.md), [05장](05_vulkan_compute.md) §5.9

## 사슬 10 — 디코드 비용을 정하는 것은 프레임워크가 아니라 복사와 스레딩이다

### 관측

- rpt3 GStreamer는 같은 HW 디코더로 32.7 FPS / CPU 30.6 ms였다. 원인은 1080p 크롭 창 버그로 생긴 CPU 복사였고,
  rpt4에서 복사가 사라지자 381.5 FPS / 0.24 ms가 됐다([`runs/gst_rpt4`](../07_results/decode_benchmark/runs/gst_rpt4/summary.md)).
- ffmpeg CLI의 2.0 ms/frame도 대부분 CPU 내려받기였다. DRM_PRIME을 유지하면 0.55 ms다([`runs/ffmpeg_outfmt`](../07_results/decode_benchmark/runs/ffmpeg_outfmt/summary.md)).
- rpt4 GStreamer 연구 경로(`yvo_gst_pipeline`)는 앱과 검출이 바이트 동일, FPS가 같았고 CPU는 약 6% 낮았다.
  그 차이는 앱의 **FFmpeg 프레임 스레드** 비용이었다([`gst_pipeline`](../07_results/gst_pipeline/summary.md), [`runs/perf_dec_threads`](../07_results/gst_pipeline/runs/perf_dec_threads/summary.md)).
- 프레임 스레드를 1개로 줄이면 b8에서 CPU −14%, e2e −8.8 ms였다. 디코드 처리량(1스레드 약 266 FPS)은 NPU 상한(51.7)보다 훨씬 높다
  ([`dec_threads`](../07_results/dec_threads/summary.md)).

### 결정

- 앱의 디코더 프레임 스레드 기본값을 **1**로 바꿨다(`YVO_DEC_THREADS=0`이면 자동). 대가는 표시 on에서 앱 내부 e2e p90 +1.9 ms다.
- 앱은 libavcodec을 계속 쓴다. 이유는 이제 성능이 아니라 **패키지 버전에 덜 민감하다는 것**이다.

### 여기서 얻을 교훈

사슬 3과 같은 모양이다. **병목이 아닌 단계(디코드)에 병렬성을 주면 이득 없이 비용만 는다.**

## 아직 열려 있는 질문

여기서부터는 **아무도 모른다.** 이걸 숨기지 않고 적어 두는 것이 이 프로젝트의 방식이다.

### 1. 연속 운용 발열 — 일부 닫힘

2026-10-11 의 40분 측정([`thermal_soak`](../07_results/thermal_soak/summary.md))이 답했다. Hailo 칩은 약 104 °C 부터 클럭이 단계적으로 내려가고 약 120 °C 에서 멈춘다.
최종 운용점 `b2/s4` 는 평형 34.25~34.75 FPS 로 **지속 가능**(30 fps 대비 최저 +14%), `b8/s16` 은 추가 냉각 없이 약 5분에 정지한다.
**남은 것**: 중간 운용점, 냉각 장치, 최소 지연 운용점(b1 은 클럭이 내려가면 버림률이 늘 수 있다).

### 2. CSI 카메라 입력

디코더가 [`ffmpeg_drm_decoder.cpp:166`](../01_src/decode/ffmpeg_drm_decoder.cpp)
에서 **HEVC 파일만** 받는다. 카메라로 가면 사슬 7의 ISP 재검토 조건도 함께 열린다.
프레임이 소스 시각에 도착하는 상황은 입력 페이싱으로 모사해 쟀다([`input_pacing`](../07_results/input_pacing/summary.md)) — 실제 센서의 촬영 시각·ISP 지연은 미측정이다.

### 3. 워크그룹 최적값의 이유

`sand_letterbox` 는 256 invocation이 최적인데 `yolo_decode` 는 60(10×6)이 더 빠르다.
`display_convert` 는 세로로 긴 3×85 타일이 16×16보다 1.83배 빠르다.
**둘 다 측정값만 있고 이유는 미확정 가설이다.**

### 4. V3D 쪽 캐시 일관성 기제

Hailo 쪽은 드라이버가 캐시를 관리한다는 것을 `perf`로 확인했다.
V3D 쪽은 프레임마다 매핑을 다시 하지 않는데도 데이터 오염이 관측되지 않는다 —
**캐시가 이미 비워져서인지 하드웨어가 감시(snooping)해서인지 가르지 못했다.**
결정적 실험에 root 권한이 필요하다.

### 5. `pace=asap`의 GPU timestamp 평균 왜곡

V3D가 커맨드 버퍼를 합치면서 한쪽 구간이 0에 가깝게 잡히는 것으로 **추정하지만 미확인**이다.
그래서 해당 조건의 **평균값은 인용 금지**이고 중앙값만 쓴다.

### 6. HVS 평면 표시가 실제로 얼마나 이득인가

`wayland-planes` / `kms` 는 V3D 표시 변환을 없애고 HVS 가 변환·블렌딩한다. → **2026-10-08 정식 측정으로 답이 나왔다**
([`display_planes_e2e/`](../07_results/display_planes_e2e/summary.md)): CPU −0.44 ms/f(−20%), V3D −72% 이고 **지연 이득은 없다**.
KMS 와 컴포지터 경유도 같다(glass 중앙 99.85 대 99.93 ms — 프로브 메모가 본 약 1 vblank 차이는 파이프라인 조건에서는 보이지 않았다).
대신 평면 경로는 버퍼를 오래 쥐어 슬롯 6이 필요하다는 새 사실이 나왔다 — glass-to-glass 가 슬롯 대기를 못 보는 탓에 처음엔 가려져 있었다.
남은 것은 소스 페이싱에서 프레임의 약 25~27%가 한 vblank 늦는 표시 박자 문제다.

**전체 목록의 정본은 [`07_results/README.md`](../07_results/README.md#아직-열려-있는-것) 다**(22항목).
위 여섯은 그중 이 챕터의 사슬과 직접 이어지는 것만 고른 것이다.

## 자가 점검

**Q1. 전처리를 GPU로 옮겨서 얻은 것은 FPS인가 CPU인가? 왜?**

CPU다. 병목이 PCIe/NPU이므로 병목이 아닌 단계를 최적화해도 FPS는 안 오른다(51.55 → 51.63).
실제로 얻은 것은 CPU 17.6 → 3.5 ms/프레임이다.

**Q2. 원시 출력으로 바꾸면 PCIe 트래픽이 늘어나는가?**

늘지 않는다. 원시 6텐서 1,221,120 B는 **이미 매 프레임 PCIe를 건너오고 있었다.**
호스트 CPU가 그걸 받아서 160,320 B로 줄이고 있었을 뿐이다.

**Q3. CPU를 절반으로 줄였으니 스트림을 두 개 돌릴 수 있는가?**

없다. 병목이 NPU(51.7 FPS 상한)인데 1080p30 두 개면 60 FPS가 필요하다.
**병목이 아닌 자원을 확보해도 병목은 그대로다.**

**Q4. ISP 전처리가 23% 빠른데 왜 안 쓰는가?**

검출이 9457 → 9237(−2.33%)로 줄었고, 정답 라벨이 없어 **어느 쪽이 맞는지 판정할 수 없기** 때문이다.
차이는 박스 정확도가 아니라 점수 임계값 0.2 부근 경계 검출에서 났다. 재검토 조건 3개를 명시해 두었다.

**Q5. 화면 해상도를 낮추면 왜 느려지는가?**

해상도가 입력과 같으면 1:1 경로(픽셀당 2.04 ns), 다르면 보간이 들어간 스케일 경로로 간다
(720p 5.72 / 900p 5.31 ns/px). 픽셀 수가 44%로 줄어도 픽셀당 2.8배면 전체는 더 비싸다.
창 모드에서 **경고 없이** 이 경로로 새기 때문에 `--display-fullscreen`이 필수다.

**Q6. 이 프로젝트에서 가장 위험한 종류의 버그는 무엇인가?**

**에러를 내지 않고 조용히 틀리는 것**이다. 백프레셔 이중 계수(성능만 절반),
창 모드 스케일 경로(2.6배), 디코더 13프레임 정지(에러 없음),
틀린 크기에 `HAILO_SUCCESS` 반환 후 콜백 0회 — 전부 같은 성질이다.
대응책은 **이상하면 드러날 값을 늘 계측해 기록하는 것**이다.

## 1. 제목
- 제목: NPU 기반 YOLO 추론에서 호스트 CPU 최소화
- 부제: 최저 지연 운용을 기준으로
- 영문 부제(작게): Minimizing Host CPU Load in NPU-Based YOLO Inference
- 발표자·소속·날짜: `발표자 (작성 필요)` 자리 표시 — 의도한 빈칸이다
- 노트: 오늘은 NPU가 추론을 맡은 뒤에도 CPU에 남는 일을 어떻게 걷어냈는지, 지연이 가장 짧은 운용 방식을 기준으로 말씀드린다.

## 2. 목차 (2026-10-27 추가)
- 항목 4개(섹션과 맞춘다): 1 문제와 대상 시스템(3~5) · 2 CPU 최소화 기술 ①~⑤(6~10) · 3 결과(11) · 4 결론(12)
- 시각 요소: 번호 원 + 항목, 섹션 색 체계와 맞춤. 수치 없음
- 노트: 먼저 문제와 대상을 보고, 다섯 가지 기술을 차례로 설명한 뒤, 결과와 결론으로 마무리한다.

## 3. 문제 — 추론만 NPU로 옮겨도 CPU는 바쁘다
- 한 프레임의 흐름: 디코드 → 크기·색·형식 변환 → 추론 → 결과 해석(박스 복원·NMS) → 표시
- 추론만 NPU가 맡으면 나머지는 CPU가 하며, 프레임마다 수 MB를 읽고 쓴다
- 출발점: 배치 1에서 응용 CPU **17.6 ms/프레임** (한 코어의 40% 이상)
- 스마트폰·서버에서도 추론 밖 전·후처리와 데이터 이동이 종단간 성능을 좌우한다는 보고가 있다 [1][2]
- 시각 요소: 5단계 흐름(아이콘 또는 도형), "추론"만 NPU 색, 나머지는 CPU 색. 큰 숫자 17.6 ms 강조
- 노트: 목표는 CPU 개입 최소화, 단 처리량이 아니라 최저 지연 운용에서.

## 4. 대상 시스템과 운용 기준
- 표 또는 카드 4개:
  - 보드: Raspberry Pi Compute Module 5 [3]
  - NPU: Hailo-8 (PCIe), 런타임 HailoRT 4.24.0 [4]
  - 모델: YOLO11m [5]
  - 입력: HEVC 영상 (SoC 하드웨어 디코더)
- 운용 기준: 처리량(FPS)이 아니라 **최저 지연**
- 노트: 같은 계열 구성의 선행 사례가 있다 [6][7].

## 5. 전체 구조 — 데이터는 하드웨어끼리, CPU는 지휘만
- 그림: `../figures/fig10_brief_cpu_offload.png` (원고 그림 1). 슬라이드 폭 대부분을 쓴다
- 캡션: 굵은 실선 = dma-buf로 복사 없이 넘기는 데이터, 가는 실선 = CPU를 거치는 작은 데이터, 점선 = CPU 제어. ①~⑤ = 다섯 기술
- 노트: 다섯 기술 — ① 하드웨어 디코더와 제로 카피 ② NPU 형식을 GPU가 직접 생성 ③ 결과 해석도 GPU ④ 최저 지연 운용 ⑤ CPU는 지휘만.

## 6. ① 하드웨어 디코더 + 제로 카피(dma-buf)
- HEVC 하드웨어 디코더(FFmpeg 하드웨어 경로 [9]), 출력은 dma-buf로 GPU에 바로 넘김 [8]
- 시각 요소 (2026-10-27 개정): **큰 숫자 카드 대신 네이티브 가로 막대 차트 2개**를 나란히 둔다. 값은 모두 1080p HEVC 1,816프레임, 디코드만, 3회 중앙값의 프레임당 CPU 시간(ms)이다.
  - **(a) 소프트웨어 대 하드웨어** (축 0부터, 선형):
    - 소프트웨어 디코드 (avdec_h265, 자동 스레드): 31.8
    - 하드웨어 디코드 + dma-buf (응용, libavcodec DRM_PRIME): 0.23~0.28
    - 하드웨어 막대가 거의 보이지 않는 것 자체가 메시지다. 라벨로 값을 꼭 보이게 한다
  - **(b) 하드웨어 디코드의 출력 경로별 (확대)** (축 0부터, 선형, 0~2.5 정도):
    - CPU 메모리로 내려받음 (ffmpeg 명령행, 출력 형식 미지정 → yuv420p): 2.02
    - dma-buf 유지 (ffmpeg 명령행, DRM_PRIME): 0.55
    - dma-buf 유지 (응용, libavcodec DRM_PRIME): 0.23~0.28
  - **0.23~0.28은 범위값이다.** 막대 하나로 그리지 않는다. 0.23까지 진한 구간 + 0.23~0.28 옅은 구간(누적 막대)으로 그리고, 라벨은 "0.23~0.28"로 직접 단다. 중간값을 만들지 않는다
  - 강조색은 dma-buf(복사 없는) 경로에, 회색은 소프트웨어·CPU 내려받기 경로에
- 한 줄 메시지(차트 위나 아래): 같은 하드웨어 디코드라도 **CPU로 내려받으면 약 3.6배**(명령행 기준 2.02 대 0.55 ms) — 비용은 디코드가 아니라 복사
- 각주(작게, 필수): (a)의 소프트웨어 값은 GStreamer avdec_h265 측정(2026-09-20), 하드웨어 값은 ffmpeg 명령행·응용 측정(2026-09-29 이후)으로 측정 날짜·도구가 다르다. 모두 1080p HEVC, 디코드만, 3회 중앙값
- 노트: 소프트웨어 디코드는 프레임당 약 32 ms로 한 코어를 거의 다 쓴다. 하드웨어 디코더를 쓰고 출력을 dma-buf로 그대로 넘기면 0.23~0.28 ms다. 오른쪽은 같은 하드웨어 디코드에서 출력을 CPU로 내려받기만 해도 약 3.6배 비싸진다는 것 — CPU 비용의 원인이 복사라는 증거다.

## 7. ② NPU가 원하는 형식(NHCW)을 GPU가 바로 만든다
- NPU는 칩 내부 배치 NHCW를 쓴다. NHWC로 넘기면 런타임이 CPU에서 변환한다
- 원인은 연산이 아니라 **캐시되지 않는 GPU 메모리를 CPU가 바이트 단위로 읽는 것**
  - 같은 전치 루프 단독: 일반 메모리 0.95 ms, GPU 메모리 12.7 ms
- 해법: Vulkan 전처리 셰이더 [10]가 GPU(V3D [11])에서 처음부터 NHCW로 쓴다
- 결과: 배치 1 응용 CPU **17.6 → 3.3 ms/프레임**
- 시각 요소: 네이티브 막대 차트 (17.6 vs 3.3, 단위 ms/프레임), 데이터 라벨 표시
- 각주(작게): GPU 960 MHz · 디코더 자동 스레드 · 배치 1/슬롯 2 조건

## 8. ③ 결과 해석(박스 복원 + NMS)도 GPU로
- NPU 원시 출력도 dma-buf로 GPU에 넘기고, CPU는 최종 검출 몇 개만 받는다
- 결과: 응용 CPU **3.25 → 0.94 ms/프레임**, 지연은 그대로 (79.1 대 79.2 ms)
- 정확도: CPU 기준 구현과 같은 결과, NPU 런타임 NMS와는 IoU 0.9 매칭 0.999
- 시각 요소: 네이티브 막대 차트 (3.25 vs 0.94) + 지연·정확도 작은 카드
- 각주(작게): GPU 1150 MHz · 디코더 1스레드 · 배치 1/슬롯 1 조건 (7번 슬라이드와 조건이 다르다)

## 9. ④ 최저 지연 운용 — 한 번에 한 장, 줄 세우지 않는다
- 배치 1 · 슬롯 1 · 입력 페이싱(카메라처럼 소스 시각에 도착) · 대기열 1칸, 처리 못 한 프레임은 버림
- 페이싱이 없으면 디코드 끝 기준 79 ms의 절반 넘게(약 42 ms, 추정)가 앞 프레임을 기다린 대기였다
- 결과: 도착 기준 평균 **58.4 ms**, 그 안의 입력 대기열 대기 약 14.5 ms, **입력 18.6% 버림**
- 그림: `../figures/fig05_input_queue.png` — 대기열 크기 N이 1 늘 때마다 b1/s1 평균 지연 +33.1 ms(1/30 s), 버림률은 거의 같음
- 주의: 58.4 ms 옆에 "입력 18.6% 버림"을 항상 같이 쓴다

## 10. ⑤ CPU는 거의 지휘만 한다 (2026-10-27 분리, 구 결과 요약의 ⑤ 줄)
- CPU는 큰 데이터를 만지지 않고 **작업 제출과 완료 확인만** 한다
- 완료도 일정 간격으로 확인(폴링)하는 대신 **완료 이벤트로 깨어나 기다린다**
- 결과: ①~⑤를 모두 적용한 최저 지연 운용점에서 응용 CPU **약 1.0 ms/프레임** (처리한 프레임 기준)
- 감소의 대부분은 ②·③의 몫이다
- 시각 요소: 개념 도식 — 가운데 CPU(작은 상자, "제출 · 이벤트 대기")에서 디코더·GPU·NPU로 가는 점선 제어 화살표, 하드웨어끼리는 굵은 실선 데이터 화살표(5번 구조도의 범례와 같은 선 규칙). "폴링 대신 이벤트 대기" 대비를 작은 두 칸(전/후)으로 보여도 좋다. 수치 축 없음
- 수치는 위 "약 1.0 ms/프레임 (처리한 프레임 기준)" 하나만. 다른 행과 비교하는 화살표·배율을 만들지 않는다
- 노트: 남은 CPU 일은 지휘뿐이다. 작업을 제출하고, 완료 이벤트가 오면 깨어나 다음 일을 넘긴다. 이렇게 해서 최저 지연 운용점에서 처리한 프레임당 약 1 ms가 남았고, 그 감소의 대부분은 앞의 ②·③ 덕분이다.

## 11. 결과 요약
- 표 (원고 표 1 그대로):

| 구성 | 응용 CPU (ms/프레임) | 지연 |
|---|---:|---:|
| 출발점: 형식 변환·NMS를 CPU에서 | 17.6 | – |
| ② NPU 형식(NHCW)을 GPU가 직접 생성 | 3.3 | – |
| ③ 결과 해석(NMS 포함)을 GPU로 | 0.94 (직전 3.25) | 79.2 ms (디코드 끝 기준) |
| ④⑤ 최저 지연 운용(입력 페이싱 + 대기열 1) | 약 1.0 | 58.4 ms (도착 기준), 화면까지 70.2 ms |

- 표 아래 각주(필수, 작게라도 반드시 남긴다):
  - 1~2행: GPU 960 MHz · 디코더 자동 스레드 · 배치 1/슬롯 2 (1,816프레임 3회 중앙값). 3~4행: GPU 1150 MHz · 디코더 1스레드 · 배치 1/슬롯 1 (900프레임 3회 중앙값)
  - 4행 CPU는 처리한 프레임 기준, 3·4행 지연은 기점이 달라 서로 빼지 않는다
  - 58.4 ms는 표시 없이 입력 18.6% 버림, 70.2 ms는 화면 표시를 켠 별도 실행(버림 19.1%)
- 검출 결과는 기준 경로와 같다 (1,816프레임에서 9,457개)
- 금지: "17.6 → 1.0 ms" 같은 한 줄 요약 화살표

## 12. 결론
- 핵심: CPU를 줄이는 열쇠는 연산을 빠르게 하는 것이 아니라 **CPU가 데이터를 읽지 않게 하는 것**
- 디코더·GPU·NPU가 dma-buf로 직접 주고받고, 형식 생성과 결과 해석을 GPU에 맡기면 CPU에는 지휘만 남는다
- 최저 지연 운용("한 번에 한 장, 줄 세우지 않기")에서 응용 CPU 약 1 ms/프레임, 도착 기준 58.4 ms (입력 18.6% 버림)
- 참고문헌은 13번 맺음말로 옮긴다(이 슬라이드에는 두지 않는다)
- 노트: 세 줄 요약을 다시 말한다.
